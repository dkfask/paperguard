## P1

### F-10 侧边栏导航静默失效，且无法自愈

**现象**
在写作页点击侧边栏「工作台」，页面毫无反应：URL 仍为 `/write/proj-30037c78611c`，内容仍是写作页。唯一痕迹是浏览器标签标题变为「角色工作台 · PaperGuard」，与实际页面不符。

**证据**

1. Console 两次同一错误（时间戳 `1790657081688` / `1790657146637`，间隔对应两次点击）：
   ```
   TypeError: Failed to fetch dynamically imported module:
     http://43.167.211.145:8080/assets/Workspace-CmasOBPq.js
       at index-CnKBjI5S.js:3:55564
   ```
2. Network：`GET /assets/DeadlineLabel-DdLFzSC7.js` → `502 Bad Gateway`，`failureReason: net::ERR_ABORTED`，耗时 5007ms（同一批嵌套依赖失败）。
3. 资产本身完好：服务器 `/var/www/paperguard/assets/` 中 `Workspace-*.js`、`DeadlineLabel-*.js` 均存在，外部直连 `200` / 145ms。属传输层抖动，非部署缺件。
4. **重试无效**：第二次点击产生第二次同样的 TypeError，浏览器缓存了失败的模块记录。整页刷新后点击「工作台」恢复正常（已验证）。

**代码根因**（`frontend/src/router.js`）

- `:34` 在 `router.beforeEach` 内即写入 `document.title`，早于路由组件解析，因此标题先变、页面后变，导航失败后标题不回滚。
- 全项目无 `router.onError()`，也无任何导航失败兜底：不弹提示、不给重试、不回滚标题。

**影响**
任意一次网络抖动（校园网、代理、CDN 超时、部署换名瞬间）都会让用户在当前会话内**永久失去侧边栏到该路由的导航能力，且零用户可见反馈**。与此前修复的三处权限死路同类，但成因在网络/路由层，API 层与 DOM 层均无法检出。

**修复方向**
- 新增 `router.onError()`，识别动态 import 失败（`TypeError: Failed to fetch dynamically imported module`）与 `NavigationDuplicated` 之外的真实失败，弹出可见错误条并提供「重试」按钮。
- 将 `document.title` 的写入从 `beforeEach` 移到 `afterEach`，避免标题与实际路由脱节。
- 失败时提示文案需区分「页面资源加载失败」与「网络异常」，并建议整页刷新作为兜底路径。

## P3

### F-02 缺失路径返回 200 HTML

nginx `location /` 的 `try_files $uri $uri/ /index.html` 使非 `/assets/` 的缺失文件返回 `200 text/html`：

```
/favicon.ico   → 200 text/html（内容为 SPA index.html）
/no-such-page  → 200 text/html（SPA 路由兜底，此项符合预期）
/assets/does-not-exist.js → 404（正确）
```

后果：缺失资源无法从状态码检出，浏览器拿到 HTML 当图片/脚本解析。

**修复方向**：为 `/assets/` 之外的静态扩展名（`.ico .png .svg .css .js .woff2` 等）加 `location` 精确匹配，命中即 `404`。

**修复方向**：部署脚本 rsync 排除 `._*` 与 `.DS_Store`。

### F-11 学生工作台「最近提交」的状态徽章无样式（结论已修正）

**初版结论有误，修正如下。**

初版依据截图判断「最近提交不显示状态徽章」。实际上 `StudentWorkspace.vue:58` **确实渲染了 `StatusBadge`**，后端 `_submission_list_view`（`backend/app/api/workflow.py:1543`）也正确返回了 `state` 字段（生产实测 `approved` / `returned`）。

真实根因：`.state-tag` 的配色规则写在 **`Workflow.vue` 的 `<style scoped>` 块**里。Vue 的 scoped 样式只对带该组件 scope id 的元素生效，而 `StudentWorkspace.vue` / `Workspace.vue` 渲染的 `.state-tag` 不带该 scope id，**因此徽章只有全局的 `display: inline-flex` 布局，没有任何底色、颜色、内边距**——渲染成一串裸文字，看上去就像「没有状态」。

**修复**：把 `.state-tag` 基础规则与各状态配色从 `Workflow.vue` 的 scoped 样式移到全局 `src/style.css`，并加注释说明不能放回 scoped。

**修复方向（已实施）**
- 为每条补状态徽章（复用既有 `StatusBadge`），并标出当前生效版本。
- 将 `.state-tag` 配色移入全局样式，避免 scoped 作用域导致徽章在其他视图失效。

### F-25【P0 安全】`/api/templates` 未认证即可读取学校论文模板

**发现**：审计匿名访问时，85 个 GET 接口里有 5 个不携带 token 也能返回 200：

| **`/api/templates`** | **漏洞** |

`backend/app/api/templates.py` 的两个读端点连 `Depends(current_user)` 都没有：

```python
@router.get("")
def list_templates(store: Store = Depends(get_store)) -> list[dict]:   # 无认证

@router.get("/{tpl_id}")

### F-15 权限收口：批次指导的学生可被教师重置密码（经产品决策）

上一轮把两套师生绑定合并展示后，教师能看到批次指导的学生，页面却写
「需管理员协助」——形成「看得到学生论文与进度，却管不了这个账号」的不一致。
**本轮经产品决策放宽**，且是**最小放宽**：

| 能力 | 账号绑定（`users.teacher_id`） | 批次指导（`supervision`） |
|---|---|---|
| 重置密码 | ✅ | ✅ **本轮新增** |
| 解绑 | ✅ | ❌ 保持不变 |

**为什么解绑不放宽**：解绑解除的是 `users.teacher_id` 这条账号绑定，
而批次指导关系挂在批次成员记录上，不是这个端点能解除的东西。
给批次来源加解绑按钮会让教师点下去必然失败，或产生语义错误的操作。

**实现**：新增 `_is_supervised_student(store, teacher_id, student)`，
两种来源任一成立即为本人指导；重置密码端点改用它，
解绑端点保持 `users.teacher_id` 比对不变。

**接口新增字段** `can_reset_password`，与 `can_manage_account` 分离，
前端两个按钮各用各的权限。关系说明文案同步改写（中英文）。

**回归测试**：后端新增用例覆盖——批次来源可重置、批次来源解绑仍 403、
无任何关系的其他学生重置 403、他人账号绑定学生重置 403；
前端用例锁定两个按钮不混用权限。经变异验证。

## 第七轮：写操作与 IDOR 权限面审计（2026-09-30）

第五轮做了读侧的四角色交叉验证，但**写操作只扫了「是否要求登录」**。
写操作越权比读更危险（可改数据、可改权限），而且真正的风险面在
**带路径参数的接口**——能否读写/删除他人拥有的资源（IDOR），
而第五轮恰好把这些接口全部跳过了。本轮补上。

### 扫描一：低权限角色遍历全部写接口

用生产库副本，以 student / teacher 身份逐个调用 129 个无路径参数的写接口。

| 角色 | 可成功执行的接口 | 判定 |
|---|---|---|
| student | `DELETE /api/ai/config`、`POST /api/auth/logout` | 均非越权 |
| teacher | 同上 | 均非越权 |

`DELETE /api/ai/config` 初看像「任何人删系统 AI 配置」，实为误判：
它执行的是 `store.set_user_ai_config(user["id"], None)`，删的是**当前用户自己的**
AI 配置；系统级配置在 `/api/ai/admin/config`，用的是 `require_admin`。

> 记录这次判据错误：不能把「低权限角色能调用」直接等同于越权，
> 必须先分清接口操作的是**个人资源**还是**系统/他人资源**。

### 扫描二：IDOR（他人资源）

student_b 尝试操作 student_a 名下的真实项目与提交：

| 操作 | 返回 | 判定 |
|---|---|---|
| 读他人项目 | 403 | 拒绝 |
| 改他人项目章节 | 403 | 拒绝 |
| 改他人项目封面（空体） | 422 | 参数校验先行 |
| 改他人项目封面（**合法体**） | **403** | 拒绝 |
| 把他人项目丢进回收站 | 404 | 拒绝 |
| 触发他人项目导出 | 404 | 拒绝 |
| 读他人提交 | 403 | 拒绝 |
| 给他人提交加批注（**合法 schema**） | **403**「无权访问其他学生的阶段任务」 | 拒绝 |
| 审批他人提交 | 404 | 拒绝 |
| 访问教师接口 | 403 | 拒绝 |
| 读自己 AI 配置 / 自己信息（对照组） | 200 | 设计如此 |

**422 的那一环必须追到底**：参数校验排在权限校验之前，合法请求体下
是否就会放行？用 `CommentCreate` 的真实字段（`body`/`severity`/`block_id`）
重试后确认仍是 403，事后复查攻击者也读不到该项目（403）。
结论：422 只是校验顺序，**不是**藏着的越权。

### 结论

读侧与写侧、匿名与已认证、个人资源与他人资源，四种组合全部核实完毕：
**未发现越权**。本轮没有产生代码改动，只补充了审计证据。

这也是第七轮没有新缺陷产出的原因——前几轮已经把明显的洞堵上了，
剩下的风险集中在「参数校验顺序」这种需要构造合法请求体才能验证的角落。

### P0-01：`POST /api/auth/role-certification` 缺前置条件（越权）

**这是本轮真正的发现，也是上一轮「已完成」结论漏掉的东西。**

`/role-certification` 是注册后的身份自助认证入口。前端路由在
`router.js:44` 只写了「`user` + `unselected` 的人要被**送去**这个页面」，
**没有写反向**：已经是 `student`/`teacher`/`admin` 的人**不许进**。
后端 `submit_role_certification` 也只有 `Depends(current_user)` 一道校验。

于是任何已登录角色都能调这个端点，而它的两条分支都很危险：

- `role="user"` 分支会**立刻**覆写调用者自己的
  `role`、`status`、`role_application_status` 并 `save_user`，
  **全程不经过任何审批**；
- `role="student"|"teacher"` 分支把 `requested_role` 与
  `role_application_status="pending"` 写进去——而管理员审批端点
  （`api/auth.py:317`）会执行 `target["role"] = target["requested_role"]`。
  也就是说「申请更高角色」这条路对**已获批账号**同样成立。
- `GET` 端点更直接：`store.list_organization_units()` **没有任何作用域过滤**，
  全量学校/学院组织树发给任何登录用户。UAT 只有一所学校所以看不出来，
  生产有真实数据时任何学生都能枚举全校组织结构。

**生产实测证据**（用 UAT 教师账号，事后已完整还原并经 API 复核）：

```
变更前  role=teacher  status=active  role_application_status=""
POST /api/auth/role-certification {"role":"user"}
变更后  role=user     status=active  role_application_status="approved"
```

**一个正式的 active 教师，被自己一次 POST 降成了 user，全程没有管理员参与。**
这条链路是纯 API 就能走通的，不需要浏览器，也不需要任何界面缺陷配合。

> 为什么前七轮没发现：这个端点不在逐屏审查的路径上——它要求
> `user`+`unselected` 的账号才能进，而这种账号既没有真实业务数据、
> 也不在任何一屏里出现。之前的 170 次 GET × 4 角色安全扫描
> **全是读接口**（`GET /api/teacher/students` 之类），
> 写操作审计也只覆盖了「按路径参数枚举」，没有单独审「谁能改自己的角色」。
> 这是审计方法的盲区，不是执行疏忽。

**修复**（`backend/app/api/auth.py`）：

```python
def _require_unselected_user(user: dict) -> None:
    if user.get("role") != "user":
        raise HTTPException(status_code=403, detail="当前角色无需学校身份认证")
```

GET 与 POST 各自在入口调用。前端 `router.js` 同步加了反向守卫，
把不该看到的入口藏起来（后端才是安全边界，前端只负责不给入口）。

**注意这里只判 `role != "user"`，没有额外要求 `unselected`**：
被驳回的申请者 `role` 仍是 `user`，必须还能重新提交。
专门写了 `test_rejected_user_can_reapply` 守住这一点，
以及 `test_unselected_user_still_keeps_the_legit_flow` 防止「越权修过头」
把正常认证流程一起挡掉。

**变异验证**：把 `_require_unselected_user` 的判断改成 `if False: pass`
（用 `assert old in s` 确认锚点真的命中并替换），
`test_role_certification_rejects_non_user_roles`、
`test_role_certification_teacher_is_also_locked_out`、
`test_role_certification_options_do_not_leak_org_tree` 三个用例立刻 failed，

## 第十轮：给验证设施本身补上防假绿的自测

### 起因

上一轮我把 P0 越权修完、部署完、复验完，结论是「未结清项只剩 2 项」。
这一轮回头审**验证设施本身**，发现两个问题——其中一个是本项目第三次
栽在同一个地方：**假绿**。

### 问题一：部署表里的「当前生产版本」又陈旧了（第二次）

第九轮我给部署表补到 `56eae5d-rc9`，但第 519 行仍然留着
「`b674943` …**当前生产版本**」。加上更早那次（`b418904` 标成当前版本时
生产已是 `b674943`），**同一个标注已经陈旧两次**。

根因不是忘了改，是**做法本身有问题**：在一张只会追加的历史表里
手工维护「当前」这种易变状态，每发一次版它就必然过期一次。
而过期的部署信息比没有更危险——回滚时会照着错的版本号去找不存在的目录。

**结构性修复**：部署表不再内联标注「当前生产版本」，只做纯历史记录。
唯一权威源改为服务器上的版本标记文件：

```bash
ssh perpetual 'cat /home/ubuntu/paperguard/current-release'
```

并新增 `ops/check-report-version.sh`，把「报告部署记录最后一行声称的版本」
与「生产标记文件」对一遍，不一致就非零退出。

它的四个场景都实测过（**不确认变异生效的验证等于没验证**）：

| 场景 | 期望退出码 | 实测 |
|---|---|---|
| 报告与生产一致 | 0 | 0 ✓ |
| 报告版本写错 | 1 | 1 ✓ |
| 报告里没有部署行 | 2 | **初次写成 1，已修** |
| 报告文件不存在 | 2 | 2 ✓ |

「没有部署行」初次返回 1 而不是 2，原因是 `set -euo pipefail` 下
grep 无匹配会让整个命令替换以 1 退出，脚本在走到那条空值检查之前
就被掐掉了。**1（版本不一致）和 2（输入错误）含义不同，自动化才分得清**，
已加 `|| true` 修掉。

### 问题二：自测给了我自己一个假绿灯

第九轮我给 `ui-verify.mjs` 的假绿做了修复，但**只修了产品脚本，没写自测**。
本轮补 `ops/test-ui-verify.mjs`（回环 mock，不碰生产），
先写 5 个场景，跑通了，就当它有效。

然后做变异验证：把 `record()` 的状态归一化整个删掉
（`assert old in s` 确认锚点命中并替换），重跑自测——

**11/11 通过。** 自测完全没抓到刚刚被我修掉的那个缺陷。

原因很具体：场景 1–5 全都走 `assert()`，而 `assert()` 传的是
**字符串** `'passed'` / `'failed'`，所以归一化删不删都照样能抓到。
而真正的假绿只发生在**引导页那处直接传原始布尔**的代码路径上，
mock 从来不走那条路。

也就是说：**我写的自测测的是相邻的东西，不是那个缺陷本身。**
它转绿不是因为被测代码正确，而是因为它压根没碰到出问题的地方。

补了场景 6：让 mock 把 `/first-login` 渲染成空白页
（「接口全 200 但界面空白」正是真实存在的故障形态），
强制引导页那处布尔求值为 false。重放同一个变异：

```
[PASS] scenario6.blank_onboarding_page_fails_loudly   （变异前）
[FAIL] scenario6.blank_onboarding_page_fails_loudly — exit=0（应 1）result=passed（应 failed）
[FAIL] scenario6.boolean_false_becomes_string_failed — 引导页检查项 status=false
ui-verify 自测: 11/13 通过
```

`status=false` 就是那个假绿的原始形态，自测抓住了它。
还原后 13/13 全绿。生产重跑 37 项全过，无回归。

### 顺带修的两处

- `ui-verify.mjs` 原来**强制要求教师+学生两个账号都提供**才肯跑。
  实际排查时手上往往只有一个账号，硬性要求只会让人把整个脚本绕开。
  改为「至少提供一个，缺的跳过并提示」，全缺才退出 2。
  写自测时第一版直接撞死在这上面才发现。
- 角色面板的 `main_content_rendered` 断言：自测 mock 的主区只有 100 字符，
  低于 120 阈值，每轮都要空等满 20 秒超时，整套自测跑两分钟。
  这不是产品问题而是 mock 太瘦，但也说明阈值需要有依据——
  已把 mock 加到 600 字符并把自测的导航超时压到 6s。

### 这一轮的教训

同一个坑栽了第三次，**每次形态还不一样**：

1. 备份时机错误 → 变异后测试仍全过（假绿）
2. `record()` 收到布尔 → 汇总漏判失败（假绿）
3. **自测没覆盖出问题的代码路径 → 自测对变异无动于衷**（假绿的假绿）

第 3 条最隐蔽：前两条里我至少还知道自己在测什么，
而这一条里**测试报告本身就是那个错误信号**，而且它看起来比前两条更可信
——毕竟「13/13 通过」比「测试失败了」更像安全。

结论不是「以后小心点」，而是：**自测必须先证明自己能失败。**
写完自测的第一件事不是跑它确认通过，而是**注入一个已知缺陷看它会不会转红**。
转红了才说明这个自测有分辨力；一直绿的自测只说明它没在测任何东西。

### 为什么这个盲区值得单独立护栏

P0-01 之所以躲过前七轮，不是因为谁粗心，而是**审计方法的结构性盲区**：
此前的写操作审计覆盖的是「拿路径参数去改别人的东西」，
而「改**自己**的记录」拿到的是 `Depends(current_user)` 返回的对象，
**根本没有路径参数**，天然落在枚举之外。

这类盲区靠「下次更仔细」补不上——它必须变成一个每次提交都会跑的结构检查。
