# AI 功能 SaaS 符合性评估

日期：2026-09-30　范围：`backend/app/api/ai.py`、AI 配置存储、AI 写作调用链路
方法：代码审读 + 对 SSRF 与隔离性做实证探针，不以「看着像」下结论

---

## 结论

**配置模式是 SaaS 的，但运行治理不是。**

三级配置解析（用户自带 → 系统默认 → 环境变量兜底）、密钥不回传、
`/status` 供前端门控，这些是对的。问题集中在**多租户运行治理**：
出口地址不受控、系统级配置无租户隔离、无限流无配额无用量、密钥明文、
配置变更不进审计。

对**单校私有化部署**，S1（SSRF）与 S3（成本敞口）仍成立。
S2/S6 的严重度取决于是否一套部署服务多所学校，见各项说明。

---

## 一、符合 SaaS 的部分

| 做法 | 位置 | 说明 |
|---|---|---|
| BYOK 三级配置 | `ai.py:_resolve_cfg` | 用户自带 > 系统默认 > 环境变量，是标准多租户 AI 接入模式 |
| `/status` 供前端门控 | `GET /api/ai/status` | 返回 `enabled`/`source`/`model`，支持渐进式开通（未配置不显示入口） |
| 密钥不回传 | `GET /api/ai/config` | 只返回 `api_key_masked`（末 4 位） |
| 更新时允许留空沿用旧密钥 | `_request_cfg` | 管理员/用户改模型不必重输密钥，交互正确 |
| 系统配置 `require_admin` | `ai.py` 管理员端点 | 权限边界正确 |
| 动作白名单 + 输入长度上限 | `_ACTIONS` / `_MAX_INPUT_CHARS` | 防止任意动作与超长输入 |
| 双协议兼容 | `_chat_completion` | OpenAI / Anthropic Messages 自动分流，base_url 缺 `/v1` 自动容错，降低配置门槛 |
| 前端状态完整 | `AiSettings.vue` | loading / 测试连接 / 配置来源标识（数据库 vs 环境变量） |

## 二、不符合项

### S1【高】SSRF：用户可控制 base_url，服务端代其访问任意地址

**实证**（`/tmp/ssrf-probe.py`，本地探针）：

```
保存用户 AI 配置: 200
assist 状态: 200
内部监听器是否被命中: 是 ← SSRF 成立
  命中路径: /chat/completions
  收到头: {"Host": "127.0.0.1:51542", "Authorization": "Bearer sk-attacker-controlled"}
  发出正文: {"model":"whatever","messages":[{"role":"system","content":"你是一名中文学术论文写作助手…}
```

任何已登录用户（学生即可）保存一个指向内网地址的 `base_url`，
之后每次调用 `/api/ai/assist` 都会让服务端向该地址发起 POST，
并把**论文正文**作为请求体发过去。

`ai.py:93` 的 `_normalize_base_url` 只做 `strip()` + 去尾斜杠，
无 scheme 限制、无 host 白名单、无私网/回环/链路本地地址拦截。

**SaaS 影响**：多租户 SaaS 中「用户可传 URL + 服务端代发请求」是经典 SSRF 载体。
可用于探测内网服务与端口、访问云元数据端点（`169.254.169.254`）、
触达仅内网可达的管理接口；响应差异还能用于端口扫描。

**建议**：出口 URL 校验——仅允许 `https`（按需放行 `http`）、
解析主机后拒绝私网/回环/链路本地/保留网段、必要时加域名白名单；
校验须在**每次请求前**做（DNS 记录可能变化），不能只在保存配置时做一次。

### S2【高·取决于部署形态】系统级 AI 配置无租户隔离

`system_settings` 是**全局键值表，无租户列**（`db.py:166`），
`ai_default_config` 全库只有一份（`db.py:795`）。

`PUT /api/ai/admin/config` 一次改动，**全体租户立即受影响**。
没有按学校隔离、没有按套餐分层、也没有「本租户禁用 AI」的开关。

**严重度取决于**：
- 一校一套私有化部署 → 影响面等于全校，属产品决策不一定是缺陷
- 一套部署服务多所学校 → 这是明确的跨租户越界

代码里已有 `organization_id` 维度的组织树与 `_visible_unit_ids` 作用域机制，
说明架构是按多学校设计的，但 AI 配置没有跟上。

**建议**：给 `ai_default_config` 加 `organization_id`，或明确记录
「本系统为单租户部署」并在文档中写清，避免后续被当成多租户用。

### S3【高】无限流、无配额、无用量记账

- `POST /api/ai/assist` **没有任何速率限制**（全项目 grep 无 ratelimit/throttle/limiter）
- **没有任何 AI 用量记录**：无 token 计数、无调用次数、无成本归集
  （`ai_usage_declared` 是学生申报字段，与用量统计无关）
- 无单用户日配额、无租户总额度、无超限提示

**对照**：同一个项目里连微信推送都做了 `mini_program_push_quotas` 表
（`db.py:150`）和 `consume_push_quota`，唯独成本更高的 LLM 调用没有。

**SaaS 影响**：LLM 是按量计费资源。无限流意味着单个账号被盗或脚本失控即可
烧掉全部额度；无用量记录意味着无法计费、无法分摊成本、无法回答「谁花了多少」。
这是 SaaS 与内部工具最本质的区别之一。

### S4【中】密钥明文存库

`set_system_ai_config`（`db.py:807`）以 **JSON 明文**写入 `system_settings`，
用户级密钥同理。读库即得全部 LLM 密钥。

**SaaS 实践**：密钥应加密存储（应用主密钥或 KMS 派生），
目标是「DB 泄露 ≠ 密钥泄露」。当前状态下 DB 备份、只读副本、
误开的运维查询都会直接暴露计费凭证。

### S5【中】AI 配置变更不进审计台账

项目**已有**完整审计设施：`audit_events` 表（`db.py:233`）+ `_audit()`，
在 `specs.py`、`process_records.py` 等多处调用。

但 `api/ai.py` **零审计调用**。管理员更换系统级模型与密钥是重要配置变更，
在学术诚信产品上尤其需要留痕（谁在何时把系统默认模型指向了哪个服务）。

### S6【中·取决于部署形态】无数据出境与委托处理披露

用户论文全文会作为 prompt 发往系统默认配置所指向的第三方模型服务。
当前**没有**：用户同意流程、数据处理说明、「内容是否用于模型训练」的告知、
以及不同租户可选不同数据处理地。

对涉及未发表学术数据的系统，这是合规要点；若服务境外模型服务还涉及数据出境。

### S7【低】上游故障无熔断

超时默认 60s（`PAPERGUARD_AI_TIMEOUT`），无重试上限、无熔断、无并发上限。
上游不可用时，每个请求都会占满一个连接 60 秒，容易在故障期间放大成
自身资源耗尽。

### S8【低】依赖注入写法与全项目不一致

`ai.py` 全部用 `Depends(lambda: Store())`，其余模块用 `Depends(get_store)`。
功能等价但每请求新建实例，风格不统一，改动容易漏。

## 三、建议处理顺序

| 优先级 | 项 | 理由 |
|---|---|---|
| P0 | S1 SSRF 出口校验 | 可被普通用户触发，指向内网，属于可利用的安全问题 |
| P0 | S3 限流 + 配额 + 用量记账 | 成本敞口无上限，SaaS 化的硬性前提 |
| P1 | S4 密钥加密存储 | DB 泄露即密钥泄露 |
| P1 | S5 配置变更审计 | 产品已有设施，补调用即可 |
| P2 | S2 / S6 租户隔离与数据披露 | 取决于是否多租户部署，需先定产品形态 |
| P3 | S7 熔断、S8 风格统一 | 健壮性与一致性 |

## 四、一个前置问题

S2 与 S6 的处理方案都取决于同一个尚未明确的前提：
**这套系统是「一校一套私有化部署」还是「一套部署服务多所学校」？**

当前代码同时具备两者的特征：有 `organization_id` 维度的组织树与作用域机制
（倾向多租户），但系统级配置、邮件配置等又是全局单份（倾向单租户）。
这个前提不定下来，租户隔离的改法差异很大（加 `organization_id` 列
vs 明确声明单租户并写入文档）。
