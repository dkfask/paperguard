## 二、逐项说明

### S1 SSRF（已修，`573312d`）

新增 `backend/app/services/outbound_guard.py`，守卫生效在**请求入口**
（`ai_assist` 与两个 `/config/test`），且在**消耗配额之前**——被拦的请求
不占用用户额度，也就不需要退款逻辑。

关键设计是**解析 DNS 并逐个检查返回地址**，而不是检查字符串。实证：
`getaddrinfo` 会把 `2130706433`、`0x7f000001`、`127.1` 全部解析成
`127.0.0.1`，而 `ipaddress` 解析不了这些写法——只做字符串检查的实现
会全部漏掉。

保存路径只做语法级检查（`resolve_dns=False`）：让保存成败取决于 DNS
可用性不合理，而 DNS 记录会变，TOCTOU 下「保存时安全、请求时不安全」
可利用，所以安全边界必须在请求前。

### S2 租户隔离（已修，`742612d`）

迁移 `0010_tenant_system_settings`：`system_settings` 增加
`organization_id`，复合主键 `(key, organization_id)`。

**SQLite 无法给已有表改主键，只能重建表**。存量行一律归到
`organization_id=''`（平台全局默认），因此升级后行为不回退——原来生效的
配置仍然生效，只是从此可以被单校覆盖。

拆成两个方法是刻意的：`get_system_setting`（不回退）与
`get_tenant_system_setting`（回退）。混在一处会让人误以为「A 校读不到就
自动用平台配置」，而那正是要修的跨租户外流。

`_resolve_cfg` 按 `_school_of(user)` 解析，取不到学校时回退全局默认，
不让「组织信息不全」的用户直接失去 AI 功能。

**范围说明**：数据保留策略（`operations.py` 的 `retention_policy`）
**仍保持平台级**。它是平台运维配置而非租户数据面配置，按校区分反而会
让保留期出现歧义。这是明确的取舍，不是遗漏。

### S3 限流与记账（已修，`c833954`）

新增 `ai_usage` / `ai_quota` 两表（迁移 `0009_ai_usage_quota`）与
`services/ai_governance.py`。

- 配额消费是**原子**的：一条带 `WHERE used < limit` 的 upsert 完成
  「判超限 + 计数」。先查后写有并发竞态——两个请求同时读到
  `used=limit-1` 会双双通过检查（变异验证用 60 线程复现）。
- 先扣突发再扣日配额；突发被拒时归还日配额，避免用户被两处同时卡住。
- `organization_id` 在**调用时**落库。不在汇总时再关联用户表——用户之后
  调换学校会让历史用量归属跟着漂移，计费口径就不成立。
- 失败也记用量：失败同样消耗上游成本。

### S4 密钥加密（已修，`887283a`）

新增 `services/secret_store.py`，标准库 encrypt-then-MAC，**不引入
`cryptography`**（带原生扩展，部署时新增二进制依赖，多一个 wheel 就多一处
升级失败点）。将来换 Fernet/AESGCM，替换点只有两个函数。

密文格式 `pgsec1$<nonce>$<cipher>$<mac>`。选择 MAC 而非纯 XOR 流的理由：
同库的 `auth.py::_openid_cipher` 就是派生流 XOR，它对篡改毫无检测能力；
而 API Key 会被原样拼进 HTTP header，攻击者改一字节不会报错，只会让请求
打向他自己的地址。

**主密钥缺失时不阻断读取**：存量明文在未配置 `PAPERGUARD_SECRET_KEY` 时
仍要能用，否则一次配置遗漏会让全平台 AI 立刻不可用；新数据则明文落库
并告警，便于运维发现「忘了配主密钥」。

生产已生成 64 位 hex 主密钥写入 `/etc/paperguard/paperguard.env`（权限 640），
存量 1 条明文配置已迁移为密文。

### S5 审计（已修，`a9d2827`）

覆盖四个变更端点（用户级存/清、系统级存/清）。

审计里**只放元数据**：base_url 的 host 与 model 名。API Key 和论文内容
都不进审计流——它是管理端可见的，凭据不该出现在那里。

审计写入失败**不阻断**配置写入。若审计表出错就让管理员改不了配置，那
是在用可追溯性换可用性，两头都输。

### S6 数据出境披露（已修，`1ca81d1`）

`GET /api/ai/disclosure` 返回**实际生效**的接收方 host（走
`_resolve_cfg`，因此与真实流量一致），管理端 AI 设置页在表单上方显示披露
区块并实时回显当前 Base URL 的主机名。

披露由服务端给出而非写死在界面文案，理由是接收方随配置而变——用户可能
自带 key 指向别家供应商，前端写死就成了**假披露**，比不披露更糟。

### S7 熔断（已修，`b5dca3d`）

`services/ai_breaker.py`，进程内实现，不引入 `pycircuitbreaker`。

连续失败 5 次（`PAPERGUARD_AI_BREAKER_THRESHOLD`）后打开，冷却 30 秒
（`PAPERGUARD_AI_BREAKER_RESET_SEC`）后半开，**只放 1 个探针**——刻意如此：
冷却结束那一刻若所有等待请求一起冲过去，熔断等于没开。

按**上游端点**（base_url）聚合而非 api_key：同一供应商多密钥故障通常是
同一个原因，按端点聚合才能在第一次撞墙时就保护住。

### S8 依赖注入统一（已修，`b5dca3d`）

全项目 185 处用 `Depends(get_store)`，只有 15 处写
`Depends(lambda: Store())`。两种写法并存时测试要 monkeypatch 的入口就有
两个，漏掉一个就会出现「测试全绿但线上走了另一条路径」。

`ai.py` 10 处、`teacher.py` 4 处、`auth.py` 的 `current_user` 1 处全部改掉。

### 两个值得记下的测试教训

**1. 变异 C 最初是假绿。** S3 的 9 条用例全在服务层直接调
`ai_governance`，没有一条从 HTTP 入口证明 `/api/ai/assist` 真的会调配额
校验——把入口里的 `begin_call` 整段删掉，9 条仍然全过。补了
`test_assist_endpoint_enforces_quota_over_http`（直接打 HTTP 断言 429 且
请求没发往上游）才真正捕获。

**2. `test_ai_audit` 曾间歇性失败。** 根因是它按 action 前缀 + `events[0]`
取审计事件，而 S2 之后同一个 action 有 `ai_config:system` 和
`ai_config:system:<school>` 两种 `resource_type`；`test_ai_api.py` 也用
admin 身份写系统配置，两者同为 admin，且 `list_audit_events` 在同一秒内
多条记录顺序不保证稳定。改为 **action + resource_type + actor_id +
reason 里的 model 名** 四重精确过滤后，全量连跑 4 次全绿。
