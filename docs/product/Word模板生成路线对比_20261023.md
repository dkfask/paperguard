# Word 模板生成路线本地对比

日期：2026-10-23。对比对象：PaperGuard 现有锚点渲染器、docxtpl 0.20.2、docx4j 17.3.3。

## 1. 结论与建议

本次真实模板的基础试填，没有显示必须整体更换生成引擎的理由。建议继续补齐现有 Python 锚点路线的模板准备、字段样式、结构保护和独立成品检查。docxtpl 可作为标准化模板的候选适配器；docx4j 保留为复杂内容控件和数据绑定的候选组件。

三条路线都能在明确映射后填入封面字段和单段正文，保留本轮检查的表格、分节、关系与媒体。完成内容控件的样式准备后，对应输出在同一 LibreOffice 环境下逐页像素一致。

这个结果只证明本次有限场景下的输出一致。姓名、学号空白格的试填仍存在字体大小观感偏小的问题，说明显式字段样式是共同缺口。三条路线也都不能据此直接宣布符合学校规范或通过 Word/WPS 验收。

## 2. 样本与实验范围

样本是用户提供的“毕业设计（论文）毕业论文（报告）-物联网工程-软硬件结合项目内容参考模板 - 1101.docx”。原始文件没有被修改。

- 原始 SHA-256：`2dc61a4635ff749d98ddfd70c2fdb8dd268cb07253d08a2d1f7c21b35eb10f76`。
- 包内结构：正文 1 张封面表格、9 个 `sectPr`、7 个页眉部件、2 个页脚部件、6 个媒体文件。
- 映射位置：封面右列的 6 个字段，以及正文 XML 的第 21 个直接元素，即中文摘要的一段示例文字。
- 短文本：65 个字符，包含中文、数字及 `& < >`，验证文本转义。
- 长文本：6020 个字符，仍作为一个段落插入；不代表完整论文章节的生成测试。

实验分别执行原样保存、短文本试填、长文本试填，共得到 9 个最终原型文件。现有锚点与 docxtpl 使用相同的占位符准备副本；docx4j 使用绑定相同位置和数据的内容控件副本。

本轮直接调用渲染器，没有通过网站准入、项目创建、正式导出、归档或下载入口。这些实验不能证明网站当前已允许使用此模板。

## 4. 影响选型的实际差异

### 4.1 现有锚点路线的修改范围较小

当前渲染器已经能在表格单元格内识别明确占位符。本轮试填不需要重建封面表格；填入位置外的正文结构指纹也保持不变。

但它仍会重新序列化页眉页脚等故事部件，并未实现所有未编辑 XML 部件逐字节复制。现有模板准入、稳定单元格定位、空白字段样式和完整源包复检仍需补齐。

这说明现有基础可以继续使用；本轮没有验证它已经覆盖任意模板或正式业务全流程。

### 4.2 docxtpl 会修改未填入区域的标识和空白属性

本轮短文本输出中，填入区域外发现 10 处图形 `id` 改写，以及 7 处 `xml:space` 属性改写，没有发现属性删除。对应渲染在本次 LibreOffice 环境中仍与现有路线一致。

这些变化不能直接定性为版式破坏，但也不能按“只改绑定位置”自动放行。接入时需要解释并验证这些变化的影响。[docxtpl 渲染源码](https://github.com/elapouya/python-docx-template/blob/master/docxtpl/template.py#L473)

它的主要价值是复用占位符、循环和表格等成熟语法；普通标记的 run 范围和复杂区域语法仍需模板准备流程处理。[官方文档](https://docxtpl.readthedocs.io/en/latest/)

### 4.3 docx4j 需要正确准备控件样式

初始实验仅绑定了内容控件的值，没有将原文字 run 属性复制到 `w:sdtPr/w:rPr`。结果填入文字丢失了部分字号和字体属性，长文本渲染为 25 页。补齐控件样式后，相关格式指纹恢复，长文本为 27 页，并与其他路线逐页像素一致。

因此，控件创建与数据绑定需要作为一个完整适配过程验证。本轮结果不支持把初始差异解释为 docx4j 普遍无法保留样式。[官方绑定实现及变更记录](https://github.com/plutext/docx4j/blob/VERSION_17_3_3/CHANGELOG.md)

绑定时还观察到以下改写：

- 部分布尔属性从 `0/1` 转为 `false/true`，属于需要解释的表示差异。
- VML 备用图形分支中有 5 处 `w14:anchorId` 属性被省略。
- 部分嵌入图形数据的文本表示和数字属性发生规范化。

这些改写在本次 LibreOffice 页面中没有表现出差异。Word/WPS 对备用分支的行为本轮未验证，因此不能把这些属性省略直接加入通用允许清单。

### 4.4 三条路线都需要显式定义空白字段的格式

姓名、学号单元格在原件中为空，实际试填均出现比其他字段偏小的文字。字段的可见文字 run 并没有完整的直接字体属性；三条原型均沿用了该状态。

因此，字段定义应保存经确认的字体、字号和对齐等要求，并检查生成文字的有效样式。原模板的说明文字、段落标记属性和真正的文字 run 属性也需要区分。三份输出彼此一致，不能代替对这些要求的核对。

## 5. 接入与维护比较

下表是结合本次实验、现有代码及候选官方能力作出的工程判断，不是性能或成熟度排名。

| 维度 | 现有锚点路线 | docxtpl | docx4j |
|---|---|---|---|
| 运行环境 | 沿用 Python | 沿用 Python，新增依赖 | 需要 Java 组件和调用边界 |
| 模板准备 | 明确占位符、书签或控件等位置 | 使用其模板标记和专用语法 | 内容控件、XML 绑定和控件样式 |
| 本次局部修改的可控性 | 最少额外正文改写 | 需解释全局 ID / 空白属性变化 | 需解释绑定后的规范化和备用属性变化 |
| 已有复杂数据绑定能力 | 有限，需要逐项补齐 | 可复用循环、表格等语法 | 原生内容控件绑定、重复与条件机制值得进一步验证 |
| 独立校验和业务门禁 | 继续由 PaperGuard 完成 | 同左 | 同左 |
| 建议定位 | 当前实施主线 | 可选模板适配器 | 复杂绑定的候选组件 |

docx4j 的复杂内容控件和 OpenDoPE 能力以[官方入门文档](https://github.com/plutext/docx4j/blob/VERSION_17_3_3/docs/Docx4j_GettingStarted.md)为依据，本轮没有实测这些高级场景。其他候选项目的资料比较见[GitHub 调研报告](Word模板一致性_GitHub调研_20261023.md)。

## 6. 证据与验证边界

本轮环境为 Python 3.12、python-docx 1.2.0、lxml 6.1.1、docxtpl 0.20.2、Java 17.0.20、docx4j 17.3.3。渲染器为随工作区依赖提供的 LibreOfficeDev 26.8.0.0.alpha0，使用 96 DPI 和本地字体配置。

默认渲染配置最初没有正确显示中文。配置字体目录及宋体、黑体等字体别名后，重新渲染了基线及最终输出。报告中的页数和像素结论均来自这组配置，不能与其他机器或真实 Word/WPS 的页数直接等同。

本轮完成了 9 份输出的 SHA-256 绑定核对，以及删除页脚、删除分节、修改表格属性、修改填入文字字号这 4 个负向对照。负向对照验证的是实验比较脚本，不是网站正式导出门禁。
