## 0. 本规格要解决什么

W-02 建存储、W-03 建上下文与授权、W-04 建隔离。本包解决**人怎么进来**：

成员邀请、名册导入、教师认证、组织授权、租户切换 UI。

§24.2 把 **AT-08/09/10/11** 四条归给本包，全部指向同一件事——
**批量把外部身份变成租户成员，且不能出错、出错不能半途越界。**

### 0.1 现状取证（2026-10-01，代码只读）

`backend/app/api/teacher.py:152-229` 的 `bulk_import_students` 是当前唯一的批量建号路径：

| 事实 | 位置 | 对本包的意义 |
|---|---|---|
| **部分成功语义**：`success_count` + `failed_list` 逐条 continue | `teacher.py:158-229` | 无事务、无预检；**部分成功即部分越界**（AT-09） |
| **无预检报告**：直接边校验边写 | 同上 | AT-10 要求「预检报告」，当前**不存在** |
| **`default_password` 由请求体传入明文** | `teacher.py:198` `hash_password(req.default_password)` | 密码经 HTTP 明文传输并可能被记录；**总设计 9.1 行有脱敏要求** |
| **不写 `organization_context`** | 同上 | **INC-09**：导入的学生无学校归属，迁移后会被 RLS 过滤成「看不到数据」 |
| `teacher_id` 是全局单值 | `teacher.py:207` `"teacher_id": user["id"]` | 跨租户师生关系无数据库级约束（W-04 §4 负例 2） |
| 邀请路径 | `backend/app/api/auth.py:144-151`（无邮箱注册） | `organization_context` 不强制（INC-09 五条路径之一） |

> **「部分成功」不等于「安全」。** 当前实现里前 3 条成功、第 4 条失败时，
> 前 3 条的账号**已经落库**——如果这 3 条属于不同组织或不同名额，
> 失败点之后没有任何回滚。AT-09 的「错误不部分形成越界授权」正是针对这一点。

## 1. 导入的两阶段契约

**把「校验」与「写入」彻底分开**，这是 AT-10「预检报告」与 AT-09「不部分形成越界」的唯一共同解法。

```
阶段一：预检（只读，无副作用）
  输入：名册行 + 目标租户/组织 + 名额状态
  输出：逐行 verdict（CREATE / CONFLICT_SKIP / BLOCKED）+ 汇总统计
  保证：**不写任何库**；同一输入重复预检结果完全一致（幂等）
        ↓
       人工/调用方确认
        ↓
阶段二：提交（单事务）
  输入：预检报告 + 确认后的行
  保证：**全成功或全失败**；任一行失败则整个事务回滚
```

### 1.0 两阶段契约的规则（IMP-1～IMP-6，2026-10-02 补）

> **为什么补这一节（INC-75）**：本节是 W-05 **最承重的契约**——
> AT-09「不部分形成越界」与 AT-10「预检报告」的**唯一共同解法**就是它。
> 但它此前**整节没有编号规则**，而 §2 起每条约束都有 `XX-N`。
> 后果有二：① 总设计 §18.2 的 `POST /tenants/{t}/member-imports/preview`
> **没有任何规则级锚点可绑**，只能标 ⚠；② `spec_rule_id_check` 的 RI-1
> （悬空引用）与 EP-2（接口归属绑定）**都看不见它**——
> **没有编号的东西既无法被引用，也无法被检查**。
> **规则编号不是形式，是可被机器追溯的最小单位。**

| # | 规则 | 可检验形式 | 对应 |
|---|---|---|---|
| **IMP-1** | **预检阶段不得写任何库**——包括不更新 `updated_at`、不写审计、不建临时成员 | 两次预检后全库逐表行数与内容摘要不变 | AT-10 / AC-05-8 |
| **IMP-2** | 同一输入重复预检**结果完全一致**（verdict 与汇总统计逐字节相同） | 两次预检输出 diff 为空 | AC-05-8 |
| **IMP-3** | **任一行 `BLOCKED` 则不得进入提交阶段**——提交接口必须整体拒绝，**不得只提交非 BLOCKED 行** | 含 BLOCKED 的预检报告提交 → 拒绝且库无变化 | AT-09 |
| **IMP-4** | 提交阶段的输入必须与预检报告**同一份**（`hash`/`version` 不匹配即拒绝），**不得由调用方重新指定行集合** | 改行集合或换报告 → 拒绝 | CC-3 |
| **IMP-5** | 预检必须检出**无组织归属**（无 `school_id`）并判 `BLOCKED`——这是 INC-09 的直接拦截点 | 无 `school_id` 的名册行 → `BLOCKED` | INC-09 / AT-10 |
| **IMP-6** | `CONFLICT_SKIP` **不得改动被跳过账号的任何字段**，且**必须报出该账号所属组织**——调用方须能区分「本行跳过」与「被别的组织占用」 | 同名跨组织 → `CONFLICT_SKIP` + 带出占用方组织标识 | AT-10 |

> **IMP-1 与 IMP-2 是一对**：只保证「不写库」而不保证「可重复」，
> 调用方就无法安全地「预检 → 等人工 → 提交」——
> 中间数据变了却没人知道，重试就会按过期的判断写入。
>
> **IMP-6 是本节最容易被漏掉的一条**：当前实现遇到同名账号一律
> `CONFLICT_SKIP` 且**不检查组织是否相同**，于是「A 校老师导入学生」时
> B 校的同名学号被静默跳过，调用方看到 `success_count=0`
> **却不知道是被哪个学校占用了**。**静默跳过比报错更难排查。**

### 1.1 逐行 verdict 分类（AT-08/09/10 共同口径）

| verdict | 含义 | 处置 |
|---|---|---|
| `CREATE` | 可安全创建 | 进入提交阶段 |
| `CONFLICT_SKIP` | 已有账号且**已绑定同一教师** | 跳过，**不改其任何字段** |
| `BLOCKED` | 冲突或前置不满足 | 见下表，**绝不猜测** |

`BLOCKED` 的子类（对应 `teacher.py` 现有的 `reason` 字段）：

| 原因 | 现状行为 | 目标行为 |
|---|---|---|
| 学号或姓名为空 | 已实现 | 保持 |
| 学号已存在且绑定其他教师 | 已实现 | 保持，**不得静默改绑** |
| 学号已存在但**组织不同** | **未区分** | 新增：同校不同组织也需人工裁决 |
| **无组织归属**（无 `school_id`） | **未检查** | 新增：**INC-09 的直接拦截点** |
| 名额不足 | **未检查** | 新增（AT-09 席位边界） |
| 邮箱未验证 | **未检查** | 新增（AT-10） |

> **「不得静默合并身份」是 AT-10 的硬要求。**
> 当前实现遇到同名账号一律 `CONFLICT_SKIP`，
> 但它**不检查该账号的组织是否与本次导入相同**——
> 于是「A 校老师导入学生」时，B 校的同名学号会被静默跳过，
> 调用方看到 `success_count=0` 却**不知道是被哪个学校占用了**。

## 2. 密码处理（现有实现的安全缺陷）

### 2.1 不得由请求体传入明文密码

**现状**：`hash_password(req.default_password)`——密码经 HTTP 明文传输。

| # | 规则 | 说明 |
|---|---|---|
| PW-1 | 导入**不接受**明文密码入参 | 密码生成在服务端完成 |
| PW-2 | 采用**一次性初始凭据**：生成随机临时密码，**只存 hash** | 响应体不回传明文 |
| PW-3 | 首次登录**强制改密**（`must_change_password`） | 现状 `teacher.py:208` 已有，保留 |
| PW-4 | 临时凭据**一次性消费** | 改密后立即失效，不可复用 |
| PW-5 | 响应体**只回凭据标识**，不回密码 | 交付渠道（线下/邮件）由 W-10 定义 |

> **PW-2 的存储形态必须回到 W-02 的边界**：总设计 9.1 行要求脱敏，
> `tenant_invitations` 已用 `token_hash` 而非明文（`W-02 §3.3`）。
> 成员初始凭据**沿用同一形态**，不新造第三种。

### 2.2 邮件缺配置时**不得**假成功（AT-11）

| # | 规则 |
|---|---|
| ML-1 | 邮件未配置 ⇒ **明确失败**，不得「记录成功」 |
| ML-2 | 发送失败 ⇒ 邀请**保持 `pending`** 且接口**明确失败**；**不得**把「已创建」表达成「已送达」 | **本设计不设 `sent` 状态**（INC-60）：`tenant_invitations` 的取值只有 `pending`/`accepted`/`revoked`/`expired`，投递结果**不写入邀请状态机**。原条文写的 `sent` 在 DDL 里不存在，实施者照写会撞 CHECK——**规格引用了 DDL 不允许的取值，等于把一条规则变成一个会误导人的错误提示** |
| ML-3 | 后端业务门禁**独立于邮件结果**——即使邮件成功，未完成首次引导前该成员**仍不得访问客户数据** |
| ML-4 | 「假验证成功」是本包最严重的失败模式：调用方以为流程走通，实际成员无权限 |

> **ML-3 是重点**：邮件成功只说明「消息发出去了」，
> **不说明「这个人已经被授权」**。两者被混为一谈就会出现
> 「邮件显示成功、但成员一进去什么都看不到」——即 AT-11 的
> 「后端业务门禁仍阻断」与「无假验证成功」两条判据。

## 3. 并发准入（AT-09）

席位与名额的判定**必须在数据库内原子完成**，不能在应用层先查后写。

```
错误做法（当前所有名额类逻辑的风险模式）：
  count = SELECT count(*) WHERE quota      # T1
  if count < limit:                        # T2  ← T1 与 T2 之间有窗口
      INSERT ...                           # T3

正确做法：
  INSERT ... SELECT ... WHERE (SELECT count(*) ...) < limit   # 单语句原子
  -- 或唯一约束 + ON CONFLICT
  -- 或 SELECT ... FOR UPDATE 锁住配额行后再判
```

| # | 规则 | 说明 |
|---|---|---|
| CC-1 | 名额判定与写入**同一事务**，中间不得有应用层分支 | 消除 check-then-act |
| CC-2 | 并发接受邀请：`tenant_invitations` 的 `UNIQUE (tenant_id, user_id)` 兜底 | 重复接受必须**一次生效或明确拒绝**（AT-08） |
| CC-3 | 并发导入同一名册：按 `username` 的数据库唯一约束兜底 | 不得产生两个同名成员 |
| CC-4 | 失败时**回滚整个事务**，不留半成品 | AT-09「不部分形成越界授权」 |

> **CC-4 与当前实现的根本差异**：现状是「逐条 continue，成功的已落库」。
> 改成两阶段后，**预检阶段发现任何 `BLOCKED` 就不允许进入提交阶段**——
> 这不是「回滚」，是「根本不开始」。

## 4. 邀请生命周期（AT-08）

```
   创建            接受             失效
  ──────► pending ──────► accepted   revoked（管理员撤销）
              │                     expired（expires_at 到期）
              └──► expired
```

| # | 规则 | 判据来源 |
|---|---|---|
| INV-1 | 重复接受**一次生效或明确拒绝**，不得产生重复成员 | AT-08 |
| INV-2 | 过期邀请必须拒绝，且**不得**因时钟偏差被接受 | AT-08 |
| INV-3 | 撤销后立即失效，即使 token 已被拿到 | AT-08 |
| INV-4 | **身份不符必须拒绝**：token 绑定的身份与实际接受者不一致 | AT-08「越权角色」 |
| INV-5 | 接受路径走 W-02 §3.6.3 ③ 的**特权路径**（按 `token_hash` 查），**不得**为它开 RLS 口子 | W-03 §2.3 E1 |

> **INV-4 的必要性**：若 token 只证明「持有者知道这个字符串」，
> 则拿到 token 的人可以以**任何身份**加入租户并获得对应角色——
> 这是 AT-08 明确点名的「越权角色」。

### 4.2 教师移交（AT-12 的业务流侧）

现状：`users.teacher_id` 是**全局单值**（`db.py:184`），
一个学生只能有一个指导教师，且该关系**不受租户约束**。

| # | 规则 | 层 |
|---|---|---|
| TM-1 | 移交后**双向**写入 `teacher_student_bindings`（W-02 §3.2） | 应用层 |
| TM-2 | 双方 membership **必须同租户**，由复合外键保证 | 数据库层（W-04 §4 负例 2） |
| TM-3 | 旧 `users.teacher_id` 标 `legacy` 并**保留**，不删不改 | 迁移期 |
| TM-4 | 移交**不改变**学生的其他授权（组织、角色） | 应用层 |
| TM-5 | 移交记录进 `audit_events`，含原教师与新教师 | 审计层（W-10） |
| TM-6 | 移交时**旧绑定置 `ended`（不删）、新绑定置 `active`**；迁移期从 `users.teacher_id` 导入的绑定置 `legacy` | 数据库层（值集合见 W-02 `binding_state_chk`） |

> **TM-3 的理由**：直接改写 `users.teacher_id` 会让「移交前是谁带的」
> 这一事实在数据里彻底消失。W-02 §4 #21 已定 `audit_events` 标 `legacy`
> 而非伪造——**历史必须可追溯，不能为了让当前状态干净而销毁它**。
>
> **TM-1 与 TM-2 缺一不可**：只有 TM-1（应用层改绑）时，
> 越权调用可直接写库绕过；只有 TM-2（数据库约束）时，
> 应用层无合法写入路径可走。**两层职责与 W-04 §2 的 L1/L3 同构。**

## 6. 客户生命周期（2026-10-01 补，INC-59）

> **这一节是补缺，不是新增设计。** 总设计 §23.1 的 W-05 行第一项就是「**客户启用**」，
> §18.2 列了 `POST /platform/tenants` 与 `POST /platform/tenants/{t}/activate` 两条平台端点，
> §12.1 定义了 `draft → active` 的状态与「首位所有者设置与启用检查」——
> 但**本规格原先 §1～§5 只覆盖导入、密码、并发、邀请、组织切换，
> 客户生命周期一条规则都没有**。实测 `activate` / `启用客户` 在 13 份规格里 **0 次出现**，
> 且 W-02 原先的 `tenants_status_chk` **根本不允许 `draft`**
> （集合是 `provisioning/active/suspended/closed`），两条平台端点**在存储层就无法实现**。

| # | 规则 | 说明 |
|---|---|---|
| CL-1 | 租户创建**只能**由平台能力发起（§18.1「不会因现有 `admin` 字符串自动放行」）；平台身份的 `tenant_id` 必须为 None | W-03 CI-2 |
| CL-2 | 创建后租户状态**必须是 `draft`**，**不得**直接建成 `active` | §12.1 `draft` 行的禁止行为：正式教学发布、平台 AI、收费 |
| CL-3 | 创建请求**必须**携带幂等键；同一键重复创建返回同一租户，**不产生第二个客户** | §18.2「平台能力、幂等、客户批准记录」 |
| CL-4 | 创建**必须**落批准记录：谁批准、批准了哪些条款（负责人、组织范围、数据外发、试点期限、退出联系人），缺项即拒 | 总设计 §6 流程「明确负责人、组织范围、数据外发、试点期限和退出联系人」 |
| CL-5 | **启用不是「把 status 改成 active」**，而是一次带 version 的检查清单执行；同 version 竞争返回 409 | §18.2「version 与检查清单，不是直接改字符串状态」 |
| CL-6 | 启用检查清单至少覆盖：①首位所有者已设置且账号已验证 ②组织已创建并绑定 ③已选择**已发布**模板 ④成员准入已配置 ⑤权益与非货币配额已确认 ⑥AI 政策已配置 ⑦readiness 检查通过 | §6 流程七步 + §12.1 `draft` 行 |
| CL-7 | 清单任一项未过 ⇒ **不启用**，并返回**逐项未通过原因**；不得只说「检查失败」 | 「响亮失败」优于「静默成功」 |
| CL-8 | 模板**必须**是 `published`（W-06 PV-2），**不得**引用 `draft`/`retired` 的 `plan_code` 版本 | 与 PV-2 同族；引用未发布版本会让权益口径无法追溯 |
| CL-9 | `draft` 租户下的访问由 **W-03 E7** 把关：首位所有者可进入并完成启用，其余请求 403 | E7 于 2026-10-01 因本节一并新增 |
| CL-10 | 商业维度**不写进** `tenants.status`；`restricted` 由 W-06 的 subscription/权益派生 | §12.1 首句「不用一个 status 混合所有原因」；W-02 `tenants_status_chk` |
| CL-11 | 已 `active` 的租户**不得**退回 `draft`；回退属数据事故，走 W-10 的恢复/审计通道 | 把生产租户打回 draft 会让全部成员瞬间失去服务且难以定位 |

> **CL-5 是本节最容易做错的一条**。最省事的实现是
> `UPDATE tenants SET status='active' WHERE id=?`——一句话、两行代码、测试全绿。
> 但 §18.2 明写「**version 与检查清单，不是直接改字符串状态**」：
> 直接改状态会把「清单第 3 项没过」这类问题变成**启用成功后才暴露**，
> 而此时组织、模板、权益、AI 政策可能各缺一半。
> **省下的七行代码，换来的是无法追溯的部分初始化租户。**

> **CL-11 与 §12.1 的 `closing`/`closed` 不冲突**：`closing`→`closed` 是退出流程（W-10），
> `active`→`draft` 是**从未发生过**的状态倒流，两者处置路径完全不同。

> §24.2 中「纯 W-05」的 AT-08/09/10/11）。两条都是 `W-03/05` 共属：
>
> - **AT-07**（旧 admin 迁移、平台与客户管理分离）：导入会碰到**已存在的旧账号**，
>   若不显式处理映射，就会出现「导入顺带把旧账号提权」——
>   `permission-matrix.md` P-ACT-3 已指出 `admin` 当前隐式等于全平台访问。
> - **AT-12**（教师移交）：W-03 §5 明确「教师移交的**业务流**属 W-05」，
>   本包只负责 W-03/W-04 之外的落地部分。**三方拼合才构成完整 AT-12**：
>   W-03 管授权层、W-04 管数据库层约束、本包管业务流。
>
> **这正是 AT-11 的价值**：AT-10 只能查出「引用错的」，
> 漏引的 AT 在收口时不会被发现——**它默认不做，而且没人知道**。

> **AC-05-2 与 AC-05-3 必须一起验**：只验「预检报告」不验「不部分写入」，
> 会得到一个漂亮的报告但事务仍然半提交；反之只验原子性，
> 则调用方拿不到可行动的冲突清单。**两者是同一个设计的两面。**

## 8. 门禁

| 检查 | 工具 | 守住什么 |
|---|---|---|
| 建号路径 `organization_context` 契约 | `account_path_check.py` | **INC-09**：导入路径必须写组织归属 |
| 上下文与失败出口 | `context_resolution_check.py` | W-03 §2.3 E1～E6 |
| 全局 `role` 引用计数 | `context_resolution_check.py` CR-4 | `teacher_id` 全局单值的改造进度 |
| 逐条 AT 归属与漏引 | `at_traceability_check.py` AT-10/AT-11 | 本表覆盖 §24.2 归 W-05 的全部 AT |

**本包暂不新增静态门禁**：AT-08～AT-11 全部是**运行时并发与副作用**判据，
静态检查（正则/AST）证明不了「预检真的没写库」「并发真的不超额」。
在无并发测试设施与真实 PG 之前，新增的门禁只能验证形式，
**那会给出一个看起来像验证的绿灯**。该缺口如实登记在总设计 §26.3。

> **可以静态查且值得查的一项**：`bulk_import_students` 是否仍接受明文密码入参。
> 这条可在实施后由 `account_path_check` 扩展覆盖（PW-1），
> 但**现在不写**——当前实现必然报红，写了只是把已知缺陷变成常红项，
> 不产生新信息。
