（AT-35～AT-39），全部围绕一件事：**钱和量的每一次变化，都必须留下守恒的、不可篡改的、可追溯的事实。**

## 1. 商业模式不写死（CM）

§15.1 明确支持多个方向，**首版收费模式必须裁决**。本包因此只定义**模式无关的骨架**。

| # | 规则 | 说明 |
|---|---|---|
| CM-1 | 账务对象必须能同时表达「固定许可」「非货币额度」「余额按量」三种模式，**且三者不共用一个钱包** | §15.1 三条并列 |
| CM-2 | **非货币额度用 quantity ledger，单位明确**；次数/token **不得混入货币 journal** | §15.2 第 4 条 |
| CM-3 | 供应商成本用**带精度和币种的独立成本事实**表达，**不得直接抵扣客户余额**，**不得自动跨币种转换** | §15.2 第 6 条 |
| CM-4 | BYOK 是否收服务费与供应商账单**分开裁决**；不把用户供应商成本记成平台收入 | §15.1 第 4 条 |
| CM-5 | 若最终采用固定机构许可而非余额钱包，**不必向客户暴露「充值余额」**；但支付、应收、调整仍须有不可变账务事实 | §9.4 末段原文 |
| CM-6 | 任何模式都**不得**用「充值 100 元 = 1000 次」的形式记账 | `quota-and-billing-review.md` §6：那会在真实收费时产生对不上的历史数据 |

> **CM-2 与 CM-6 是同一类错误的两个方向**：
> CM-2 防止「次数混进钱」，CM-6 防止「钱混成次数」。
> 二者共同的后果是**口径不可逆**——一旦历史数据用了错误单位，
> C1 真实收费时必须回头清洗，而清洗历史财务事实需要审批和凭证，
> 远贵于一开始就分开。

## 2. 账务不变量（JV）

§15.2 的七条不变量是本包的**验收判据本体**，不是建议。

| # | 不变量 | 可检验形式 |
|---|---|---|
| JV-1 | 一笔 `journal_entry` 关联**唯一**业务事实和**唯一**结算动作 | `business_ref` + `entry_type` 唯一约束 |
| JV-2 | 同币种各行**带符号整数金额合计为 0** | `SUM(signed_amount_minor) == 0` 逐凭证断言 |
| JV-3 | 客户资金账户、预留、业务关联**属于明确租户**；平台汇总收入**不通过客户接口**读取其他客户账户 | 账户 `tenant_id` 非空 + 接口越权用例 |
| JV-4 | `available = posted_balance − active_holds`；余额、预留与新凭证**在同一事务更新**；**无授权透支政策时可用余额不得为负** | 并发用例 + 负余额断言 |
| JV-5 | 金额只用**最小货币单位整数**；单 token 价格需精确有理数或十进制定价，**冻结进位/累计/舍入规则** | 禁止浮点；舍入策略落 `price_versions.rounding_policy` |
| JV-6 | 已过账凭证**不可删改**；退款、冲正、人工调整生成**新凭证**，记录审批与原因，**关联原凭证** | `original_entry_id` 非空 |
| JV-7 | 审计、账务、使用请求**都必须能强关联**，关键路径**不允许空 `request_id`** | 逐表非空断言 |

> **JV-7 与 W-10 的 AU-2 直接冲突，必须在这里显式化解。**
> W-10 定的 AU-2 是「审计写失败**不得**阻断业务——宁可丢审计也不许丢业务」，
> 理由是审计与业务同通道会构成 DoS。
> 但 §15.2 第 7 条要求「**不能复用当前『审计失败不阻止配置保存』的 best-effort
> 语义作为收费保证**」。
> **两者都对，但适用面不同**：
> - 教学业务路径（读论文、提交、导出）→ AU-2 成立，审计异步 + 告警；
> - **资金路径**（过账、结算、调整、退款）→ **必须**强关联，
>   审计/事件写失败即**整个事务回滚**。
>
> 理由：业务丢一次是体验问题，**账务丢一次是财务事实丢失**。
> W-10 规格需回填这条分工（见 §7 交接）。

## 3. 预留与结算（RS）

§15.3 的两个事务骨架**照搬**，本节补的是**规格必须回答、实现者最容易做错**的部分。

### 3.1 预留事务

```text
锁定已唯一登记的 request；固定顺序锁定租户预算/配额、计费账户
→ 检查冻结规则、余额和最大可预留量
→ 原子准入 request + 创建唯一 reservation
→ 增加 held/reserved
→ 写关键审计/事件
→ 提交
```

| # | 规则 | 说明 |
|---|---|---|
| RSV-1 | **固定锁顺序**：request → 租户配额/预算 → 计费账户。**任意两笔事务不得以相反顺序取锁** | §15.3 建议「固定锁顺序并处理冲突」；顺序不定会死锁，重试又会把短事务拖长 |
| RSV-2 | 重试的是**数据库短事务**，**绝不重发供应商调用** | §15.3 原文 |
| RSV-3 | 预留唯一键 = `request + reservation_kind`；同请求同类型**只创建一次有效预留** | §15.4 |
| RSV-4 | 预留**不得因过期自动释放**，除非能确认**未派发** | §15.3 第 3 条、`reservations` 约束；与 W-08 UQ-5、W-06 QT-3 同一约束 |
| RSV-5 | `dispatching`/`unknown` 的预留按**对账政策**处理，**不因定时器到点就退款** | §15.3 第 3 条 |

> **RSV-4/RSV-5 与 W-06 BQ-02 的表面冲突必须裁定**：
> BQ-02 待裁决项写「`reserved` 超时回收时长：导出 2 小时、渲染 30 分钟、AI 同步调用不预留」。
> 其中「**AI 同步调用不预留**」与 §15.3「`dispatching`/`unknown` 的预留按对账政策处理」
> **不是一回事**——前者是不预留，后者是预留了不许自动退。
> 本规格采纳 §15.3：**AI 调用一旦预留，就只能由对账释放**。
> 若采纳 BQ-02 的「不预留」，则 `available` 不含未决消耗，
> 并发下会**超发**——与 JV-4 冲突。**建议 BQ-02 裁决时删除「AI 同步调用不预留」这一项。**

### 3.2 确认结算事务

| # | 规则 | 说明 |
|---|---|---|
| RSV-6 | 结算前必须验证**版本**与**未结算状态**；已结算请求**不得二次结算** | §15.3 |
| RSV-7 | 读取**已冻结**价格与可信 usage；`price_version` 取**发生时**的版本 | §9.4 `price_versions`「账务引用发生时版本」 |
| RSV-8 | 结算失败**保持待结算事实，可重放**，**不重新调用 AI** | §15.3 第 1 条 |
| RSV-9 | 实际结果**超出预留**时进入明确异常策略：**阻断后续消费并对账**；是否补扣**须批准**；**不自动产生负余额** | §15.3 第 2 条 |
| RSV-10 | 无法核对未知调用时**创建人工处理案件并保持原始事实**；赔付/免收**以新的授权凭证表达**，**不伪造供应商「已失败」** | §15.3 第 4 条 |

> **RSV-9 最容易被实现成「自动扣成负数」**——
> 代码上最省事，账务上最糟。正确形态是：
> 超预留 ⇒ 记 `overage` 异常状态 + **冻结该租户后续消费** + 生成对账案件，
> 人工裁决后再补一张凭证。**「自动透支」不是便利，是把财务决策交给了浮点数。**

### 3.3 幂等规则（ID）

§15.4 的七行动作唯一键，**全部照搬并绑定到对象**：

| 动作 | 业务唯一键 | 本包对象 | 重复行为 |
|---|---|---|---|
| AI 业务请求 | tenant + membership + operation + client_key | `ai_requests` | 同内容返回已有请求（W-08 IQ-2） |
| 预留 | request + reservation_kind | `reservations` | 只创建一次有效预留（RSV-3） |
| 用量事件 | request + event_seq / provider_event | `usage_events` | 重复插入忽略同内容；**冲突进异常** |
| 结算/释放 | request + settlement_type | `journal_entries` | 只影响一次余额/配额 |
| 手工调整 | approved_adjustment_id | `journal_entries` | 重复提交返回原凭证 |
| 支付确认 | provider + merchant + external_transaction | `payment_event_inbox` | 只过账一次（W-12） |
| 退款/冲正 | approved_refund_id + original_entry | `journal_entries` | 重复**不能突破可退总额**（§16.4） |

| # | 规则 | 说明 |
|---|---|---|
| IDB-1 | 客户端 `Idempotency-Key` 与服务端 `request_id` **分开**；前者不可枚举后者 | §15.4 末段 |
| IDB-2 | 内容指纹用**受控 HMAC**，**冻结指纹密钥版本**，重试时**按该版本比较** | 轮换不得导致相同内容误报冲突 |
| IDB-3 | 幂等记录保留期限按**外部重放窗口与账务要求**确认；**财务事实不得因缓存到期重新执行** | §15.4 末段 |

> **IDB-2 的失败形态很具体**：指纹密钥轮换后，
> 同一份内容用新密钥算出的指纹不同 ⇒ 客户端重试被判成「同键不同内容」⇒ **409**。
> 而用户实际上提交的是**一模一样**的内容。
> 这类故障只在轮换当天出现、且**无法复现**（历史请求已过期），
> 因此**必须靠冻结 `fingerprint_key_version` 预防，不能靠事后排查**。

## 4. 定价与精度（PR）

**本节是 D-03 的落地位置，D-03 未裁决前不得填值。**

| # | 规则 | 说明 |
|---|---|---|
| PR-1 | `price_versions` **发布后不可改**；账务引用**发生时**版本 | §9.4 |
| PR-2 | 金额一律**最小货币单位整数**；**禁止浮点**参与金额运算 | JV-5 |
| PR-3 | 单 token 价格用**精确有理数或十进制**；**冻结进位/累计/舍入规则** | §15.2 第 5 条 |
| PR-4 | 舍入策略**在累加前确定**并落库；**不得逐 token 取整后再相加** | 「不让浮点误差或逐 token 取整改变账单」 |
| PR-5 | 币种**不得混用**；跨币种**不自动转换** | CM-3、AT-37 |
| PR-6 | `billing_statements` **不从当前计划反算历史**；`entry_refs` 指向实际凭证 | §9.4 |
| PR-7 | `usage_quality` **非 `provider_reported`** 的请求**不得**按 token 自动计价 | W-08 US-3/US-8、AT-23 |

> **PR-7 是 C1 最容易被绕过的一条**，因为它「看起来只是个过滤条件」：
> 若结算时不看 `usage_quality`，C 级（估算，误差 ±30%）和 D 级（网关剥掉 usage）
> 的消耗会**按估算 token 计价**。
> 后果是**账单金额建立在 ±30% 的猜测上**，
> 而客户侧的争议「你凭什么收我这么多」将无法用数据回答。
> 正确形态：这类请求**只进配额预警，不进金额**（`quota-and-billing-review.md` §8.1 A/B/C/D 分级）。

## 5. 对账（RC）

§15.5：「差异生成可见案件和告警，**不在修复脚本里直接覆盖余额**。」

| # | 规则 | 说明 |
|---|---|---|
| RC-1 | 至少核对六组：请求↔事件、事件↔结算、预留↔有效请求、钱包余额↔过账流水、订单↔渠道交易、退款总额↔原支付 | §15.5 |
| RC-2 | 差异写入 `reconciliation_cases`，**记录证据来源与可信程度** | §15.5 末段 |
| RC-3 | **禁止**任何脚本直接 `UPDATE` 余额；修复必须**生成凭证**（JV-6） | 「不在修复脚本里直接覆盖余额」 |
| RC-4 | 供应商**不提供可查询请求号/可信计量**的路径，**不得承诺可自动按 token 收费**；应改用已裁决的其他模式或**排除该模型** | §15.5 末段 |
| RC-5 | R-7 月度对账（MR-FIX-7）**依赖 MR-FIX-1 + MR-FIX-4** | 当前两项均未做 |

> **RC-3 值得单独强调**：直接改余额的「修复脚本」在紧急时极具诱惑——
> 它能立刻让报表对上。代价是**这个数字从此没有凭证、没有审批、无法解释**，
> 而它会一直显示在对账单上。**对不上的数字可以保留为案件，不能被抹平。**

## 6. 验收

| AC | 关联 AT | 判据 | 证据 |
|---|---|---|---|
| AC-11-1 | **AT-35** | 同一请求并发预留/结算/释放：**唯一业务效果**，余额/配额**不漂移**，**journal 守恒**（逐凭证 `SUM == 0`） | 本包 §3.1/§3.2；并发压测 + 守恒断言 |
| AC-11-2 | **AT-36** | `unknown`、延迟 usage、预留到期与恢复：**无未知退款、无重复扣费**；对账后**按冻结规则**处理 | 本包 §3.1 RSV-4/RSV-5、§5 |
| AC-11-3 | **AT-37** | 价格变更、币种/单位混用、舍入与超预留：**历史版本稳定**，精度规则一致，异常**不产生擅自透支** | 本包 §4；超预留 → 冻结消费 + 案件，非负余额 |
| AC-11-4 | **AT-38** | BYOK 与平台池、固定许可与额度：**收入 / 供应商成本 / 非货币权益三者分开**，**不假装统一钱包** | 本包 §1 CM-2/CM-3/CM-4 |
| AC-11-5 | **AT-39** | 账务修正、人工调整、投影重建：**新凭证关联原事实**，审批可查，**投影重建不更改资金** | 本包 §2 JV-6、§5 RC-3 |

**本包无法独立验证的部分**（不得混入「通过」）：

- **AT-35～AT-39 全部依赖 MR-FIX-1～4 与三维额度**，五项**当前均未做**。
  在此之前，AC-11-1～5 **连测试数据都造不出来**——
  没有 token、没有 `reserved`、没有用量查询入口。
- 并发语义必须在**真实 PostgreSQL** 上验证（§15.3 明确建议行锁）；
  本机无 PG 实例，**SQLite 结果不得代替 PG 结论**。
- D-02/D-03/D-07 未裁决 ⇒ `price_versions` 无值、货币模式无归属。
  **在裁决前，本包不得进入实施**（不是「先做了再说」——

## 7. 门禁

| 判据 | 静态可查？ | 处置 |
|---|---|---|
| 账务表是否登记 RLS 策略、是否漏 `tenant_id` | ✅ | `rls_policy_check` RL-1 双向核对自动覆盖新增表 |
| 金额列是否为整数、是否混入浮点 | ⚠️ **DDL 可查** | 类型可静态核对；**舍入正确性不可静态查** |
| 业务唯一键（JV-1、RSV-3、IDB-3）约束是否存在 | ✅ **仅约束存在性** | 约束缺失可查；**约束正确性不可静态查** |
| 凭证守恒 JV-2 | ❌ | 运行时断言 |
| 锁顺序 RSV-1 | ❌ | 并发测试 + 死锁计数 |
| `usage_quality` 过滤 PR-7 | ❌ | 运行时断言 |

> **本包不新增静态门禁**，与 W-04/05/06/07/08/09/10 同一判断。
> 特别说明「业务唯一键」这一行——它**看起来**可以静态查（DDL 里有 `UNIQUE` 就行），
> 但**唯一约束只能保证「不重复插入」，保证不了「不重复产生资金效果」**：
> 真正的判据是 RSV-6 的版本校验与结算状态判定，属运行时。
> 写一个只查 `UNIQUE` 的门禁会给出**虚假的安全感**，比不写更糟。
