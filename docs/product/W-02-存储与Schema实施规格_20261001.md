# W-02 存储与 Schema 实施规格

> 状态：**design_ready**（本文件是规格，不是实施结果；**未执行任何 DDL，未创建任何表**）。
> 日期：2026-10-01（Asia/Shanghai）。阶段：G0。依赖：W-01 的资源登记表与 ADR-02 决议。
> 上游：`saas-platform-design-20261001.md` 第 7、8、9、10、19、22 节。

## 2. 已验证事实（阻塞级）

以下全部于 2026-10-01 在 HEAD `e166f97` 实测。**未标注即已验证。**

### F-01（阻塞 ADR-02）DDL 在**每个请求**执行，不是启动时

- `Store.__init__` 调用 `_init_schema()`：`backend/app/db.py:91`
- `_init_schema()` 执行 28 张表的 `executescript()` + 多处 `PRAGMA table_info` 守卫 + 10 条账本写入：`backend/app/db.py:108-547`
- `Store()` 有 **17 处**实例化点（`backend/app/worker.py:35`、`backend/app/cli/migrate.py:19`、9 处 `backend/app/api/*.py`、`backend/app/main.py:77,178`）
- 统一 DI 为 `get_store()`（`backend/app/auth.py:617-624`，其 docstring 明确"全项目统一用 `Depends(get_store)`"）；`Depends(get_store)` 在后端出现 **202 次**，API 模块内 `Depends(` 共 410 次

**后果（推断，需在 E1 阶段实测确认）**：在 PostgreSQL 上，每次请求执行 25 条 `CREATE TABLE IF NOT EXISTS` + 目录表访问，会持续争用 catalog 锁并使连接池无法复用。总设计第 271 行的表述是"不要继续把 DDL 隐式放在**启动过程**"，**实际现状比这严重一个量级**。

> **这是 W-02 的第一优先项。** 在 DDL 从请求路径移除之前，讨论 RLS、连接池、事务局部租户设置都没有意义——连接根本不会被复用。

### F-02 迁移账本是"打标"，不是迁移状态

- `SCHEMA_MIGRATIONS` 是硬编码字符串元组：`backend/app/db.py:29-43`
- 账本写入无条件 `INSERT OR IGNORE`：`backend/app/db.py:543-547`
- CLI `migrate` 仅检查 10 个版本号是否齐全，不执行、不校验、不回滚：`backend/app/cli/migrate.py:19-27`

**后果**：账本显示"已应用"与 DDL 实际生效之间无对应关系校验。SQLite 幂等建表掩盖了这一点；PostgreSQL 上同样的"每次请求建表"会产生真实的迁移事故。

### F-03 唯一键在共享库下会跨租户冲突

| 表 | 现有约束 | 取证 | 共享多租户下的冲突 |
|---|---|---|---|
| `document_packages` | `UNIQUE (template_version_id, spec_version_id, renderer_version, rule_engine_version)` | `backend/app/db.py:314` | 模板按设计是**租户资产或公共资产**（总设计 10 节）。两个租户用同一版本四元组会**撞唯一键**，第二个租户无法创建 |
| `workflow_idempotency` | `PK (user_id, action, idem_key)` | `backend/app/db.py:383-391` | 总设计 9.4 要求幂等唯一范围为**租户+成员+操作+键**。同一账号在两租户（AT-01）会互相顶掉幂等记录 |
| `ai_quota` | `PK (user_id, period)` | `backend/app/db.py:294-300` | 每用户每日计数，**无租户口径**。总设计 9.3 要求 `quota_periods` 按租户+主体+指标 |
| `mini_program_bindings` | `user_id UNIQUE` | `backend/app/db.py:209` | 全局身份绑定。总设计 10 节允许身份全局，但**业务消息必须引用租户成员** |
| `email_verification_codes` | `PK (email)` | `backend/app/db.py:188` | 全局邮箱验证，跨租户共用属预期，但需在设计中显式承认 |

### F-04 组织树无法支撑租户映射查询

`organization_units(id, data, updated_at)`，整棵树的 `parent_id`/`name`/`type` 全在 `data` 这个 JSON 列里，无外键、无索引（建表语句见 `backend/app/db.py:338-342`，三列依次为 `id` / `data` / `updated_at`；`parent_id`/`name`/`type` 是 **JSON 内的键，不在 DDL 列中**。对应模型见 `backend/app/models/organization.py:16-24`）。

**后果**：总设计第 10 节要求"根组织经人工确认映射租户，子树继承并持久化"。当前 schema **没有任何可用于生成归属候选的索引或约束**，M1 预检只能全表扫描 + 应用层解析。`list_organization_units()` 每次全量反序列化（`backend/app/db.py:2022`）。

### F-05 10 张表以 JSON 文本承载业务状态

`templates` / `projects` / `requirement_sets` / `document_packages` / `document_projects` / `validation_runs` / `organization_units` / `check_runs` / `policy_audit_events` / `workflow_records` —— 全部 `(id, data TEXT, ...)`，主键为不透明字符串。

**后果**：总设计 25.1 列出的"JSON 遗漏租户字段"风险是**已实现状态**，不是潜在风险。且 `workflow_records` 用 `(kind, id)` 复合主键 + `kind` 区分业务类型（`backend/app/db.py:355-362`），一个 kind 内部混装多种业务对象，租户列无法统一表达。

### F-06 全局角色与指导关系是当前授权的根

`users.role`（全局单角色）+ `users.teacher_id`（全局指导教师）：`backend/app/db.py:179`、`backend/app/db.py:184`。

**后果**：这正是 ADR-03 要拆分的对象，也是总设计 25.1"旧全局 admin 被滥用"风险的实际来源。W-02 阶段**只加侧边列，不改这两列语义**（改动属 W-03/W-04）。

### F-07 `jobs` 缺任务契约 6 个字段中的 5 个

现有：`id, job_type, resource_type, resource_id, state, attempt_count, max_attempts, available_at, lease_until, lease_token, leased_by, last_error, created_at, updated_at, completed_at`（`backend/app/db.py:410-426`）。

总设计 19.1 要求：`tenant_id`、`resource_version`、`payload_schema_version`、`attempt_generation`、`lease_epoch`、`deadline`。

**现状缺失**：`tenant_id`、`resource_version`、`payload_schema_version`、`attempt_generation`、`lease_epoch`、`deadline` —— **6 个全缺**。已有 `lease_token` 但**无 epoch/栅栏**，对应总设计 25.1"任务租约短于处理"风险。**W-02 只加列，不改领取逻辑**（属 W-09）。

### F-08 三个运行表无租户列

`workflow_events`（`backend/app/db.py:392-409`）、`audit_events`（`backend/app/db.py:363-374`，有 `organization_id` 无 `tenant_id`）、`ai_usage`（`backend/app/db.py:253-265`，有 `organization_id`）。

总设计第 434 行已明确：`ai_usage` 的 `organization_id` **不能完整证明合同租户和实际 token**。W-02 阶段这三张表**只加 nullable 侧边列 + 不回填**（除 W-01 预检给出确定证据的行）。

### F-09 连接生命周期

`with self._connect() as conn:` 在全文件大量使用（如 `backend/app/db.py:102`、`backend/app/db.py:1859`）。CPython 的 `sqlite3.Connection` 上下文管理器**只提交/回滚，不关闭连接**。

**后果**：现有 SQLite 模式下靠 GC 回收，隐患被单文件数据库掩盖。PostgreSQL + 连接池下会导致**连接泄漏**。E1 必须把连接生命周期改为显式管理。

### F-10 SQLite 专有构造清单（PG 适配必须逐点处理）

| 构造 | 出现位置 | PostgreSQL 对应 |
|---|---|---|
| `PRAGMA table_info(x)` | `backend/app/db.py:442,413,416,436` | `information_schema.columns` |
| `PRAGMA foreign_keys = ON` / `busy_timeout` | `backend/app/db.py:96-97` | 连接参数 / `lock_timeout` |
| 索引表达式 `json_extract(data,'$.project_id')` | `backend/app/db.py:383-384` | 需生成列或 `jsonb` + GIN；**不能直接翻译** |
| DML 中 `json_extract` / `json_set` | `backend/app/db.py:386,358` | `jsonb_set` / `->>` |
| `INSERT OR IGNORE` | `backend/app/db.py:545` 等 | `INSERT ... ON CONFLICT DO NOTHING` |
| `INSERT OR REPLACE` | `backend/app/db.py:480,1287` 等 | `ON CONFLICT DO UPDATE`（**语义不同：REPLACE 会删行重建，破坏 FK 与外键引用**） |
| `INTEGER` 布尔 | `users.email_verified` 等 | `boolean` |
| TEXT ISO 时间戳 | `_now()` `backend/app/db.py:67-68` | `timestamptz` |
| 表名/列名重建式迁移 | `backend/app/db.py:528-542` | PG 事务内 DDL，但需注意锁与 `ALTER TYPE` 限制 |

> **`INSERT OR REPLACE` 语义差异是隐蔽风险**：SQLite 下会删除旧行再插入，级联引用随之断裂；PG 的 `ON CONFLICT DO UPDATE` 保留行。逐点改造时必须区分，不能批量替换。

## 3. 目标 Schema 设计

> 以下是**待评审的 DDL 草案**。遵循总设计 9.1 行：现有不透明 ID 保留（`{prefix}-{12 hex}`），不重编号。

### 3.1 通用约定

- 主键一律 `text`，**不重编号历史 ID**
- 客户业务表 `tenant_id text NOT NULL`
- 时间 `timestamptz`，统一 UTC 存储
- 金额 `bigint`（最小货币单位，**禁止浮点**，总设计 9.1 行）
- 可变聚合带 `version`，用比较并交换更新（总设计 9.1 行）
- **父子关系用 `(tenant_id, parent_id)` 复合外键**（总设计 8.2 行第 325 行）

### 3.2 租户与身份对象（总设计 9.2）

```sql
CREATE TABLE tenants (
    id               text PRIMARY KEY,
    kind             text NOT NULL DEFAULT 'institution',
    name             text NOT NULL,
    slug             text NOT NULL UNIQUE,
    status           text NOT NULL DEFAULT 'active',
    timezone         text NOT NULL DEFAULT 'UTC',
    policy_version   text NOT NULL DEFAULT 'v1',
    version          integer NOT NULL DEFAULT 1,
    created_at       timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT tenants_kind_chk   CHECK (kind IN ('institution','individual')),
    -- **2026-10-01 修正（INC-59）**：本约束原先是
    --   CHECK (status IN ('provisioning','active','suspended','closed'))
    -- 与总设计 §12.1 的六个状态**只有 `active`/`closed` 两项重合**，且：
    --   · `draft` 缺失 → §18.2 `POST /platform/tenants`「新建 draft 客户」会被本约束**直接拒绝**
    --   · `provisioning` 是**设计里不存在**的状态（凭空多出来的第四个）
    --   · `suspended` 与 §12.1 的 `suspended_security` **命名分歧**（W-03 E6 跟着错）
    --   · 最根本：§12.1 首句要求「安全状态、商业服务状态和成员状态**分别建模**，
    --     不用一个 status 混合所有原因」——把六种原因塞进一列正是它明令禁止的形态。
    -- 现在 `tenants.status` **只承载生命周期/安全维度**；
    -- 商业维度（`restricted` 等）由 W-06 的 subscription/权益派生，**不入本列**。
    CONSTRAINT tenants_status_chk CHECK (status IN
        ('draft','active','suspended_security','closing','closed'))
);

CREATE TABLE tenant_organizations (
    tenant_id  text NOT NULL REFERENCES tenants(id),
    id         text NOT NULL,
    parent_id  text,                       -- NULL = 根节点
    type       text NOT NULL,
    name       text NOT NULL,
    code       text NOT NULL DEFAULT '',
    status     text NOT NULL DEFAULT 'active',
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    version    integer NOT NULL DEFAULT 1,
    PRIMARY KEY (tenant_id, id),
    -- 作为子表 FK 目标必须显式声明；PK 已覆盖，但显式写出以防后续改 PK
    UNIQUE (tenant_id, id),
    -- 复合父子外键：阻止 A 租户把节点挂到 B 租户父节点下
    FOREIGN KEY (tenant_id, parent_id)
        REFERENCES tenant_organizations (tenant_id, id)
        ON DELETE RESTRICT,
    CONSTRAINT tenant_org_type_chk
        CHECK (type IN ('school','college','major','course','batch')),
    CONSTRAINT tenant_org_no_self_parent CHECK (parent_id IS DISTINCT FROM id),
    -- **2026-10-01 补（INC-60）**：本列原先**没有任何取值约束**。
    -- 学校合并、更名、停办是真实运营动作，归档后行**不能删**（子表外键仍指向它），
    -- 因此需要第二个取值。`archived` 的语义是「不再参与新授权」，
    -- 既有数据与导出仍可读——与租户 `closed` 的处置方向一致。
    CONSTRAINT tenant_org_status_chk CHECK (status IN ('active','archived'))
);
CREATE INDEX idx_tenant_org_parent ON tenant_organizations (tenant_id, parent_id);
```

> **`parent_id` 必须可为 NULL。** 若用 `DEFAULT ''` 空串，复合外键会要求存在一个 `id = ''` 的父行而永远失败。PostgreSQL 的 `MATCH SIMPLE` 语义下，`parent_id IS NULL` 时该外键不参与检查——这正好实现"根节点豁免"，且不需要额外触发器。

```sql
CREATE TABLE tenant_memberships (
    id           text PRIMARY KEY,
    tenant_id    text NOT NULL REFERENCES tenants(id),
    user_id      text NOT NULL,
    status       text NOT NULL DEFAULT 'active',
    auth_version integer NOT NULL DEFAULT 1,     -- 撤权递增，总设计 8.1 行第 312 行
    joined_at    timestamptz NOT NULL DEFAULT now(),
    left_at      timestamptz,
    version      integer NOT NULL DEFAULT 1,
    UNIQUE (tenant_id, user_id),
    -- 必须存在：membership_roles / membership_org_grants / membership_certifications /
    -- teacher_student_bindings / member_external_ids 共 6 条复合外键引用 (tenant_id, id)。
    -- PostgreSQL 要求被引用列是主键或唯一约束（官方文档 5.5.5：
    -- "A foreign key must reference columns that either are a primary key or form a
    -- unique constraint"），PK(id) 不覆盖 (tenant_id, id)，缺此行则建表直接失败。
    UNIQUE (tenant_id, id),
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    CONSTRAINT membership_status_chk
        CHECK (status IN ('invited','active','suspended','left')),
    CONSTRAINT membership_left_ts_chk
        CHECK ((status = 'left') = (left_at IS NOT NULL))
);

CREATE TABLE membership_roles (
    tenant_id     text NOT NULL,
    membership_id text NOT NULL,
    role_code     text NOT NULL,
    PRIMARY KEY (tenant_id, membership_id, role_code),
    FOREIGN KEY (tenant_id, membership_id)
        REFERENCES tenant_memberships (tenant_id, id) ON DELETE CASCADE
);

CREATE TABLE membership_org_grants (
    tenant_id           text NOT NULL,
    membership_id       text NOT NULL,
    organization_id     text NOT NULL,
    capability          text NOT NULL,
    include_descendants boolean NOT NULL DEFAULT false,
    PRIMARY KEY (tenant_id, membership_id, organization_id, capability),
    FOREIGN KEY (tenant_id, membership_id)
        REFERENCES tenant_memberships (tenant_id, id) ON DELETE CASCADE,
    FOREIGN KEY (tenant_id, organization_id)
        REFERENCES tenant_organizations (tenant_id, id) ON DELETE CASCADE
);

CREATE TABLE membership_certifications (
    id            text PRIMARY KEY,
    tenant_id     text NOT NULL,
    membership_id text NOT NULL,
    kind          text NOT NULL,
    status        text NOT NULL DEFAULT 'pending',
    reviewer_id   text,
    reviewed_at   timestamptz,
    created_at    timestamptz NOT NULL DEFAULT now(),
    FOREIGN KEY (tenant_id, membership_id)
        REFERENCES tenant_memberships (tenant_id, id) ON DELETE CASCADE,
    CONSTRAINT cert_status_chk CHECK (status IN ('pending','approved','rejected'))
);

CREATE TABLE teacher_student_bindings (
    id                     text PRIMARY KEY,
    tenant_id              text NOT NULL,
    teacher_membership_id  text NOT NULL,
    student_membership_id  text NOT NULL,
    scope                  text NOT NULL DEFAULT '',
    state                  text NOT NULL DEFAULT 'active',
    created_at             timestamptz NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, teacher_membership_id, student_membership_id),
    -- 双方必须同租户：两个复合外键各自锁定 tenant_id
    FOREIGN KEY (tenant_id, teacher_membership_id)
        REFERENCES tenant_memberships (tenant_id, id),
    FOREIGN KEY (tenant_id, student_membership_id)
        REFERENCES tenant_memberships (tenant_id, id),
    CONSTRAINT binding_no_self CHECK (teacher_membership_id <> student_membership_id),
    -- **2026-10-01 补（INC-60）**：本列原先**没有任何取值约束**，
    -- 而 W-05 **TM-3 明确要求写入 `legacy`**——规格要求的取值在 DDL 里不受约束，
    -- 等于该要求可以被一个拼写错误静默违反。
    -- `ended` 由 W-05 **TM-6** 定义：教师移交时旧绑定置 `ended`（不删）。
    CONSTRAINT binding_state_chk CHECK (state IN ('active','ended','legacy'))
);

CREATE TABLE member_external_ids (
    tenant_id     text NOT NULL,
    membership_id text NOT NULL,
    namespace     text NOT NULL,
    external_id   text NOT NULL,
    PRIMARY KEY (tenant_id, namespace, external_id),
    FOREIGN KEY (tenant_id, membership_id)
        REFERENCES tenant_memberships (tenant_id, id) ON DELETE CASCADE
);
-- 同一 (tenant, namespace, external_id) 不得挂到两个不同成员上；由上面的 PK 保证
```

**`teacher_student_bindings` 的设计要点**：现有 `users.teacher_id`（F-06）是全局单值，且**一个教师只能有一个 `teacher_id` 反向不成立**——迁移时需双向展开为 (teacher, student) 对，且**必须同租户**。两个复合外键是唯一的数据库级保证；只写单列外键无法阻止跨租户绑定（总设计 8.2 行第 325 行）。

CREATE TABLE platform_role_bindings (

### 3.3.0b 成员 BYOK 凭据（`provider_credentials`，2026-10-02 补，INC-82）

> **为什么补这一节**：这张表的 DDL 原先寄居在
> [`docs/tenancy/system-settings-scope-inventory.md` §5](../../tenancy/system-settings-scope-inventory.md)，
> 而那一节的标题写的是「**交 W-07**」——**它是盘点素材，不是任何规格的存储规格**。
> 后果是三重的：① §3.6 RLS 矩阵 **24 张里没有它**（矩阵与建表必须一一对应）；
> ② `account-migration-inventory` 的 **MIG-05** 却要求
> 「逐条核对 `provider_credentials` 无缺 `membership_id` 的租户级误用」——
> **迁移检查项指向一张在本规格里根本不存在的表**；
> ③ §9.3 把它列为 **C0 权益与运营对象**，而 C0 是要放行的阶段。
>
> **它存的是 BYOK 密钥的版本化引用**（`key_ref` 指向 `secret_store`，不存明文），
> `tenant_id NOT NULL` 而 `membership_id` 可空——
> **缺 RLS 意味着跨租户可读，风险等级在全部 C0 表里最高**。
> W-07 `BK-1`/`BK-2`/`BK-3`（BYOK 必须存这里、必须绑定成员、A 校密钥 B 校不可见）
> 全部依赖这张表**存在**；而 `rls_policy_check` 的 **RL-1** 正是靠
> 「已建表但矩阵未登记」这条反向判据把它抓出来的。

```sql
CREATE TABLE provider_credentials (
    id            text PRIMARY KEY,
    tenant_id     text NOT NULL REFERENCES tenants(id),
    membership_id text,        -- NULL = 租户级默认；非空 = 成员 BYOK（复合外键见 §3.6.3）
    provider_ref  text NOT NULL,
    key_ref       text NOT NULL,   -- 指向 secret_store 的版本化引用，**不存明文**
    key_version   integer NOT NULL,
    state         text NOT NULL DEFAULT 'active',
    created_at    timestamptz NOT NULL DEFAULT now(),
    -- **2026-10-01 补（INC-60）**：本列原先**没有任何取值约束**。
    -- `retired` 对应 W-07 **SK-8** 的「核对完成 → 才退役旧 `key_id`」——
    -- **退役是轮换流程的终态，必须能被持久化并可查**，
    -- 否则「旧密钥已退役」这件事只存在于某个人的记忆里。
    CONSTRAINT provider_cred_state_chk CHECK (state IN ('active','retired','revoked'))
);

-- **2026-10-02 补（INC-82）**：唯一性必须是**两个部分唯一索引**，
-- 而不是原盘点文档里的 `UNIQUE (tenant_id, membership_id, provider_ref)`。
--
-- **为什么原写法是静默失效的**
-- ------------------------------
-- PostgreSQL 官方文档 §5.5.3 明写：
-- > By default, two null values are **not considered equal** in this comparison.
-- > That means even in the presence of a unique constraint it is **possible to
-- > store duplicate rows that contain a null value in at least one of the
-- > constrained columns**.
--
-- `membership_id` 可空 ⇒ 租户级默认（`membership_id IS NULL`）的那些行
-- **两两都不相等** ⇒ 同一租户同一 provider **可以插入任意多条租户级默认**，
-- 而「同一租户同一 provider 只有一个租户级默认」正是 W-07 **`BK-2`** 的要求。
-- **这个约束不报错，只是什么都拦不住**——比没有约束更坏，
-- 因为读 DDL 的人会以为它生效了。
--
-- **为什么不用 `UNIQUE NULLS NOT DISTINCT`**
-- ----------------------------------
-- 那是 **PostgreSQL 15+** 才有的语法（官方 §5.5.3 与 15 版发行说明）。
-- 而本项目的**目标 PG 版本尚未锁定**（总设计只写「版本按部署兼容性锁定」，
-- 仓库里没有任何 `postgres:1x` 镜像或版本断言），
-- **在版本未定时把某版本独有的语法写进 DDL，
-- 就是把一个未决的部署事实偷偷变成既成事实**——
-- 将来部署到 PG 14 整段 DDL 直接建不起来，而那时才发现改不动。
--
-- **两个部分索引在任何 PG 版本都成立**，且把两个语义分开写清楚。
CREATE UNIQUE INDEX provider_cred_tenant_uniq
    ON provider_credentials (tenant_id, provider_ref)
    WHERE membership_id IS NULL;            -- 租户级默认：每 provider 至多一条

CREATE UNIQUE INDEX provider_cred_member_uniq
    ON provider_credentials (tenant_id, membership_id, provider_ref)
    WHERE membership_id IS NOT NULL;        -- 成员 BYOK：同一成员同一 provider 至多一条
```

> **`membership_id` 用复合外键而不是裸列**：W-07 `BK-2` 要求
> 「非空时该凭据只能被该成员使用」，**而 `membership_id` 属于哪个租户
> 只能从 `tenant_memberships` 推出来**——裸 `text` 列允许写出
> 「A 租户的凭据引用 B 租户的成员」这种行，而 **L3 复合外键正是为堵它而存在**
> （总设计三层防护不可互相替代）。复合外键语句紧接本节 DDL 之后。
>
> **⚠ 与盘点文档的关系**：[`system-settings-scope-inventory.md` §5](../../tenancy/system-settings-scope-inventory.md)
> 里的**同一段 DDL 保留原文**（供追溯），但**以本节为准**——
> 那是盘点素材，不是存储规格。**两份 DDL 不一致时，规格赢。**

```sql
-- L3 复合外键：`(tenant_id, membership_id)` 必须整体命中 `tenant_memberships`
-- 的主键，从而**在数据库层**禁止「A 租户的凭据引用 B 租户的成员」。
--
-- ⚠ 这不是冗余：RLS 策略按 `tenant_id` 过滤**看不见**这个错误
-- （A 租户的 RLS 会放行这一行，因为它的 `tenant_id` 确实是 A），
-- **只有复合外键能发现**。三层防护不可互相替代。
ALTER TABLE provider_credentials
    ADD CONSTRAINT provider_cred_member_fk
    FOREIGN KEY (tenant_id, membership_id)
    REFERENCES tenant_memberships (tenant_id, id)
    -- `membership_id` 可空 ⇒ 复合外键在它为 NULL 时**不生效**（SQL 语义），
    -- 租户级默认行因此不受此约束——**这正是我们要的**：
    -- 租户级默认不属于任何成员，不该被成员外键拦住。
    -- ⚠ 但也因此：**`membership_id` 非空时该复合外键必须真的生效**，
    --   漏建它等于这张表没有任何成员归属校验。
    DEFERRABLE INITIALLY IMMEDIATE;
```

> **被引用列已核实存在**：`tenant_memberships` 在 §3.2 已声明
> `UNIQUE (tenant_id, id)`（注释里已写明「PK(id) 不覆盖 (tenant_id, id)，
> 缺此行则建表直接失败」）⇒ 上面这条复合外键的 `REFERENCES` 目标成立。
> **实施时若调整了该表的主键/唯一约束，这条外键必须同步核对。**

### 3.4 DDL 静态验证（2026-10-01，pglast 8.4 / libpg_query）

本节 DDL 草案**从未在任何 PostgreSQL 实例上执行过**（本地无 PG，docker 未运行）。
已用两级无服务端静态检查验证，工具固化于 `docs/tenancy/tools/ddl_static_check.py`：

| 级别 | 检查 | 结果 |
|---|---|---|
| 1 语法 | PostgreSQL 官方解析器逐条解析 | 22 条语句**全部通过** |
| 2 外键目标 | 每条 FK 的被引用列是否被目标表 PK/UNIQUE 覆盖 | 首轮 **8 条不通过**，修复后 8 条批内 + 2 条跨批**全部通过** |

**第 2 级发现并修复的真实缺陷**：`tenant_memberships` 原有 `PK(id)` 与 `UNIQUE(tenant_id, user_id)`，**不覆盖 `(tenant_id, id)`**。而 `membership_roles`、`membership_org_grants`、`membership_certifications`、`teacher_student_bindings`（2 条）、`member_external_ids` 共 **6 条复合外键**引用该列组。依据 PostgreSQL 官方文档 5.5.5 节：

> A foreign key must reference columns that either are a primary key or form a unique constraint, or are columns from a non-partial unique index.

**若不修复，这 6 条会在 `CREATE TABLE` 时直接失败**：`there is no unique constraint matching given keys for referenced table "tenant_memberships"`。**语法解析器无法发现此类错误**——这正说明单层验证不足。

**修复**：`tenant_memberships` 增加 `UNIQUE (tenant_id, id)`（与 `tenant_organizations` 的既有做法对称）。

**同时被官方文档证实的另一处设计**：`tenant_organizations` 的自引用外键 `FOREIGN KEY (tenant_id, parent_id) REFERENCES tenant_organizations (tenant_id, id)` 依赖默认 MATCH SIMPLE 语义——

> Normally, a referencing row need not satisfy the foreign key constraint if any of its referencing columns are null.

`parent_id IS NULL`（根节点）时外键不参与检查，**无需额外触发器**即实现根节点豁免。该设计成立。

**未覆盖**：本检查只验证语法与外键目标。**索引选择性、RLS 实际拦截、CHECK 约束运行时行为、事务隔离级别均未验证**，仍需真实 PostgreSQL 实例（W-02 T-02.7 / E6）。

### 3.5 RLS 骨架（决策属 W-04，此处只固定前提）

```sql
ALTER TABLE tenant_memberships ENABLE ROW LEVEL SECURITY;
ALTER TABLE tenant_memberships FORCE  ROW LEVEL SECURITY;   -- 总设计 8.2 行第 321 行

CREATE POLICY tenant_memberships_tenant_isolation ON tenant_memberships
    USING      (tenant_id = nullif(current_setting('app.tenant_id', true), ''))
    WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), ''));
```

**四个必须写进 ADR-02 的前提**：

1. `current_setting('app.tenant_id', true)` 在**从未设置**时返回 `NULL`；`tenant_id = NULL` 永不为真 → **天然默认拒绝**，满足 AT-05「缺上下文拒绝」，无需额外触发器
2. 设置必须用 **`SET LOCAL`**（事务局部），事务结束自动清除 → 满足总设计 8.2 行第 323 行
3. API/worker 角色**不得**是表所有者、不得有 `BYPASSRLS`；仅"需验证的表"加 `FORCE`
4. 迁移角色单独控制，**不使用** API 连接

#### 3.5.1 `nullif` 修正的准确口径（2026-10-01 补）

前提 1 只覆盖了 `current_setting` 的**「从未设置」**分支。还有第二个分支：**GUC 被显式置为空串**
（应用侧常见写法是 `set_config('app.tenant_id', payload.get('tenant_id') or '', false)`），
此时 `current_setting('app.tenant_id', true)` 返回 `''` 而**非** `NULL`。

**必须如实说明它在本项目里不是安全问题**：本规格 `tenant_id` 是 `text`（§3.1 通用约定），
`tenant_id = ''` 对任何真实行都为假，**结果仍是拒绝**。文献中常见的
`invalid input syntax for type uuid: ""` 崩溃是 `uuid`/`bigint` 强转才有的，
**本项目不适用**——引用他人经验时不能直接套用。

加 `nullif(..., '')` 的真实收益是两点，都属于**可观测性与一致性**，不是安全：

- 把「无上下文」收敛成**单一**表示（`NULL`），使排障时不必区分两种「都拒绝」的原因；
- 后续若有人把 `tenant_id` 改成 `uuid`（`tenants.kind='individual'` 的规划里存在这种可能），
  策略不会因为 `''` 而整表报错——**把未来的崩溃点在今天就消掉**。

**结论**：这是预防性归一，不是安全修复。写规格时不能把可观测性收益写成安全收益。

#### 3.5.2 五条来自 PostgreSQL 官方文档的边界（全部影响本规格）

| # | 官方行为 | 对本规格的影响 | 处置 |
|---|---|---|---|
| 1 | **参照完整性检查永远绕过 RLS**（唯一/主键约束、外键引用） | 租户 A 可通过「插入成功/外键报错」的差异**推断租户 B 是否存在某行**——官方原文称之为 "covert channel" | §3.2 已用 `(tenant_id, parent_id)` **复合外键**把租户写进键里，这是唯一正解；§3.6 逐表复核 |
| 2 | **表所有者绕过 RLS**，`FORCE` 才生效 | 迁移与 API 同用户时策略形同虚设 | 前提 3；AT-06 断言 |
| 3 | **超级用户与 `BYPASSRLS` 角色永远绕过**，`FORCE` 也不生效 | 运维账号必须单独控制 | 前提 3、4；**平台路径需要它**（§3.6 `tenants`/`platform_role_bindings`） |
| 4 | **`TRUNCATE` 不受 RLS 约束** | API 角色若被误授 `TRUNCATE` 可清空租户表而不触发任何策略 | 平台/迁移角色之外的**显式 `REVOKE TRUNCATE`** |
| 5 | **备份工具会受 RLS 影响**：`pg_dump` 以受 RLS 约束的角色运行时**只导出该角色可见的行** | 若备份角色是 API 角色，**备份会静默缺数据**且不报错 | T-02.7 必须用 `BYPASSRLS` 角色或 `row_security = off`（后者遇过滤直接报错，不静默）；**RPO/RTO 仍不承诺数值** |

> 第 5 条与第 1 条同源：**「RLS 已启用」不等于「所有路径都被 RLS 保护」，也不等于「所有路径都被 RLS 限制」**。
> RLS 是**行可见性**机制，**不是访问控制机制**——`GRANT`/`REVOKE` 是另一层，两者都要有。

**W-02 范围内只做**：建表 + 策略存在性验证 + 空上下文拒绝验证。**跨租户越权矩阵属 W-04。**

#### 3.6.2.1 平台默认拒绝表的 `ENABLE`/`FORCE`（**无策略是刻意的**）

`platform_role_bindings` 与 `migration_batches` **不写任何 `CREATE POLICY`**——
`ENABLE` + 无适用策略 = 对该角色**默认拒绝**（看不到任何行、改不了任何行）。
但 `ENABLE` 与 `FORCE` **必须写**，否则表所有者直接绕过，连默认拒绝都没有。

```sql
-- ⑩ platform_role_bindings：「谁拥有平台角色」的权威表
ALTER TABLE platform_role_bindings ENABLE ROW LEVEL SECURITY;
ALTER TABLE platform_role_bindings FORCE  ROW LEVEL SECURITY;
-- 刻意不建 CREATE POLICY：对 API 角色默认拒绝

-- ⑪ migration_batches：迁移/运维账本
ALTER TABLE migration_batches ENABLE ROW LEVEL SECURITY;
ALTER TABLE migration_batches FORCE  ROW LEVEL SECURITY;
-- 刻意不建 CREATE POLICY：对 API 角色默认拒绝
```

> **只 `ENABLE` 不建策略 ≠ 什么都不做**。没有 `ENABLE` 时表所有者看得到全部行；
> `ENABLE` 之后无策略才是真拒绝。**「默认拒绝」本身是一项必须显式声明的设计决定。**

#### 3.6.3 四条例外策略（**不得套用上面的模板**）

##### ① `tenants`：双主体策略

租户成员必须能读**自己那一行**（显示机构名/时区），平台运维必须能读**全部**。
它没有 `tenant_id` 列——**租户身份就是主键 `id` 本身**。

```sql
ALTER TABLE tenants ENABLE ROW LEVEL SECURITY;
ALTER TABLE tenants FORCE  ROW LEVEL SECURITY;

-- 平台主体：X-Expected-Tenant 路径（总设计 §8.2，仅 require_platform_admin 可用）
CREATE POLICY tenants_platform_read ON tenants
    FOR SELECT TO pg_read_all_data
    USING (true);

-- 租户主体：只看自己
CREATE POLICY tenants_self_read ON tenants
    FOR SELECT
    USING (id = nullif(current_setting('app.tenant_id', true), ''));

-- 建租户只允许平台角色（默认主体 = API 角色，其下无策略 = 默认拒绝）
-- 因此**不写**任何 FOR INSERT/UPDATE/DELETE 的 API 策略：
-- 多个 PERMISSIVE 策略之间是 OR 关系，写一条 USING(true) 的 SELECT 策略
-- 不会放宽写权限——RLS 的 USING 与 WITH CHECK 是两套子句。
```

> **注意策略组合语义**：`tenants_platform_read` 与 `tenants_self_read` 都是 **PERMISSIVE**，
> 多条 PERMISSIVE 之间取 **OR**。这不是"平台 AND 租户"的收紧效果。
> 若日后要叠加「即使平台身份也必须满足某条件」，必须显式写 `AS RESTRICTIVE`
> （RESTRICTIVE 与其他策略取 **AND**，需 PostgreSQL 9.5+ / 15+ 视用法而定）。
> **W-02 不使用 `RESTRICTIVE`**——避免在未验证的版本语义上建立隔离依赖。

##### ② `platform_role_bindings` / `migration_batches`：默认拒绝

这两张表**对 API 角色不建任何策略**。`ENABLE ROW LEVEL SECURITY` 且无适用策略
⇒ 该角色**看不到任何行、也改不了任何行**（默认拒绝）。

平台运维路径通过**具备 `BYPASSRLS` 的独立角色**访问（§3.5.2 第 3 条已确认
`FORCE` 对 `BYPASSRLS` 无效，因此这**必须**靠角色隔离而非策略）。

> **为什么不给 `platform_role_bindings` 建策略**：它是「谁拥有平台角色」的权威表。
> 租户侧一旦可读，就能枚举平台管理员账号 → 定向钓鱼/撞库。
> **默认拒绝是唯一正确选择**，不存在「只给只读策略」的中间态。

##### ③ `tenant_invitations`：令牌接受必须走特权路径，**不得开口子**

**问题**：用户接受邀请时**还不是成员**——此时没有 `app.tenant_id`。
按 3.6.2 的标准策略，`token_hash` 校验这一步会因**无租户上下文**而查不到任何行，
邀请流程直接不可用。

**错误做法**（必须明确禁止）：给 `tenant_invitations` 加一条
`USING (true)` 或 `USING (current_setting('app.tenant_id', true) IS NULL)` 的策略来「让流程跑通」。
后者尤其危险——它把「**忘记设上下文**」从**拒绝**翻转成**放行**，
直接摧毁 AT-05「缺上下文拒绝」这一安全性质。**故障模式从「看不见」变成「全看得见」。**

**正确做法**：接受路径使用**独立特权连接**（`BYPASSRLS` 角色）或
`SECURITY DEFINER` 函数按 `token_hash` 定位，**在应用层完成归属校验后再切换到标准租户上下文**。
令牌校验属于**未认证流程**，本来就必须独立于 RLS 上下文。

| 流程 | 租户上下文 | 访问方式 |
|---|---|---|
| 租户管理员**创建/撤销**邀请 | 有 | 标准策略（3.6.2 ⑧） |
| 邀请接受（**未认证**） | **无** | **特权路径**：按 `token_hash` 查，不依赖 `app.tenant_id` |
| 接受完成后的成员操作 | 有 | 标准策略 |

##### ④ `support_grants`：标准隔离 + **授权窗内的跨租户访问**

`support_grants` 自身是**租户数据**（记录「谁被授权进入哪个租户」），
所以**行隔离用标准策略**（3.6.2 ⑨）。但平台支持人员在**工单有效期内**需要读该租户数据。

**这里有一个容易做错的地方**：支持授权**不是**通过在 `support_grants` 上加一条
`USING (true)` 实现的——那样等于让**所有**租户上下文都能看到全部授权记录，
把「谁在支持我们」变成公开信息。

正确做法是**两个独立的授权点**，不能合并：

| 授权对象 | 授权内容 | 授权方式 |
|---|---|---|
| `support_grants` 这**张表** | 谁能读这条授权记录 | 标准 RLS 策略：仅**该租户自己** + 平台 `BYPASSRLS` 角色 |
| 被授权的**目标租户数据** | 支持人员能读哪些表/行 | **应用层**在工单校验通过后，用 `SET LOCAL app.tenant_id` 切到目标租户 |

**`support_grants` 行的 RLS 策略不负责放行目标数据**——它只管这张表本身。
目标数据的访问由「`SET LOCAL` 前必须先校验 `expires_at > now() AND revoked_at IS NULL`」
这一**应用层前置条件**保证。**这条校验写在 W-04，不在本节。**

> **风险登记**：把跨租户访问做成 RLS 策略里的时间判断
> （例如 `USING (expires_at > now())`）是**错误做法**——
> 它让**策略本身**成为授权载体，而策略无法可靠表达"哪个工单、谁批准、审计留痕"。
> **授权判定留在应用层，RLS 只负责行隔离。** 两层职责不可混淆。

#### 3.6.4 与 §4 现有表的关系（**阶段不同，不要混**）

§4 判定的**现有 `tenant` 表**（**张数以 §4.1 行 8～24 的清单为准，本节不复述数字**。

### T-02.5.1 contract 阶段：`SET NOT NULL` 与 RLS 的**前置条件**（2026-10-01 补）

> **本节不产出可执行 DDL，只固定"什么条件下才允许执行 contract"**。
> 原因见下：contract 阶段的每一条 DDL 都**不可回退**，前置条件不成立时执行等于
> 把「数据缺失」升级成「服务不可用」。

#### 实测冲突（本地真实库，2026-10-01）

用 `backfill_migrate.py` 对 `backend/data/paperguard.db` 跑 dry-run 实测：

```
源用户总数        15
已迁移成员关系     3
隔离清单         22        ← 关键
待业务裁决         2
MIG-07 账实平衡：15 = 3 + 10 + 2 + 0
```

**22 条隔离行的 `tenant_id` 必然为 `NULL`**，分布为：

| 表 | 隔离行数 | 原因 |
|---|---|---|
| `users` | 10 | rule-3：`organization_context` 无 `school_id`（**INC-09**，产品缺口） |
| `projects` | 6 | backfill：`owner_id` 指向的用户无租户成员关系 |
| `templates` | 3 | 模板无 `owner`、无 `scope`（**INC-03**） |
| `requirement_sets` | 3 | **口径警告：这里数的是「解析不出租户的行」，不是「`scope_id` 为空的行」**。实测**两者的基数碰巧都是 3，但集合不同**（2026-10-02 实跑核对，见 INC-74）：① **`scope_id` 为空的是 4 行**（含 `scope='teacher'` 那行，它**有 `owner_id=user-uat-teacher`**，走 owner 分支成功解析，因此**不进隔离**）；② **进隔离的 3 行** = `scope='global'`（归属未在设计中定义）+ 两条 `scope='college'`（`scope_id` 空）。`scope='global'` 那行 `scope_id` 也为空，**但它进隔离的理由是「归属未定义」，不是「scope_id 空」**——而它恰恰是唯一能证明**空串同时承载两种语义**的证据 |

> 注意 `users` 隔离 10 条而 MIG-07 分桶里 `backfill` 桶也是 10——
> **同一批用户在两个桶里各出现一次**（这正是 INC-07 分桶修复的原因：
> 直接对子集求和会得 `3+12+2=17 ≠ 15`）。上表的 22 是**行**数，
> 分桶的 15 是**用户**数，两者口径不同，不能互相校验。

#### 三条不可回退的 DDL 及其阻断条件

| contract 动作 | 对 `tenant_id IS NULL` 行的影响 | 当前能否执行 |
|---|---|---|
| `SET NOT NULL` | PostgreSQL 直接**报错**（存在 NULL 值） | **否**——22 行阻断 |
| 建 RLS（§3.6 同款策略） | 该行**对所有租户不可见**（`tenant_id = NULL` 不匹配任何上下文） | **否**——22 行静默消失 |
| 移除旧唯一约束 | 无直接影响 | 是（但会失去兜底） |

**第二条是最危险的**：`SET NOT NULL` 至少会**响亮地失败**；
而建 RLS 会让这 22 行**静默地对所有人消失**——
对应设计文档里已记录的「静默失效比报错更难发现」。

#### 因此 contract 的准入条件（**全部满足才允许**）

1. 隔离清单**归零**（22 → 0）。每一条都必须有**真实归属**，
   不得用「默认落到某租户」消号——**这与 AC-02-9「0 条被猜测归属」是同一条纪律的两面**。
2. `templates` 归属**先由产品裁决**（INC-03）：模板是「每租户副本」还是「平台级共享」？
   若为平台级共享，则 `templates` 不应是 `tenant` 判定，`§4` #11 的判定要改。
3. `requirement_sets` 的 `scope='global'` 归属**先定义**（INC-04）。
4. `workflow_events`（§4 #23 明确要 `NOT NULL`）单独确认：
   本地库 0 行，**取不到样本**，其 `NOT NULL` 只能等真实数据出现后再验证。

**若上述条件未满足，正确做法是「不执行」**——
contract 阶段推迟**不会**造成损害，而错误执行会让 22 行数据对所有用户不可见。

#### 由此产生的设计要求

- `templates` 若裁决为「平台级共享」，则需要 `asset_scope` 列**先有值**才能区分
  「公共资产」与「本租户资产」；**禁止用 `tenant_id IS NULL` 同时表达"公共"和"未归属"**
  （§4 #11 已写明此禁止，contract 执行时必须复查）
- 隔离清单必须成为**可跟踪的工单**，而不是一次性报告——
  工具 `backfill_migrate.py` 的 dry-run 每次都能重新产出它

**未验证**：以上全部基于本地库 dry-run（`local_gate_passed`）。
真实 PostgreSQL 上 `SET NOT NULL` 的实际报错行为**未验证**（本机无 PG）。

### T-02.6 回填与校验器（E5）

**做**：
1. **回填器**：分批、幂等、有 checkpoint 写入 `migration_batches`；支持中断续跑
2. **独立校验器**（与回填器**不同进程/不同代码路径**，避免自证）：
   - 数量核对：每表总数、已回填数、冲突数
   - 关系核对：组织树无环、无跨租户父子、无断链
   - 摘要核对：不可变内容的 hash 与源库一致（提交快照、归档 manifest、总设计 10 节"不破坏原快照和清单哈希"）
   - 版本核对：`document_packages` / `plan_versions` 类冻结版本一致
   - 权限核对：迁移角色与 API 角色权限符合 ADR-02
   - 真实产物核对：至少 1 个真实 DOCX/归档能打开且内容一致

**归属规则（只读预检产出，M1）**：
- 根组织经人工确认映射租户，子树继承 → `tenant_id`
- 多根、循环、断链、冲突 → **进入隔离清单，不猜测**
- 个人历史项目无机构归属 → **不自动分给当前学校**
- 老审计事件 → 标 `legacy`，不伪造 `request_id`/操作者

**DoD**：
- 回填器**连跑两次**，第二次产生 0 行变更（幂等证明）
- 中断后从 checkpoint 续跑，结果与不中断一致
- 校验器对**故意注入的 5 类错误**（跨租户父子、孤儿、摘要不符、版本漂移、越权角色）**全部报出**
- 冲突数据 100% 落在隔离清单，**无一条被猜测归属**

> **「前置 AT-xx」与「验收 AT-xx」是两种不同关系**（2026-10-01 显式化）
>
> 本表初版把 `AT-04` / `AT-05` / `AT-45` 混在判据文字的括号里，
> 读起来像「W-02 验收这三条」。**但 §24.2 里没有任何一条 AT 归属 W-02**——
> AT-04 归 W-04、AT-05 归 W-03/04、AT-45 是跨阶段条目。
>
> 真实关系是：W-02 交付的**约束与策略是这些 AT 的前置**，
> AT 本身要由 W-03/W-04 的运行时行为验证。混淆两者会导致两种错误：
> - 以为 W-02 做完这三条 AT 就过了 → 漏掉 W-03/W-04 的运行时验证
> - `at_traceability_check` 的 AT-10 把它们当归属声明 → 误判归属不符
>
> 因此本表用 `E3 · 前置 AT-04` 显式标注关系，判据文字里不再夹带裸 AT 编号。
> **前置关系仍被记录，只是不再冒充验收归属。**

> 证据格式遵循总设计 24.4 行，环境标 `LOCAL` / `ISOLATED`，终态标 `PASS` / `FAIL` / `NOT RUN` / `BLOCKED` / `RESIDUAL`。

## 7. 负面与并发测试要求

**负面**（必须全部有独立用例，不得只测正例）：
1. 缺 `app.tenant_id` 的读/写 → 拒绝（AT-05）
2. A 租户 `parent_id` 指向 B 租户组织 → 数据库拒绝
3. A 租户成员绑定 B 租户成员为师生 → 数据库拒绝
4. A 租户组织授权指向 B 租户组织 → 数据库拒绝
5. `tenant_id` 写策略：`WITH CHECK` 拒绝改写为其他租户
6. 同 `idempotency_key` 不同内容 → 冲突而非静默复用（总设计 4.8 行）
7. 迁移角色被 API 路径使用 → 拒绝
8. 表所有者 / `BYPASSRLS` 角色出现在普通路径 → 断言不存在（AT-06）

**并发**（对应总设计 9.1 行 CAS 与 W-09 预留）：
9. 两个事务并发改同一 `quota_periods.used` → 只有一个成功
10. `version` 比较并交换 → 失败方得到明确冲突，不静默覆盖
11. `tenant_memberships.auth_version` 并发递增 → 不丢失更新
12. 唯一键扩展后并发插入同一业务键 → 恰好一条成功
