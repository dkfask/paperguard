# W-13 SSO、域名品牌与独立部署模板 · 实施规格

> 版本：2026-10-01 · 阶段 **按客户范围**（非阶段门禁）· 依赖 W-03（租户上下文）、W-05（成员与启用）
> 上游：总设计 §11.3（SSO 扩展）、§11.4（离校/停用/移交）、§23.1 W-13 行、§24.2 AT-43
> 下游：无（本包是设计链末端）
> 状态：`design_ready` —— 规格已定稿可执行，**未实施、运行时零验证**

## 0. 本规格要解决什么

W-13 是**唯一按客户触发、而非按阶段放行**的工作包。
§23.1 的完成定义写得很直接：**「逐客户验证，不把可选能力拖入所有试点门禁」**。

这一定位本身就是本包最容易做错的地方——
**「按需」极易被实现成「随手」**：
把 SSO 绑定写成「邮箱相同即视为同一人」，
把自定义域名做成「读取请求 Host 决定当前租户」，
两者都**看起来实现了功能**，且**在试点客户身上都「能用」**。

§24.2 只给了它 **1 条 AT**（AT-43），
但那条 AT 的判据——**「绑定正确 issuer/subject/租户，不凭 email 给管理员」**——
覆盖的正是上述两个失败形态。

### 0.1 现状取证（2026-10-01，代码只读）

| # | 事实 | 位置 | 意味着 |
|---|---|---|---|
| 1 | 全仓 `sso`/`oidc`/`saml`/`jwt`/`id_token`/`issuer` 检索**零业务命中** | `backend/app/**.py` grep | **无任何 SSO 实现** |
| 2 | 唯一含 `openid` 的是 `backend/app/auth.py:332` 的 `_openid_cipher` | `backend/app/auth.py:332-353` | ⚠️ **那是微信推送的可逆保护，不是 OIDC**。`secret_store.py:12` 已自述它是「派生流 XOR、**对篡改无检测能力**」——**不得被误认为已有外部身份支持** |
| 3 | **nginx 是 `server_name _;`（接受任意 Host）** | `ops/nginx/paperguard.site.conf:17` | ⚠️ **AT-43「域名伪造」的现状** |
| 4 | 后端**零 `TrustedHostMiddleware`** | 全仓 grep | 应用层**不校验 Host**，主机头完全由客户端控制 |
| 5 | CORS 由 `PAPERGUARD_CORS_ORIGINS` 环境变量驱动，默认 `http://localhost:5173` | `backend/app/main.py:131-141` | CORS 是**浏览器**机制，**不保护**服务端到服务端或直接 API 调用 |
| 6 | 前端**无 branding/logo/自定义域名任何概念** | `frontend/src` grep | 品牌能力从零 |

> **第 3、4 条合起来是本包最需要先讲清的一条。**
> 当前**单租户、按 IP 访问**的部署下，不校验 Host **不构成可利用漏洞**——
> 没有任何决策依赖 Host。
> 但 W-13 一旦引入「按域名区分租户」或「自定义域名」，
> **Host 就从「无关信息」变成「租户身份的唯一来源」**，
> 而它此刻**完全由客户端控制、且 nginx 与应用都不设防**。
> **这不是「先有漏洞后加功能」，而是「加功能会让一个无害的现状变成越权入口」。**
> 因此 DM-1（Host 可信化）**必须先于**任何按域名分租户的逻辑落地。

## 1. 域名与主机可信化（DM）—— AT-43 前半

| # | 规则 | 说明 |
|---|---|---|
| DM-1 | **任何依赖域名的决策落地前**，必须先有 Host 可信化：应用层 `TrustedHostMiddleware` + nginx 显式 `server_name` | §0.1 第 3、4 条；顺序颠倒就是把无害现状变成越权入口 |
| DM-2 | 域名→租户的映射**只从已登记的租户记录读取**，**不得**从请求 Host 即时推断 | 「即时推断」等于让客户端指定租户 |
| DM-3 | 未登记的域名 ⇒ **拒绝**，**不得**回退到默认租户 | 与 W-07 TP-4 同一原则：**未知不得借用** |
| DM-4 | CORS **不得**作为域名安全的依据；`allow_origins` 的取值来自**已登记域名**而非请求头 | CORS 保护的是浏览器，服务端调用不受它约束 |
| DM-5 | 重定向/回调 URL 必须是**已登记域名下的固定路径**，**不得**从请求构造 | 防开放重定向 |
| DM-6 | 域名变更（新增/移除/转移）**必须**有审批、版本与审计 | 与 W-06 PV-5、W-10 §1.1 同族 |
| DM-7 | `Host`/`X-Forwarded-Host` 的信任**只接受来自已配置代理的请求** | 直接采信可被伪造 |

> **DM-4 需要特别说明，因为它是常见误解**：
> 有人会认为「CORS 配了域名就等于域名安全了」。
> 实际上 CORS 只在**浏览器**发起跨源请求时生效——
> 攻击者用 `curl`、脚本或服务端调用时**完全不受约束**。
> CORS 是**体验与部分防护**，不是身份来源。

## 2. SSO 身份绑定（SS）—— AT-43 后半

§11.3：「外部 subject 以**租户 + 身份提供方 + subject** 绑定成员，
**不能仅凭 email 字段连接高权限账号**。」

### 2.1 五个必须校验的条件

| # | 规则 | 说明 |
|---|---|---|
| SS-1 | 校验 **`issuer`**（精确匹配，不接受后缀/通配） | issuer 不同即不同机构 |
| SS-2 | 校验 **`audience`** | 否则 A 机构的令牌可被 B 机构接受 |
| SS-3 | 校验 **`state`/`nonce`** | 防授权码重放与 CSRF |
| SS-4 | 走**授权码流程**（`response_type=code`），**不接受**隐式流 | 隐式流把令牌暴露在 URL |
| SS-5 | 经**验证**的机构身份映射后才建立绑定 | §11.3「经过验证的机构身份映射」 |

### 2.2 绑定键与跨机构隔离

| # | 规则 | 说明 |
|---|---|---|
| SS-6 | 绑定唯一键 = **`tenant_id` + `issuer` + `subject`**，三者缺一不可 | §11.3 原文 |
| SS-7 | **禁止**用 email 作为绑定键，**尤其禁止**对高权限角色 | AT-43「不凭 email 给管理员」 |
| SS-8 | email 相同但 `(issuer, subject)` 不同 ⇒ **两个不同的人** | 跨机构同名邮箱是常态，不是异常 |
| SS-9 | email 变更**不得**自动改绑既有 SSO 绑定 | 否则外部身份提供方的一次改邮箱就能劫持本地绑定 |
| SS-10 | 一个本地账号可绑定**多个** `(issuer, subject)`，但**每个租户内至多一条**绑定 | 跨机构任职是真实场景 |
| SS-11 | 绑定**不删除历史论文**；SSO 权限变动与成员同步**分别处理** | §11.3 第 2 段 |

> **SS-7 的失败形态值得写具体**：若用 email 绑定，
> 攻击者只需在**任意一个**机构 IdP 里注册**同名邮箱**，
> 登录时就会命中本地高权限账号。
> 危害随「哪些机构接了 SSO」而扩大——
> **接的机构越多，攻击面越大**，而这与「我们更安全了」的直觉相反。

### 2.3 SSO 与既有账号生命周期

§11.3 第 2 段：管理员锁定、成员退出、回收权限和数据移交**分别处理**。

| # | 规则 | 说明 |
|---|---|---|
| SS-12 | SSO 登录**不得**绕过席位准入（W-06 SL-1） | SSO 是认证方式，不是权益来源 |
| SS-13 | SSO 登录**不得**自动授予管理员 | §11.3「不走自动管理员授权」 |
| SS-14 | 缺失验证条件时**拒绝绑定**，**不**降级为密码登录后放行 | §11.3 原文 |
| SS-15 | IdP 侧停用**不会**自动撤销本地成员；撤销走 W-03 `auth_version` 通道 | 否则每次 IdP 抖动都会误伤教学；反向的「等 IdP 通知」也不可靠 |

## 3. 品牌（BR）

| # | 规则 | 说明 |
|---|---|---|
| BR-1 | 品牌配置属 `tenant_settings`（W-06 TP-7），**有 `schema_version` 与继承规则** | 与 W-07 一致，不新开配置体系 |
| BR-2 | 品牌**不得**影响任何正文权限或数据可见性 | §12.2「管理治理：功能开关与范围，**不提高正文权限**」 |
| BR-3 | 上传的品牌资产走 `storage_objects` 目录（W-04），**不进**通用文件路径 | 防静态旁路（AT-13 同一教训） |
| BR-4 | 品牌资产**限制类型与尺寸**，且**服务端重新编码/校验**，不信任扩展名 | 与 W-05 上传安全同族 |
| BR-5 | 品牌切换**不影响**既有会话与数据归属 | 品牌是呈现层，不是身份层 |

## 4. 独立部署模板（DP）

§23.1 W-13 行：「独立部署模板等扩展」，ADR-02 备注「按客户需求独立部署可保留」。

| # | 规则 | 说明 |
|---|---|---|
| DP-1 | 独立实例**必须**仍满足 W-01～W-12 的安全不变量（租户隔离、RLS、密钥、审计、恢复） | 独立部署是**部署形态差异**，**不是安全降级** |
| DP-2 | 模板必须**显式声明**它跳过了哪些能力及原因；**不得**以「独立实例」为由隐式跳过 | 跳过的能力若不登记，日后无人知道它没被验证 |
| DP-3 | 独立实例的**配置、密钥、备份、恢复**各自独立，**不得**跨实例共享主密钥 | 密钥共享 = 一次泄露击穿全部客户 |
| DP-4 | 模板升级**必须**走 W-10 §5 的恢复要求（先验证再替换） | 模板是最容易被「直接覆盖」的东西 |
| DP-5 | **不得**为单个客户在共享实例上开「事实上的独立部署」特例 | 特例会侵蚀 W-04 的隔离假设 |

> **DP-5 是本节最需要守住的边界**：
> 「就这一个客户特殊一下」在实现上极其方便，
> 而它的后果是**共享实例上出现一个不受 W-04 假设约束的特例**——
> 之后所有关于该实例的安全论证都不再成立。
> 正确路径是**真独立部署**（成本更高）或**明确的功能差异**（成本可控）。

## 5. 扩展的门禁纪律（XG）

§23.1 完成定义的第二半：**「不把可选能力拖入所有试点门禁」**。

| # | 规则 | 说明 |
|---|---|---|
| XG-1 | 启用 W-13 任一能力的租户，**必须**跑该能力的**专项门禁**；未启用的租户**不跑** | 「按需」的正确形态 |
| XG-2 | 但**基础安全门禁对所有租户一律执行**，**不得**因「该客户没启用」而豁免 | 与 XG-1 不矛盾：可选能力按需，基础安全不让步 |
| XG-3 | 每个启用项必须有**可核对的启用记录**（谁、何时、依据哪份客户要求） | 「按客户范围」必须可追溯，否则范围会静默扩大 |
| XG-4 | 关闭某扩展**不得**削弱已产生数据的可见性 | 关闭 SSO 不等于删除绑定记录 |

> **XG-1/XG-2 是一对**：
> 只有 XG-1 会让「没启用 SSO」被当成「可以不做安全检查」；
> 只有 XG-2 会让「基础门禁」被拖成「全客户全量检查」而无法执行。
> **分开写，是因为它们经常被同一个人用同一种理由一起违反。**

## 6. 验收

| AC | 关联 AT | 判据 | 证据 |
|---|---|---|---|
| AC-13-1 | **AT-43** | ①SSO 映射：`(issuer, subject, tenant)` 三元组正确绑定；**同名邮箱跨机构不合并**；**不凭 email 给管理员** | 本包 §2；多 IdP 替身 + 跨机构同名邮箱用例 |
| AC-13-2 | **AT-43** | ②域名伪造：伪造 `Host`/`X-Forwarded-Host` **无法**切换租户、未登记域名被拒 | 本包 §1；伪造头用例 + 直连（非浏览器）调用 |
| AC-13-3 | **AT-43** | ③跨机构外部身份：A 校身份在 B 校**不可用**；撤销 A 校绑定**不影响** B 校同一本地账号 | 本包 §2.2 SS-10 + W-03 `auth_version` |

**本包无法独立验证的部分**（不得混入「通过」）：

- **SSO 需真实 IdP 或高保真替身**。替身若只返回「合法令牌」，
  AC-13-1 的 issuer/audience/nonce 校验**根本不会被执行**——
  三个校验条件里没有一个会被测到。替身**必须能签发错误 issuer / 错 audience / 重放 nonce**。
- **DM-1 的 nginx 侧验证需要真实反向代理**；应用层 `TrustedHostMiddleware` 可单测，
  但 `server_name` 与 `X-Forwarded-Host` 的可信代理配置**必须实测**。
- 跨租户身份用例需要 `tenant_memberships`（表不存在，连续多轮阻塞）。
- **D-10 未裁决**（微信/SSO 是否进入 C0 范围）——本包**按客户触发**的定位
  意味着它**不阻塞** C0，但**具体客户是否需要**尚未确定。

## 7. 门禁

| 判据 | 静态可查？ | 处置 |
|---|---|---|
| 新表（SSO 绑定、品牌配置）是否登记 RLS | ✅ | `rls_policy_check` RL-1 双向核对 |
| **是否仍存在「按请求 Host 即时推断租户」的代码** | ✅ **可静态查** | 建议纳入 `context_resolution_check`：**当前 114 处全局 `role` 引用**已是同类问题，域名分租户若以同样方式实现，形态一致 |
| nginx `server_name` 是否为通配 `_` | ✅ 可静态查 | 属 `ops/` 部署配置，随模板变更而非随代码变更 |
| SSO 五项校验是否齐全（SS-1～SS-5） | ❌ | 运行时 + 恶意 IdP 替身 |
| 绑定键是否含 `tenant_id`+`issuer`+`subject` | ⚠️ DDL 可查 | 约束可查；**实际绑定逻辑不可静态查** |
| 品牌不影响正文权限（BR-2） | ❌ | 权限回归用例 |

> **本包不新增独立门禁**，与前十二个包同一判断。
> 唯一下面标 ✅ 的两项**可以**并入既有门禁而不新建：
> 「按 Host 即时推断租户」并入 `context_resolution_check`，
> `server_name` 并入 `design_doc_check` 的部署配置核对。
> **不建议**为此单开一个门禁——**门禁数量本身是成本**，
> 只有当一个判据有独立的失败模式时才值得独立存在。

## 8. 明确不做

| # | 不做 | 理由 |
|---|---|---|
| 1 | SAML | §11.3 只要求「OIDC **等**」；先做一种，**不预建第二套** |

| 6 | 把品牌做成「换个 logo 就算租户隔离」 | BR-2 |
