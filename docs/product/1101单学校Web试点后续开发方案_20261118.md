# PaperGuard 1101 单学校 Web 试点后续开发方案

2026 年 11 月 18 日制定，供开发与验收使用。方案依据主线提交 `8684f94`；实施时从最新主线建立独立工作区。微信小程序真机验收和多租户扩展另行排期。

## 首期目标

**交付一个可供学校试用的 1101 Web 师生闭环。** 学生用学校 1101 v4 正式模板和真实规范 PDF，在现有写作页完成一篇含代表性插图的论文。PaperGuard 负责排版和成品格式检查。学生能下载可提交的 Word 成品，教师能批注退回并接受重提后的版本，学校能从归档取回教师接受的同一份成品。

**首期范围**　一个试点学校、一个试点批次、一套经确认的正式模板与规范。沿用现有图片插入、写作、教师审核和归档流程。插图工作聚焦图题、编号和成品中的字号核验。图内标注证据不足时标为待核验，硬性规则按现有门禁处理。学校日常必用的插图如果持续因证据不足而无法交付，记录为试点阻塞。

### 首期验收标准

1. **合格样稿可交付。** 使用正式模板和完整规范 PDF，至少一篇含代表性学生插图的样稿，在同一候选版本上完成写作、导出、提交、教师退回、学生重提、教师接受和自动归档。
2. **阻断原因可定位。** 另用一份违规或证据不足的样稿验证门禁。学生可找到需核对的插图和对应规则。模板固定图形可正确识别，不触发学生插图的字号阻断。
3. **归档成品可核对。** 教师接受的最终提交与归档包中的 `final.docx` 文件摘要一致。对同一文件在桌面 Word 和 WPS 中更新目录并核对目录页码、分节页眉页脚、跨页表格和图题位置。
4. **试点环境可运行。** 经授权发布后，在同一线上版本上用受控师生账号复验完整流程，并留存版本、成品和检查记录。

以上四项作为首期交付判据。限流修复和 CI 通过是工程前置，正式模板和规范下的师生闭环、归档成品与桌面验收决定试点是否可交付。

现有本地测试已在跳过规范 PDF 附件时跑通师生流程。加载真实规范 PDF 的用例则在导出时确认页面提示“图中标注字号待核验”，随后结束。下一轮需要保留这个阻断用例，同时验证符合学校规范的论文确实可以交付。[现有师生流程测试](https://github.com/dkfask/paperguard/blob/8684f94/frontend/e2e/full-lifecycle.spec.ts#L655)

## 第一阶段　恢复主线测试

独立复现 Python 3.11 下的管理员 AI 配置限流失败。在每分钟仅允许一次请求的测试中，第二次请求仍然成功。检查两次请求是否处于同一限流窗口、是否共享正确的计量状态，以及单独运行和整组运行的结果，再根据根因修复。[当前失败记录](https://github.com/dkfask/paperguard/actions/runs/43712311057/job/132806339880)

**验收条件**　在同一窗口内，第一次请求成功，第二次被限流，上游只收到一次调用。修复提交通过 Python 3.11、3.12 和项目要求的 CI 检查。

## 第二阶段　验证学生插图的字号

按学校原文“图中标注符号和文字的字号不大于图题字号”核验。先选取学校实际使用的插图，区分模板固定图形、可读取文字属性的学生插图和只有像素的截图。用最终导出的 Word 核对图题字号与图内标注大小，依据能取得的证据确定实现范围。[现有规则识别逻辑](https://github.com/dkfask/paperguard/blob/8684f94/backend/app/services/requirement_check.py#L48)

| 验收样例 | 预期结果 |
| --- | --- |
| 模板自带的固定图形 | 系统识别其来源，图形不触发针对学生插图的字号阻断。 |
| 标注大小可核验且符合规则的学生插图 | 通过该项检查；其余要求也满足时可下载成品。 |
| 标注明显大于图题的学生插图 | 系统阻止交付，并指出图号和违反的规则。 |
| 无法可靠取得标注字号的截图 | 系统指出具体图号、待核验规则和可行的修改方式。 |

**验收条件**　四类样例均得到预期结果。如果学校常用截图仍缺少可靠的判定方法，应明确系统支持的输入形式及学生可采取的修改办法，并将受影响场景保留为试点交付阻塞。

## 第三阶段　跑通正式规范下的师生流程

使用同一份 1101 v4 正式模板和规范 PDF，保留应当阻断的样稿，另准备一份含合规插图、应当正常交付的样稿。后者按业务顺序验证以下步骤。

1. 学生完成写作、导出 Word 并提交给教师。
2. 教师批注并退回，学生修改后重新提交。
3. 教师接受最终提交，后台自动归档。
4. 下载归档包，核对归档清单、包内 `final.docx` 和教师接受的最终提交文件的 SHA-256 摘要。[已有归档校验](https://github.com/dkfask/paperguard/blob/8684f94/frontend/e2e/full-lifecycle.spec.ts#L939)

**验收条件**　两条场景在同一候选版本上通过，合格样稿可以下载，归档成品与教师接受的版本一致。

## 第四阶段　核验成品并进入试点发布

用第三阶段实际归档的同一份论文，在桌面 Word 和 WPS 中分别更新目录。核对目录条目指向的实际页码、各分节的页眉页脚和页码、跨页表格，以及图题与插图的相对位置，并记录所用软件版本和发现差异的页码。

**验收条件**　两款软件的成品核验记录齐全，影响提交或阅读的版式问题已修复并复核。随后按项目发布流程单独确认部署，核对线上前后端版本，并使用受控师生账号在同一发布版本上完成提交、退回重提、接受和归档下载。

## 执行顺序

第一阶段作为独立修复提交。第二阶段优先验证学校常用插图能否取得可信的字号证据，这是影响试点交付的主要技术问题。取得可重复的合规样稿后进入第三阶段，并把第三阶段归档的成品直接用于第四阶段验收。

## 2026 年 11 月 18 日执行记录

- **限流修复**　本地在 Python 3.11 模拟两次请求跨 UTC 分钟，复现了 CI 中第二次请求返回成功的问题。提交 `3d3ee31` 将测试时钟固定在同一窗口，并补齐独立运行所需的测试管理员。Python 3.11 和 3.12 的本地后端全量回归各通过 2753 项。GitHub CI 的 5 项检查通过，证据对应修复分支提交。[修复分支 CI](https://github.com/dkfask/paperguard/actions/runs/44285401847)
- **正式规范阻断用例**　以主线 `8684f94` 为基线，使用 1101 v4 正式模板、2027 届规范 PDF、真实样稿及现有服务端排版模式重跑 Chromium 流程。走到学生导出，确认图内字号门禁阻止交付，结果 1 项通过、1 项按桌面测试范围跳过。本地测试提交 `1c1346c` 将模板试排断言的等待上限调至 120 秒并通过前端类型检查。本机 Word 分页探针超时，仍需使用含可核验插图的合格样稿验证下载、归档和桌面版式。
- **字号证据实验**　抽检的学生样稿有 27 个嵌入绘图对象，正文图内文字没有可读取的 Word 字号属性。作为独立验证，合成原生柱状图的 DOCX 回读能区分 10.5 磅图题与两组轴标注（9 磅、14 磅），LibreOffice 导出的 PDF 保留了对应的显示字号。这个结果用于评估已有材料中哪些字号证据可读取。试点开发范围沿用原方案，围绕现有图片和文档流程核验。
- **阻断时可定位插图**　提交 `c97a5c6` 在现有导出拦截提示中加入“查看待核验详情”，从检查详情可跳转到正文插图。使用正式模板和规范 PDF 的桌面浏览器回归验证了该路径，结果 1 项通过、1 项按桌面范围跳过。该回归的终点是打开阻断详情并定位插图。
- **学校样例图形**　学校附件《阅读6》《阅读7》的正文“图4.1”均为 Word SmartArt。源文件的 SmartArt 标注和图题有效字号均可读为 10.5 磅。提交 `e955417` 修复显式无高亮值的解析，两份样例均可在本地完成文本与结构解析，后端全量回归 2754 项通过。单独保留图 4.1 和图题后，两个样例都通过源包安全检查，但现有导入均未保留 SmartArt，完整性对账正确阻断。
