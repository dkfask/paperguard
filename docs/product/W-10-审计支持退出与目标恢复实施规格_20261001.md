## 0. 本规格要解决什么

W-10 是 **C0 的集成收口包**。§24.2 把 **6 条 AT** 归给它，全部是

原设计阶段发现的是“表有了、关键路径未补齐”；本轮已补部分审计/AI 元数据路径，**不代表这 6 条 AT 已完整实现**。

## 1. 审计（W-10 / AT-29）

### 1.1 什么动作必须留痕

| 类别 | 动作 | 缺失后果 |
|---|---|---|
| 认证 | 登录失败、登出、改密、重置他人密码 | 无法追查账号盗用 |
| 授权 | 角色变更、成员停用、组织授权撤销 | **无法证明谁在什么时候拿到了什么权限** |
| 数据 | 导出、批量删除、批量修改 | 无法响应「谁导出了我们的数据」 |
| 跨租户 | 平台角色读取客户数据、支持访问 | 商业信任崩塌 |
| 计费 | 额度调整、权益变更（W-06/W-11） | 无法对账 |

### 1.2 三条硬约束

| # | 规则 | 说明 |
|---|---|---|
| AU-1 | 审计写入**不得**因业务失败而跳过 | 失败的操作**更要**留痕（否则攻击探测不可见） |
| AU-2 | 审计写入**不得**成为业务可用性的单点 | 审计库故障不得阻断业务；**宁可丢审计也不许丢业务**——但必须**告警** |
| AU-3 | 审计**只增不改不删**；更正只能追加一条反向记录 | 可改可删的审计等于没有审计 |

> **AU-2 的取舍必须写清楚**：审计与业务不可用同一个强一致通道。
> 若审计写失败导致业务回滚，攻击者只要打满审计表就能让业务全停——
> **这本身就是一种 DoS**。正确做法是**异步落审计 + 失败告警**，
> 并在 W-10 的运营手册里写明「审计缺口窗口」。

### 1.3 敏感字段不得入库（AT-29 前半）

`error-codes.md` 已有 EC-04 检查 message 泄漏；**审计记录**同样受约束：

| 禁止入库 | 替代 |
|---|---|
| 明文密码、初始凭据 | 凭据标识（哈希前 8 位 + 发放时间） |
| token / API key / BYOK 密钥 | 密钥指纹（`sk-****abcd`） |
| 文档正文、学生姓名、邮箱 | 对象 ID + 计数 |
| 支付签名、卡号 | 支付流水 ID |

> `tenant_invitations.token_hash`（W-02 §3.3）与成员初始凭据（W-05 §2 PW-2）
> 已确立「**只存 hash**」的形态，审计沿用同一标准——**不新造第三种**。

## 2. 支持授权（W-10 / AT-30）

### 2.1 `support_grants` 的四要素

W-02 §3.3 已定义表结构，本包只定**运行时规则**：

| # | 规则 | 判据来源 |
|---|---|---|
| SP-1 | 支持访问**必须**凭有效 `support_grant`（`expires_at > now()` 且 `revoked_at IS NULL`） | AT-30「过期/撤销/超范围立即拒绝」 |
| SP-2 | 授权**窗内**且仅限授权 `capabilities` 列出的范围 | AT-30「超范围」 |
| SP-3 | **必须**双人批准（`approvers` 至少 2 条） | W-02 §3.3 已有 `approvers` 字段 |
| SP-4 | 访问**与结束**都要留痕（AT-30 明文要求两端） | `revoked_at` + 审计 |
| SP-5 | **不得读取其他租户**——`tenant_id` 精确匹配，无「平台支持可见全部」的通配 | W-04 §2 L1 语义 |

> **SP-5 是最容易做错的一条**：支持人员天然要跨租户工作，
> 于是实现时很容易顺手加一条「支持角色可见所有租户」的策略——
> **那等于给了一个没有到期时间的超级管理员**。
> 正确形态是：支持访问**始终以某个具体 `support_grant` 为界**，
> 窗关即失效，**不存在「支持账号全局可见」这种状态**。

### 2.2 与平台角色的区别

W-03 §3.1 已分离平台角色（`platform_role_bindings`）与租户角色。
支持授权是**第三类**：

| 类别 | 范围 | 有效期 | 批准 |
|---|---|---|---|
| 平台角色 | 全平台 | 长期 | 一次性授予 |
| 租户角色 | 单租户 | 成员在职期间 | 租户管理员 |
| **支持授权** | **单租户** | **有 `expires_at`** | **双人批准** |

## 3. 退出、降级与安全暂停（W-10 / AT-31）

总设计要求「**商业限制保留合法退出；安全封禁不被导出绕过**」。

| 场景 | 数据访问 | 导出 | 说明 |
|---|---|---|---|
| 商业限制（欠费/降级） | **保留合法读取** | **允许** | 用户有权取回自己的数据 |
| 安全暂停（安全事件） | 阻断 | **必须拒绝** | 不得用导出绕过封禁 |
| 主动退出 | 阻断 | 允许 | **申请本身见 §3.1（`XR-1～XR-5`）**；申请获批后才进入 §4 的删除/导出 |

| # | 规则 |
|---|---|
| EX-1 | 商业限制**不得**阻断导出（阻断即违约） |
| EX-2 | 安全暂停**必须**阻断导出，且**阻断原因写审计** |
| EX-3 | 两者**不得**共用同一错误码（运营要能区分「欠费」与「安全」） |
| EX-4 | 降级**不删除**数据，只限制能力 |

> **EX-1 与 EX-2 表面矛盾，实为同一原则的两面**：
> **限制的目的是保护数据，不是惩罚用户。**
> 欠费的用户仍有权取回自己的数据；安全封禁的用户不得把数据带走。
> 把两者都做成「一律禁止导出」看似安全，实际是**用合规问题掩盖安全问题**——
> 欠费客户会投诉，安全事件会被推迟到走法律程序。

### 3.1 退出申请本身（XR-1～XR-5，2026-10-02 补）

> **为什么补这一节（INC-75）**：本节的 `EX-1～EX-4` 全部讲的是
> **「退出/降级/安全暂停发生后，导出怎么办」**，
> **没有一条讲「谁来申请退出、申请了之后走什么流程」**——
> 而总设计 §18.2 有 `POST /tenants/{t}/exit-requests`「创建退出申请」，
> 要求「所有者能力、审批流程」。**§3 的表格里「主动退出」一行写着「走 §4 删除申请」，
> 但 §4 的 `TD-1～TD-4` 讲的是导出/删除的**覆盖范围与 tombstone**，
> 同样不覆盖申请本身的规则。**于是这个端点既无规则、也无锚点。**

| # | 规则 | 可检验形式 | 说明 |
|---|---|---|---|
| **XR-1** | 创建退出申请**仅限租户所有者**（`owner` 能力），管理员及以上**不得代客户发起** | 非所有者调用 → 拒绝 + 审计 | 「客户主动退出」是**客户的权利**，代客发起会把退出变成平台单方动作 |
| **XR-2** | **同一租户同时只能有一个进行中的退出申请**；重复提交返回既有申请而非新建 | 连续两次提交 → 同一 `request_id` | 幂等，且避免两套并行流程互相矛盾 |
| **XR-3** | 退出申请**不立即触发数据删除**——它只是进入 §4 的删除申请流程，**生效时点由审批决定** | 创建后库行数不变 | **「申请退出」≠「数据已删」**；把两者混同会让审计与留存义务无从判断 |
| **XR-4** | 退出申请**不得被安全暂停阻断**（EX-2 阻断的是**导出**，不是**申请**）；但安全暂停期间**不得执行**删除 | 安全暂停期：申请可建、删除被拒 | 与 EX-1 同一原则：**限制的目的是保护数据，不是惩罚用户** |
| **XR-5** | 退出申请与其后触发的删除都必须写审计，**且不得伪造 `request_id` 或操作者** | 审计逐条可查 | 与 W-10 AU-2 的分工：**资金/删除路径必须强关联**，写失败即回滚 |

> **XR-1 与 XR-3 是两条最容易被实现反的规则**：
> 把 XR-1 做成「管理员也能代发起」会让平台可以在客户不知情时发起退出；
> 把 XR-3 做成「申请即删除」会让 §4 的 TD-2（必要历史证明必须保留）
> 与 TD-4（逻辑删除 + tombstone）**失去判断依据**——
> 因为已经不知道「删除」是什么时候被谁要求的。

## 4. 租户导出、删除与 tombstone（W-10 / AT-32）

| # | 规则 | 判据 |
|---|---|---|
| TD-1 | 租户级导出**仅覆盖批准范围** | AT-32「仅批准范围」 |
| TD-2 | 删除申请后，**必要的历史证明必须保留** | 审计与合规留存 |
| TD-3 | **已删除内容不得复活**——恢复时必须应用 tombstone | 总设计 §20.2；W-02 §3.3 `storage_objects.state` |
| TD-4 | 删除是**逻辑删除 + tombstone**，非物理清除 | 物理清除后无法证明「已删」 |

> **TD-3 是本包最容易出事的点**：备份恢复会把已删除的数据带回来。
> `storage_objects.state = 'tombstoned'` 就是为此存在——
> **恢复流程必须先应用墓碑，再让数据可见**。
> W-02 §3.3 已写明「备份恢复需应用 tombstone 以免已删内容复活」，
> 本包把它变成**可验证的判据**。

## 5. 目标恢复（W-10 / AT-33、AT-34）

总设计 §20.4 明确「**RPO/RTO 不承诺数值**」，本包遵守。

### 5.1 三代同源要求

| # | 规则 | 说明 |
|---|---|---|
| RS-1 | 数据库 + 对象存储 + 密钥**必须同代** | 恢复到不同代的密钥会解不开数据 |
| RS-2 | 恢复后**必须重新校验摘要** | 摘要不符即失败，不得「尽量用」 |
| RS-3 | 恢复后**必须重放撤权** | 恢复点之后的撤权在旧备份里不存在 |
| RS-4 | 恢复后**必须重放任务状态** | 否则已完成的副作用会被重复执行（W-09 ID-1） |

> **RS-3 最容易被忽略**：备份是**过去某时刻**的，
> 而那之后的撤权、封禁、成员停用**在备份里根本不存在**。
> 不重放就会把已撤权的权限恢复出来——**恢复动作本身成为越权窗口**。

### 5.2 单租户恢复的边界

| # | 规则 |
|---|---|
| SR-1 | **不覆盖**其他租户的数据 |
| SR-2 | **不回滚**外部效果（已发出的邮件、已调用的上游、已产生的支付） |
| SR-3 | **不回滚**财务事实（账务凭证属 W-11，跨恢复点的账必须人工对账） |

> **SR-2 是物理限制，不是纪律问题**：邮件已发出就无法收回。
> 因此恢复流程**必须**在 manifest 中标注「哪些副作用不可回滚」，
> 恢复后由人工确认，而不是指望系统自动处理。

| AC-10-10 | AU-2 | 审计库故障**不阻断业务**，且**产生告警** | 故障注入 + 告警记录 |
| AC-10-11 | — | **无任何生产写操作**；恢复演练仅在**隔离环境**且**不中断现网** | 操作日志 + 演练报告 |

> **AC-10-7 是 AT-28 在本包的落地部分**（§24.2 归 `W-09/10`）。
> W-09 §5 的 AR-1～AR-3 定义**任务侧**规则，本条负责**人工修复侧**：
> 人工恢复走的是流程而非调度器，**更容易跳过 manifest 核对直接信任现有产物**——
> 因此这里把它列为独立判据而不是引用 W-09。**三方拼合才构成完整 AT-28。**

> **AC-10-7 括号里的话是硬约束**：
> 总设计 §20.4 行第 984/986 明确「RPO/RTO **不承诺数值**」且「**不得为做演练中断现网**」。
> 证据文件里出现任何具体 RPO/RTO 承诺数字，都算判据未通过。

## 7. 门禁

| 检查 | 工具 | 守住什么 |
|---|---|---|
| 错误码登记一致性 | `error_codes_check.py` EC-01～EC-06 | EX-3 要求商业限制与安全暂停**不同码**；AT-30/31 的新码须登记 |
| 消息泄漏 | `error_codes_check.py` EC-04 | AU-3 的相邻约束（message 不含内部信息） |
| 逐表判定三方一致 | `schema_disposition_check.py` | `audit_events` 判为 sidecar（`db.py:353-364`）不得被误改为 tenant |
| 规格↔AT 归属与漏引 | `at_traceability_check.py` AT-10/AT-11 | 本表覆盖 §24.2 归 W-10 的全部 6 条 |

**本包暂不新增静态门禁**：AT-29～AT-34 全部是**运行时副作用与外部系统交互**判据
（审计是否真写了、恢复是否真应用了 tombstone、密钥是否同代），
静态检查一样都证明不了。

**唯一值得静态加的一项是 AC-10-2（敏感字段不得入库）**——
它可以对 `audit_events` 写入点做文本扫描。但这要求**先有写入点**（当前零命中），
现在加只会扫到空表并报绿。**留到实施后随第一批审计写入一起加。**

## 8. 明确不做
