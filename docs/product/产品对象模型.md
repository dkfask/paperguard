# PaperGuard 产品对象模型：模板、规范与教师要求

> 版本：v0.1  
> 日期：2026-09-08  
> 状态：产品设计建议，待评审  
> 关联文档：`多层级规范体系设计.md`、`商业产品设计方案.md`（均为本地设计稿，未纳入仓库）。

## 1. 设计目标

PaperGuard 不应把学校要求、论文排版模板和教师个人要求全部塞进一个 Word 模板。现实中的论文写作依据至少由以下几类对象组成：

- **论文模板**：规定文档的结构、版式、封面和导出结果。
- **写作规范**：规定论文应该如何写，包括字数、章节、参考文献、图表和提交要求。
- **教师要求**：针对课程、作业或指导关系增加的额外要求。
- **项目快照**：记录某一篇论文在创建或升级时实际采用的模板和规范版本。

核心原则：

> 模板负责“文档长什么样”，规范负责“论文怎么写”，教师要求负责“这次还要满足什么”，项目快照负责“这篇论文最终依据了哪个版本”。

## 2. 产品对象总览

```text
组织与范围
├── 学校
├── 学院/专业
├── 课程/批次
└── 教师/指导关系

写作依据
├── 论文模板 Template
├── 写作规范 PolicyDocument
├── 教师要求 RequirementSet
└── 规范包 PolicyBundle

写作过程
└── 写作项目 WritingProject
    ├── 模板快照
    ├── 规范快照
    ├── 教师要求快照
    ├── 检查结果
    └── 例外/豁免记录
```

产品上可以把“模板 + 学校规范 + 学院规范 + 教师要求”展示为一个**写作规范包**，但底层仍保留独立对象，避免排版、规则和权限相互耦合。

## 3. 核心对象定义

### 3.1 论文模板 Template

模板是现有 PaperGuard 的核心对象，负责结构化论文和 DOCX 导出。

模板应包含：

- 章节树、章节顺序和章节标识
- 章节是否必需、是否允许为空
- 字体、字号、中西文字体、行距、缩进和段前段后
- 页边距、页眉页脚、分页和目录布局
- 封面字段、封面静态文本和封面区块
- 导出时使用的源 DOCX 基底
- 学生是否可以增删或调整章节结构

模板不应直接承载以下内容：

- 摘要建议字数
- 参考文献最少数量
- 近几年文献比例
- 必须完成实验或调研
- 教师每周提交进度
- 课程截止时间

这些内容应放入写作规范或教师要求。

### 3.2 写作规范 PolicyDocument

写作规范是学校、学院、专业或其他管理主体发布的长期要求。它既可以作为供人阅读的 Markdown 文档，也可以包含机器可执行的结构化规则。

典型内容：

- 论文总体要求
- 摘要和关键词要求
- 正文字数要求
- 章节构成和内容说明
- 图表、公式和脚注要求
- 参考文献数量、年份和格式要求
- 查重、AI 使用和提交材料说明
- 无法自动判断的人工检查清单

建议支持以下文档状态：

```text
草稿 draft → 待发布 review → 已发布 published → 已停用 archived
```

已发布版本不可原地修改，修订必须产生新版本。

### 3.3 教师要求 RequirementSet

教师要求是教师针对课程、作业、指导关系或特定学生增加的要求集合。它与学校规范独立存在，不应修改学校规范原文。

建议支持三种作用范围：

| 类型 | 适用范围 | 示例 |
|---|---|---|
| 课程级 | 教师课程下的全部学生 | 本课程论文正文不少于 5000 字 |
| 作业级 | 某一次作业或某个阶段 | 第三次作业必须完成实证分析 |
| 个性化 | 某个学生或论文项目 | 研究对象限定为某地区企业 |

教师要求可以由以下内容组成：

- 结构化规则：字数、关键词数量、参考文献数量、必填章节
- 自定义条目：自由文本 + 严重级别
- 参考文档：Markdown、PDF 或示例文件
- 截止时间和阶段安排
- 对某条规则的补充说明

教师要求不能绕过后端权限，也不能默认放宽学校的硬性要求。需要例外时，应通过豁免流程留下审批记录。

### 3.4 写作规范包 PolicyBundle

规范包是面向用户的组合视图，不一定是唯一的持久化实体。

一个项目的规范包可能是：

```text
学校：XX大学
学院：经济学院
专业：金融学
论文模板：金融学本科论文模板 v3
学校规范：本科论文写作规范 v2026.1
学院补充：经济学院论文补充规定 v2026.1
教师要求：金融计量课程论文要求 v1
项目约定：导师确认的特殊要求 v1
```

规范包用于：

- 项目创建时选择写作依据
- Writer 页面展示当前要求来源
- 检查结果按来源分组
- 导出或提交时生成合规摘要
- 规范版本更新时展示差异

底层仍应保留每个模板和规范的独立版本。

### 3.5 写作项目 WritingProject

写作项目是学生实际编辑的论文工作空间，必须保存写作依据的版本快照。

项目至少关联：

- `template_id` 与模板版本快照
- 学校/学院/专业规范版本
- 教师要求版本
- 当前有效规则的解析结果
- 检查报告和检查引擎版本
- 项目级特殊约定和豁免记录

项目不能只保存规范文件名。必须保存版本号、内容摘要值或完整快照，保证历史结果可复现。

## 4. 模板与规范的边界

判断一项要求应放在哪里，可以使用以下规则：

| 需求 | 对象 |
|---|---|
| 一级、二级标题结构 | 模板 |
| 字体、字号、行距、缩进 | 模板 |
| 页眉页脚、封面布局、目录布局 | 模板 |
| 摘要建议字数 | 写作规范 |
| 参考文献格式说明 | 写作规范 |
| 必须包含研究方法 | 专业规范或教师要求 |
| 本次作业必须引用 10 篇近五年文献 | 教师要求 |
| 本篇论文允许不写某章节 | 项目级例外，并需要审批 |
| 学生题目、研究对象和指导教师 | 项目元数据 |
| 论文提交截止时间 | 批次/阶段要求或作业要求 |

如果一条要求会改变 Word 的排版结果，优先考虑模板；如果一条要求主要判断论文内容是否达标，优先考虑规范规则。

## 5. Markdown 文档格式建议

Markdown 适合保存写作规范和教师要求。建议使用 YAML frontmatter 保存系统元数据，正文保存面向用户的说明。

### 5.1 学校规范示例

```md
---
title: 本科毕业论文写作规范
kind: school_policy
scope: university
organization_id: school-001
status: published
version: 2026.1
effective_from: 2026-09-01
applies_to:
  degree_levels:
    - undergraduate
  majors:
    - all
---

# 一、论文基本要求

本科毕业论文应围绕明确的问题展开，正文建议不少于 8000 字。

# 二、摘要要求

中文摘要建议控制在 300-500 字之间。

# 三、参考文献

参考文献按照学校规定的顺序编码制格式编排。
```

### 5.2 教师要求示例

```md
---
title: 研究方法课程论文要求
kind: teacher_requirement
scope: course
course_id: research-methods-2026
teacher_id: teacher-001
status: published
version: 1
effective_from: 2026-09-01
---

# 额外要求

1. 必须包含研究问题和研究方法章节。
2. 正文不少于 5000 字。
3. 至少引用 10 篇近五年的文献。
4. 不接受纯综述型论文。
```

### 5.3 机器可执行规则

自然语言说明和机器检查规则应明确区分。规则可以先放在 frontmatter 中，后续再迁移到独立结构化存储。

```yaml
rules:
  - id: body-word-count
    type: word_count
    target: body
    min: 5000
    severity: error
    enforce: hard

  - id: reference-count
    type: reference_count
    min: 10
    severity: warning
    enforce: soft

  - id: required-method-section
    type: section_exists
    section_key: methodology
    severity: error
    enforce: hard
```

建议规则属性至少包括：

- `id`：规则稳定标识
- `type`：检查器类型
- `target`：全文、章节或封面字段
- `params`：阈值和参数
- `severity`：错误、警告或建议
- `enforce`：硬性要求或可覆盖建议
- `description`：面向用户的解释
- `source`：规则来源

Markdown 可以作为录入和阅读格式，但不能只依赖大模型从自然语言猜出合规结论。机器检查应依赖显式规则。

## 6. 规范继承与冲突处理

建议采用以下层级：

```text
国家标准内置规则
  < 学校规范
  < 学院/专业规范
  < 批次/课程/作业要求
  < 教师要求
  < 项目特殊约定
```

规则合并建议：

1. 同一个检查目标出现多条规则时，默认采用更严格的阈值。
2. `hard` 规则不能被下级要求放宽。
3. `soft` 规则允许被下级要求覆盖，但必须显示覆盖来源。
4. 无法比较严格程度的冲突，应保留全部来源并提示人工确认。
5. 任何例外都生成豁免记录，不删除原规则。

检查结果应明确显示来源，例如：

```text
正文少于 5000 字
来源：研究方法课程论文要求 v1
级别：错误
实际值：4200 字
期望值：不少于 5000 字
```

## 7. 版本与项目快照

项目创建时冻结当前适用的写作依据：

```json
{
  "template_snapshot": {
    "template_id": "template-001",
    "version": "3",
    "content_hash": "sha256:..."
  },
  "policy_snapshots": [
    {
      "policy_id": "school-policy-001",
      "version": "2026.1",
      "content_hash": "sha256:...",
      "rules": []
    },
    {
      "policy_id": "teacher-policy-009",
      "version": "1",
      "content_hash": "sha256:...",
      "rules": []
    }
  ],
  "resolved_rules": [],
  "snapshot_created_at": "2026-09-08T00:00:00Z"
}
```

规范后续更新时，不应静默影响正在写作的项目。应提供：

```text
发现新版本规范
[查看变化] [暂不更新] [应用到本项目]
```

升级前展示旧版本与新版本的差异，升级后记录操作者、时间、原因和受影响范围。历史检查报告继续绑定旧快照。

## 8. 权限建议

| 角色 | 权限 |
|---|---|
| 学校管理员 | 管理学校模板和学校规范，发布版本，设置适用范围 |
| 学院/专业管理员 | 管理本学院或专业补充规范，不能放宽学校硬性要求 |
| 指导教师 | 创建课程、作业和指导关系下的教师要求 |
| 学生 | 查看适用规范和教师要求，不能修改正式要求，可提出异议 |
| 平台运维 | 维护系统，不因运维身份自动获得论文正文访问权限 |

教师要求默认只对以下人员可见：

- 该教师名下的学生
- 具备相应范围的管理员
- 经过授权的审核人员

学校规范通常可以面向全校用户公开。

## 9. Writer 页面建议

写作页应让学生在写作过程中看到规范，而不是只在导出时检查。

建议增加“当前写作依据”面板：

```text
当前写作依据
├── 论文模板：金融学本科论文模板 v3
├── 学校规范：本科论文写作规范 v2026.1
├── 学院补充：经济学院论文补充规定 v2026.1
└── 教师要求：金融计量课程论文要求 v1
```

检查结果按来源分组，显示：

- 规则描述
- 实际值与期望值
- 章节或字段位置
- 来源和版本
- 严重级别
- 是否可自动修复
- 是否已豁免

在以下场景展示规范：

| 场景 | 交互 |
|---|---|
| 进入项目 | 展示本项目适用规范包和版本 |
| 选中章节 | 显示该章节相关字数、结构和内容要求 |
| 实时检查 | 按来源显示错误、警告、建议和未检查项 |
| 导出前 | 硬性未完成项阻止导出，软性问题给出提醒 |
| 提交/送审 | 生成绑定规范快照的合规报告 |

## 10. 建议的数据对象

在现有 `PaperTemplate` 和 `WritingProject` 之上，可以逐步引入以下逻辑对象：

| 对象 | 关键字段 | 说明 |
|---|---|---|
| `PolicyDocument` | id、title、kind、scope、owner、status、version、markdown_content | 面向人阅读的 Markdown 规范文档 |
| `RequirementSet` | id、层级、归属、状态、生效区间、版本 | 一组可绑定的要求 |
| `RequirementItem` | set_id、type、target、checker、params、severity、enforce | 单条可检查或人工要求 |
| `PolicyBinding` | policy_id、scope_type、scope_id、priority | 将规范绑定到组织、课程、批次或教师 |
| `PolicyBundle` | template_id、policy_ids、requirement_set_ids | 面向项目创建和展示的组合 |
| `ProjectPolicySnapshot` | project_id、版本列表、解析规则、冻结时间 | 项目实际采用的不可变依据 |
| `Waiver` | project_id、item_id、申请人、复核人、理由、生效期 | 规则例外和豁免留痕 |
| `CheckRun` | project_version_id、snapshot_id、engine_version、result | 可复现的检查运行记录 |

第一阶段可以继续使用项目 JSON 保存快照，后续再把需要查询和统计的字段拆成独立表。

## 11. 分阶段落地建议

### P0：规范可见

1. 支持 Markdown 规范上传、编辑、预览和版本管理。
2. 新增学校规范和教师要求的基本对象。
3. 项目创建时绑定规范并保存版本快照。
4. Writer 页面展示当前规范包和规范来源。
5. 导出或提交时显示采用的模板与规范版本。

### P1：结构化检查

1. 支持正文、摘要、关键词和参考文献数量规则。
2. 支持必填章节和必填封面字段规则。
3. 统一模板检查与规范检查报告。
4. 报告中显示来源、版本、严重级别和未检查项。
5. 支持教师自定义要求和简单豁免流程。

### P2：组织与协作

1. 支持学校、学院、专业、课程和批次作用域。
2. 支持规范自动匹配和冲突检测。
3. 支持规范生效时间、批量升级和差异预览。
4. 支持学生阅读确认、教师发布记录和管理员审计。
5. 支持人工检查清单与教师反馈闭环。

## 12. 与现有代码的对应关系

当前代码已有以下可复用基础：

- `PaperTemplate` 已包含章节、样式、封面和源 DOCX。
- `WritingProject.template_snapshot` 已提供项目创建时冻结模板的基础。
- `project_check.py` 和 `template_compare.py` 可作为统一检查报告的扩展点。
- `frontend/src/views/TemplateEditor.vue` 可扩展模板关联规范的入口。
- `frontend/src/views/Writer.vue` 可增加规范面板、来源标签和检查结果分组。
- `frontend/src/api.js` 可增加规范文档、版本、绑定、发布和快照接口。

建议新增或扩展：

```text
backend/app/models/policy.py
backend/app/api/policies.py
backend/app/services/policy_parser.py
backend/app/services/policy_resolver.py
backend/app/services/policy_snapshot.py
frontend/src/views/Policies.vue
frontend/src/views/PolicyEditor.vue
```

第一阶段不必一次完成学校、学院、专业和批次的完整组织模型。可以先支持“全局/学校规范 + 教师要求”两档，验证产品流程后再扩展作用域。

## 13. 评审时需要确认的问题

1. 教师要求绑定到教师个人，还是绑定到“教师-学生指导关系”？
2. 学校硬性要求是否允许学院管理员申请例外？审批人是谁？
3. 字数口径如何定义：中文按字符，英文按单词，是否含标点、空格和公式？
4. 参考文献年份解析失败时，是报错、警告还是标记为未检查？
5. 项目创建后规范升级是自愿、强制还是按批次截止时间决定？
6. 教师要求是否需要学生阅读确认？
7. Markdown 是否允许上传附件，附件是否纳入项目快照和归档？
8. 导出 DOCX 是否附加规范合规摘要页？
9. 哪些规则可以自动修复，哪些规则只能提示不能代写？
10. P0 是否先只实现学校规范和教师要求，学院/专业/批次放到后续阶段？

## 14. 结论

PaperGuard 最终应采用以下对象边界：

```text
学校/学院/专业规范
  ├── 规则与说明
  └── 适用范围和版本

教师/课程/作业要求
  ├── 额外规则
  └── 教学或指导要求

论文模板
  ├── 章节结构
  ├── 版式样式
  └── DOCX 导出布局

写作项目
  ├── 当前论文内容
  ├── 模板快照
  ├── 规范快照
  ├── 检查报告
  └── 例外与审核记录
```

最值得优先实现的是：**Markdown 规范文档 + 版本管理 + 项目快照 + Writer 展示**。这四项可以先解决不同学校和教师要求并存的问题，也为后续自动检查、教师协作和规范升级打下稳定基础。
