## 0. 本规格要解决什么

W-02 交付了**存储目标规格与离线工具**（目标授权表、RLS 策略、回填器），不代表这些表/策略已部署。W-02 §10 明确交接：

> 若代码仍读 `users.role`，则**A 校教师切到 B 校时角色不随租户变**——
> 正是 W-03 完成定义里「同账号双租户不同角色不串权」要防的事。

### 1.1 既有 `core/context.py` 的现状（局部验证通过，完整门禁仍 GAP）

`backend/app/core/context.py` **已存在**一个 `frozen=True` 的 `RequestContext`，
以及 `context_for_user()` 构造器 + `ContextVar` 存取。**这不是从零开始**，但它**只覆盖**本规格的安全子集：

| 维度 | 现有 `core/context.py` | 本规格 §2.1 要求 | 差距 |
|---|---|---|---|
| 字段 | 已含 `actor_kind`、`trace_id`、`support_grant_id` 与租户/成员/版本 | 完整成员/组织/支持来源协议 | 字段存在不等于来源协议完成 |
| `role` 来源 | member 读真实成员角色；platform 是明确的平台身份；unresolved 不保留任何角色 | 完整成员角色/平台角色协议 | 125 处旧角色读取仍在；当前扫描也包含成员角色读取，需逐点迁移/裁决，不能以扫描数直接量化全部越权路径 |
| 组织范围 | 可信上下文不采用全局用户组织提示，成员组织范围暂为空 | 来自 `membership_org_grants` | 授权表/流程未实现，不能猜授组织权限 |
| 不变量 | frozen + `__post_init__`，中性默认值；CI-1/2/4/5 有正反例，CI-3 全量拒绝 support | CI-1～CI-5 | 拒绝未验证支持身份不等于有效支持授权已实现 |
| 解析函数 | `resolve_request_context` + 异步 `trusted_context`，S0→S4 / E1～E7 | 完整租户上下文协议 | draft 暂无首位所有者例外；仅 SaaS 切片走新依赖，旧业务仍分开 |

**因此 W-03 是「扩展 + 改造既有类」，不是「新建一个类」。**
两条互斥的做法必须避免：保留两个同名 `RequestContext`（必然混用），
或新建平行类而不改 `core/context.py`（旧路径继续读全局 `role`，隔离失效）。

> `core/context.py` 的 docstring 已声明「只含标识与控制元数据，
> 绝不存请求正文、文档正文、bearer token 或 API key」——
> **该边界继续有效**，扩展字段时不得引入任何业务内容。

## 2. RequestContext：不可变值对象

### 2.1 字段与不变量

```python
# 扩展 backend/app/core/context.py 既有类（见 §1.1），不是新建平行类
@dataclass(frozen=True)                       # 既有已 frozen=True，保留
class RequestContext:
    # —— 既有字段，语义不变 ——
    actor_id: str                             # = user_id
    organization_ids: tuple[str, ...]          # 保留但改由服务端确认填充
    school_id: str
    request_id: str
    locale: str = "zh-CN"
    timezone: str = "Asia/Shanghai"
    role: str = ""                            # ⚠ 语义变更：改为「本租户内角色」
    # —— 新增租户字段 ——
    trace_id: str = ""                        # 服务端受控关联
    tenant_id: str | None = None              # 平台路径可为 None（CI-2）
    membership_id: str | None = None
    capabilities: frozenset[str] = frozenset()
    auth_version: int | None = None
    support_grant_id: str | None = None
    actor_kind: Literal["member", "platform", "support", "unresolved"] = "unresolved"
    def __post_init__(self):
        # CI-1 member ⇒ tenant_id/membership_id/auth_version 非空
        # CI-2 platform ⇒ tenant_id 必须为 None
        # CI-3 support ⇒ support_grant_id 非空且未过期未撤销
        # CI-4 capabilities / organization_ids 在生命周期内不可变
        # CI-5 unresolved ⇒ 这是未解析的**空上下文**，任何授权入口都必须拒绝它
        ...
```

> **`role` 字段的语义变更是本包最危险的一处**。
> 保留字段名是为了不破坏既有调用点，但**含义**从「全局用户角色」变为
> 「当前租户内的角色」。迁移期**必须**同时存在一个开关标记迁移进度，
> 否则无法判断某个调用点读到的是旧语义还是新语义。

**五条不变量**（`__post_init__ 断言，违反即 500 而非放行）：

| # | 不变量 | 为什么 |
|---|---|---|
| CI-1 | `actor_kind="member"` ⇒ `tenant_id`、`membership_id`、`auth_version` **均非空** | 三者缺一就无法定位授权 |
| CI-2 | `actor_kind="platform"` ⇒ `tenant_id` **必须为 None** | 平台身份天然跨租户；带上 tenant 反而会让平台查询被 RLS 过滤成 0 行 |
| CI-3 | `actor_kind="support"` ⇒ `support_grant_id` **非空且未过期未撤销** | 支持访问必须有可追溯的授权凭据 |
| CI-4 | `capabilities` 与 `organization_scope` **在生命周期内不可变** | 防止服务层中途提权（可变上下文 = 可被中间件改写） |
| CI-5 | `actor_kind="unresolved"` ⇒ 这是**尚未解析出任何身份的空上下文**，**任何授权判断入口必须拒绝它** | 模块级 `ContextVar` 的默认值必须是合法实例（否则 import 期即崩），但**合法 ≠ 可用于授权**。中性取值把「能构造出来」与「可被信任」彻底分开 |

> **CI-2 的实际后果**：平台查询**不能**靠 `SET LOCAL app.tenant_id` 实现。
> RLS 策略里 `tenant_id = nullif(current_setting('app.tenant_id', true), '')`
> 在未设置时永不为真——平台路径必须走 W-02 §3.6.3 ① 的 `pg_read_all_data` 策略 + 独立连接，
> **不能**靠设置一个魔法 tenant_id 通配。**这是 W-03 与 W-04 必须提前对齐的接口。**

本轮来源提交：`d87679896285a5b61302a98181f03621adffb38d`；离线证明见 `test_request_context_contract.py`、`test_ai_recovery_contract.py`，不代表共享 SaaS 全量放行。

### 2.2 默认 `actor_kind` 的取值：裁决记录（2026-10-03）

**本条曾长期挂着「待裁决」，现已裁决。** 成因是规格自身的一处互斥：
`backend/app/core/context.py` 用 `ContextVar("...", default=RequestContext())`，
**默认值在 import 期构造**；而 §2.1 同时要求 ① `actor_kind` 默认 `"member"`
② CI-1「member ⇒ `tenant_id`/`membership_id`/`auth_version` 非空」
③ 沿用现有 `ContextVar` 默认值。**三者不可同时满足**——
按原文字面实施，后端会在 import 期就抛 `AssertionError`（已实测，见总设计 INC-107）。

**裁决：采用中性取值 `"unresolved"`**（即上面的 `Literal` 第四个成员）。

| 方案 | 内容 | 结论 |
|---|---|---|
| **(a) 中性 `actor_kind`** | 默认值改为 `"unresolved"`，`Literal` 改宽；CI-1 只对 `"member"` 生效，空默认值天然不触发 | **✅ 采纳**。改动面最小，且**把「能构造出来」与「可被信任」彻底分开** |
| (b) 默认值 `None` | `ContextVar` 不给默认，所有读取点处理 `None` | 未采纳：改动面扩到**全部读取点**，风险最高 |
| (c) 断言降级为警告 | 不改规格语义，只在非默认实例上断言 | 未采纳：会让「空上下文非法」这条不变量**失去可执行性** |

**采纳 (a) 的安全前提是 CI-5**：`"unresolved"` **只保证能构造，不保证可授权**。
任何授权判断入口必须显式拒绝它——**否则中性默认值就变成了一个万能匿名身份**。
因此 CI-5 是本裁决的**组成部分，不是补充**。

> **实施注意**：`actor_kind` 的读取点不得把 `"unresolved"` 落进
> `member` / `platform` / `support` 任一分支；三值之外的第四态必须在类型层面
> 被看见（`Literal` 已保证），而不是靠 `else` 兜底。


### 2.2 解析状态机（总设计 §8.1 的可执行化）

```
                    ┌──────────┐
   请求进来 ────────▶│ S0 会话   │── 失败→ E1
                    └────┬─────┘
                         ▼
                    ┌──────────┐
                    │ S1 账号门禁│── 失败→ E2
                    └────┬─────┘
                         ▼
                    ┌──────────┐
                    │ S2 成员/  │── 失败→ E3 / E4 / E5
                    │   支持授权 │
                    └────┬─────┘
                         ▼
                    ┌──────────┐
                    │ S3 租户状态│── 失败→ E6
                    └────┬─────┘
                         ▼
                    ┌──────────┐
                    │ S4 构造   │  构造 RequestContext
                    │  上下文  │  （CI-1～CI-4 断言）
                    └──────────┘
```

**顺序不可调换**。特别是 S2 在 S3 之前：必须先确认**这个人在这个租户有身份**，
再去判断**这个租户是否可用**。反序会让「已停用租户」被当成「无权限」，
掩盖真实的停用原因（总设计要求区分二者）。

### 2.3 七个失败出口（每出口一个独立错误码）

| 出口 | 触发条件 | HTTP | 错误码 | 是否可重试 |
|---|---|---|---|---|
| **E1** | 无会话 / 会话过期 | 401 | `AUTH_SESSION_INVALID` | 是（重新登录） |
| **E2** | 账号被停用/锁定/需改密 | 403 | `AUTH_ACCOUNT_BLOCKED` | 否（须人工或改密） |
| **E3** | 有效会话但**不是该租户成员** | 403 | `TENANT_MEMBERSHIP_REQUIRED` | 否（换租户或申请加入） |
| **E4** | 是成员但 `status ≠ 'active'`（`invited`/`suspended`/`left`） | 403 | `TENANT_MEMBERSHIP_INACTIVE` | 否 |
| **E5** | 请求携带了无法兑现的 `X-Expected-Tenant` | 403 | `TENANT_HEADER_NOT_HONORED` | 否 |
| **E6** | 租户 `status ∈ ('suspended_security','closing','closed')` | 403 | `TENANT_NOT_ACTIVE` | 否（等恢复） |
| **E7** | 租户 `status = 'draft'` 且请求方**不是**待设置的首位所有者、且端点**不属于**启用/邀请/组织准备 | 403 | `TENANT_NOT_ACTIVE` | 否（完成启用） |

> **E6 / E7 的状态取值在 2026-10-01 修正（INC-59）**：原 E6 写
> `status ∈ ('suspended','closed')`，与总设计 §12.1 的 `suspended_security` **命名分歧**，
> 且**漏掉 `closing`**（§12.1 的退出中状态）。同时 `draft` 原先**没有任何出口覆盖**：
> §12.1 的 `draft` 行只允许「首位所有者设置与启用检查」，但四个既有出口
> （E1～E5）全部不检查租户状态，**已接受邀请的首位所有者会拿到 draft 租户的全部权限**——
> 正式教学发布、平台 AI、收费三项禁止行为一个都拦不住。

> **E7 与 E6 必须分开**。E6 是「这个租户已经不在正常服务中」，
> E7 是「这个租户还没准备好对外服务」。合并成一个出口后，
> 运营分不清「该等恢复」与「该去完成启用」——而这两种情况的处置动作完全不同。

> **E7 不是「draft 租户对所有人关闭」**：首位所有者必须能进入并完成启用，
> 否则客户建好却永远启用不了。判据是**身份 + 端点**，不是状态一刀切。

> **E3 与 E4 必须分开**。两者都是 403，但 E3 是「你不在这里」，
> E4 是「你曾在这里但已被停用」——合并会让运营看不出是**授权问题**还是**执行问题**。
> `error-codes.md` 需登记这 4 个新码（当前已登记 31 个实现 + 16 个目标占位）。

### 2.4 禁止回退（总设计 §8.1 明文）

> 「没有上下文的客户资源调用不得回退到"全平台查询"」

**落地为两条硬规则**：

- **R-1**：服务层函数的 `ctx: RequestContext` 为**必填位置参数**，不得提供默认值。
  Python 无法在类型层强制，改由**门禁**（见 §6）AST 静态检查。
- **R-2**：任何客户资源 Repository 的 SQL **必须**带 `tenant_id = :ctx.tenant_id` 条件。
  W-02 的 RLS 是**第二道**防线——**不能**用它替代第一道。
  RLS 拦截时返回 0 行（静默），而应用层漏条件在 RLS 未覆盖的表上会**返回全量**。

## 3. 角色模型：从全局单值到平台/租户分离

### 3.1 两套角色，互不替代

| 维度 | 平台角色 | 租户角色 |
|---|---|---|
| 存储 | `platform_role_bindings(user_id, platform_role)`（W-02 §3.3） | `membership_roles(tenant_id, membership_id, role_code)`（W-02 §3.2） |
| 取值 | `owner` / `billing` / `support` | `tenant_admin` / `teacher` / `student` / … |
| 作用域 | 全平台 | **单个租户** |
| 取用 | `require_platform_admin` | `capabilities`（由 `membership_roles` + `membership_org_grants` 派生） |

> **迁移期映射不是一对一**。现有 `admin` **同时**被当作平台管理员和租户管理员使用，
> 而 W-02 §3.2 规则 2 明确「**旧 `admin` 不自动映射为 `platform_role_bindings`**」（Q-09 待裁决）。
> 因此迁移期 `admin` 的含义是**未定义的**，必须显式裁决，不能靠映射表猜。

### 3.2 `auth_version` 撤权语义

总设计 §8.1 行 312：

> 成员权限变更递增 `auth_version`，旧权限缓存失效；短时缓存不延迟高风险撤权。

**落地规则**：

| # | 规则 | 说明 |
|---|---|---|
| AV-1 | 能力**只在请求入口**从 `membership_roles`/`membership_org_grants` 派生一次，写入 `RequestContext` | 服务层**不得**自行查库取权限（否则 `CI-4` 不可变语义被破坏） |
| AV-2 | 撤权操作（改角色/停用成员/改组织授权）**在同一事务内**递增 `auth_version` 并失效缓存 | 先递增后失效，顺序反了会出现「已撤权但旧缓存仍可用」的窗口 |
| AV-3 | `auth_version` 校验**不得**完全依赖缓存 | 高风险操作（导出、删除、成员管理、密钥读取）必须回源比对 |
| AV-4 | 缓存 TTL **上限 60 秒**，且撤权事件**主动**失效（不靠 TTL 兜底） | TTL 是兜底，不是机制；靠 TTL 兜底等于允许 N 秒的越权窗口 |

> **AV-4 的 60 秒是上限不是目标**。若 C0 试点规模允许，
> 更好的做法是撤权时**主动广播失效**（Redis pub/sub 或版本号比对），
> 把窗口压到接近 0。60 秒是**无额外基础设施时的兜底值**，必须在 W-10 审计中如实标注。

### 3.3 最后所有者保护（AC-03-6 / AT-12）

**规则 LO-1**：一个租户**不得**因为成员操作而失去**全部**平台/租户管理员。

触发拒绝的三种操作：撤销最后一名 `tenant_admin` 的角色、停用最后一名管理员、
删除最后一名管理员所在的成员关系。

| 情形 | 处置 |
|---|---|
| 租户已无管理员 | 拒绝该操作，返回独立错误码（`TENANT_LAST_OWNER`，占位待登记） |
| 租户仍有其他管理员 | 允许，正常递增 `auth_version` |
| 平台侧强制吊销整租户 | **不走本规则**——那是 `tenants.status='closed'` 路径（§2.3 E6），与成员操作无关 |

> **必须区分「成员操作」与「平台吊销」**。若把强制吊销也纳入 LO-1，
> 平台就永远无法关闭一个已无人管理的租户——**保护机制反而成了业务阻塞点**。
>
> **判定必须在事务内完成**（`SELECT ... FOR UPDATE` 锁住成员集合后再判定），
> 否则并发撤权两个管理员可能各自看到「还有一个」而双双成功，**最后一名被撤光**。
> 这与 W-02 §7 并发项 11（`auth_version` 并发递增不得丢失更新）是同一类竞态。

## 4. 双租户标签与异步任务

总设计 §8.1 行 310-311 的两条约束：

### 4.1 双标签不串权（AT-01）

| # | 规则 | 实现含义 |
|---|---|---|
| DB-1 | **不使用**「全局当前租户」会话变量 | 总设计明文「避免依赖可被多个浏览器标签覆盖的全局当前租户」；用**显式租户路径**（`/t/{tenant_id}/...`） |
| DB-2 | 切换租户时前端**清空**正文缓存、临时文件引用、订阅与请求结果 | 缓存键必须带 `tenant_id + membership_id`（总设计行 309） |
| DB-3 | 服务端**重新确认**成员关系，不信任 URL/Header/域名 | 总设计行 306：这些「只提出目标租户」 |
| DB-4 | 后端任何进程内状态**不得**缓存「当前租户」 | 进程内单例在多标签并发下必然串权 |

### 4.2 异步任务不继承上下文

| # | 规则 | 理由 |
|---|---|---|
| AS-1 | worker **从任务记录自身**读取 `tenant_id`，不继承上一次任务的上下文 | 总设计行 311；worker 复用连接/内存，继承 = 串租户 |
| AS-2 | 派发时把 `tenant_id` + `membership_id` + `auth_version` **写入任务记录** | 与 W-02 §19.1 契约字段（`resource_version` 等）同批落地 |
| AS-3 | 消费前**重新校验** `auth_version`，与当前值不符则**拒绝执行** | 任务排队期间成员可能已被撤权；总设计行 620 要求「派发前再次核对有效成员、auth_version」 |
| AS-4 | 任务上下文与请求上下文**类型不同**，不得复用同一 dataclass | 语义不同：请求上下文是「此刻」，任务上下文是「派发时」；混用会让撤权语义失效 |

> **AS-3 是最容易漏的一条**。只在派发时校验是不够的——
> 任务在队列里可能等待数分钟，此时撤权已发生。
> 这是 W-09 的前置条件，**必须与 W-09 一起设计**，不能只留给 W-09。

## 6. 门禁

`docs/tenancy/tools/context_resolution_check.py` 做四项静态核对：

| 编号 | 检查 | 为什么静态可查 |
|---|---|---|
| **CR-1** | frozen + CI-1～CI-5 不变量；CI-3 当前仅 fail-closed | 装饰器/断言 + 构造、深度不可变和中性默认值行为检查 |
| **CR-2** | 解析函数按 S0→S4 顺序出现七个失败出口 E1～E7 | 函数体 AST 控制流 |
| **CR-3** | 服务层函数**无默认 `ctx` 参数** | 函数签名默认值 |
| **CR-4** | 旧 `users.role` 的**非测试引用点已清零**（或被显式隔离） | AST 引用计数 |

**CR-4 是本规格的关键闸门**：只要代码还在读全局 `users.role`，
「同账号双租户不同角色不串权」就**不可能**成立。门禁必须能报出还剩几处。
