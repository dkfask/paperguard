## 0. 本规格要解决什么

W-06 负责一件事：**把「这个租户现在能用什么、还能用多少」从散落在环境变量里的隐含假设，变成有版本、可冻结、可核对的显式数据。**

§24.2 把 **3 条 AT** 归给它（AT-09 席位部分、AT-14、AT-15），
而这三条的共同点是：**都在问「边界在哪里」，不在问「功能有没有」。**

本轮代码取证的结论比 W-03/04/05 更硬：**不是「实现得不够细」，是「一个对象都不存在」**。

## 1. 权益对象模型（PV）

### 1.1 七个对象与各自的失效方式

§9.3 已给出字段建议，本节补**每张表最容易被做错的地方**——
即「表建出来了，但仍然会被用错」的具体形态。

| 对象 | 最容易做错的地方 | 正确做法 |
|---|---|---|
| `plan_versions` | 发布后改 `features`/`quota_definition` | **发布后不可覆盖**；改内容必须发新 `version` |
| `contracts` | 用它当「有没有付费」的唯一判据 | C0 它只是**试点服务记录**，不能成为扣款依据 |
| `subscriptions` | 允许同一租户存在两条「当前有效」 | 「当前有效范围不得产生冲突的服务关系」须由**唯一约束**保证，不是靠查询时过滤 |
| `entitlement_grants` | 前端直接改 `limit` | 「变更产生新版本与审计，**不凭前端修改**」 |
| `quota_periods` | 查询时现算周期 | 周期边界**先落库再使用**（§3） |
| `budget_policies` | 把次数/token/货币成本混在一个字段 | 「指明是次数、token 还是货币成本，**不混用**」 |
| `tenant_settings` | 往里塞正文或明文秘密 | 「不包含正文或明文秘密；**显式继承规则**」 |

### 1.2 计划版本规则

| # | 规则 | 理由 |
|---|---|---|
| PV-1 | `plan_versions` 发布后**任何字段不可改**；变更必须新增 `version` 行 | 停售不修改历史服务关系——历史用量引用的是当时的价格与权益 |
| PV-2 | 同一 `plan_code` 的 `version` 唯一；`state` 至少含 `draft`/`published`/`retired` | 只有 `published` 可被 `subscriptions` 引用 |
| PV-3 | `retired` 计划**不得**被新订阅引用，但**已有订阅继续按原版本执行到周期末** | 停售不等于立即失效 |
| PV-4 | 生效权益值**只能来自单一有效版本**；禁止「多行相加推导无限额度」 | §12.2 明确要求——多行相加是额度无限增长的典型来源 |
| PV-5 | 权益合并顺序固定并可测：**合同批准覆盖 > 限期赠予 > 计划版本默认值** | §12.2「必须有确定的合并规则」；顺序必须写死，否则同一租户两次解析出不同权益 |
| PV-6 | 每次权益解析必须**记录所用版本号**（`plan_version_id` + `entitlement_version`）到使用现场 | 事后必须能回答「这次调用当时按哪个版本放行的」 |

> **PV-4 与 PV-5 是一对**：
> PV-4 禁止「多行相加」，PV-5 规定「多来源如何覆盖」。
> 只写 PV-4 不写 PV-5，实现者会退化成「取最大 limit 的那行」——
> 那不是合并规则，是**取巧**。

### 1.3 C0 的非付费边界

§12.3：「C0 允许平台人工批准非付费试点权益，记录原因、期限、批准人和版本；
**不生成虚假现金充值**。」

| # | 规则 |
|---|---|
| PV-7 | C0 **不创建** `billing_accounts`、不写 `journal_entries`、不产生任何 `currency` 非空值 |
| PV-8 | 试点权益必须记录 `reason` / `expires_at` / `approved_by` / `version`；`expires_at` 为空即**不予批准** |
| PV-9 | 「无批准不赠货币额度」（D-04）——C0 的赠予只能是**非货币资源**（席位、AI 次数、存储字节） |

## 2. 席位（SL）

C0 完全从零新建。§12.2：「席位 = 学生、教师、管理员人数或分池上限；
**原子激活/释放席位，不按登录次数**。」

### 2.1 三条最易做错的规则

| # | 规则 | 失败形态 |
|---|---|---|
| SL-1 | 席位占用必须是**数据库内原子操作**（唯一约束 + 条件更新），**禁止先查后写** | 两个并发导入同时读到 `used = limit-1`，双双通过 → **超额**。这与 `consume_ai_quota` 已经做对的方式一致（`db.py:1075-1089` 用 `ON CONFLICT ... WHERE used < ?`），席位必须照抄这个模式 |
| SL-2 | 席位按**激活成员**计数，不按「注册过的账号」计数 | 停用成员不释放席位 → 席位池被僵尸账号占满，新人无法加入 |
| SL-3 | 释放席位必须**幂等**：同一 `(tenant_id, membership_id, kind)` 重复释放不产生第二次 | `release_ai_quota` 的 `MAX(0, used-1)` 模式（`db.py:1091-1099`）**不能**照抄到席位上——它没有引用计数 |

> **SL-3 是本节最容易被抄错的一处。**
> 现有 `release_ai_quota` 之所以「看起来能用」，是因为它当前**没有生产调用方**
> （`refund_call` 只被测试调用，见 INC-41），缺陷从未暴露。
> 席位释放是**高频且并发**的操作，把这个模式带过去会立刻产生「多退席位 → 池子虚高」。

### 2.2 席位与降级的关系

§12.3：「降级前检查实际用量和成员数；超出新上限时**限制新增并提示整改，
不删除多出的学生或文件**。」

| # | 规则 |
|---|---|
| SL-4 | 超出新上限时，**已有成员的一切既有权利不变**（可继续读、可继续提交），只**禁止新增激活** |
| SL-5 | 降级**不得触发任何数据删除**；超限状态必须有可见的整改提示与升级入口 |
| SL-6 | 平台强制吊销成员（安全原因）**必须释放席位**，且该释放与 SL-3 的幂等要求一致 |

> **SL-4 的反面很具体**：如果实现成「降级后把超编成员置为 `inactive`」，
> 那些学生会**当场失去对自己论文的访问**——包括正在赶截止日期的。
> §12.1 的 `restricted` 行明确写着「保留授权数据读取」。

> **`restricted` 不是 `tenants.status` 的取值**（2026-10-01 因 INC-59 消歧）。
> §12.1 首句要求「安全状态、商业服务状态和成员状态**分别建模**」，
> 而 `restricted` 属于**商业维度**：它是 `subscription` 与权益到期**派生**出来的读模型，
> 由本包的 `PB`/`EP` 规则计算，**不得**写进 `tenants.status`（W-02 §3.1 的
> `tenants_status_chk` 只含生命周期/安全的五个值）。本节以下的「`restricted` 下…」
> 一律指**派生读模型**，不是那一列的值。

## 3. 配额周期（PB）

这是本包与 AT-15 的正面对应处，也是当前实现**明确不满足**的一条。

### 3.1 当前行为与目标行为的差

```python
# ai_governance.py:59-60
def _utc_periods(now: datetime) -> tuple[str, str]:
    return now.strftime("%Y-%m-%d"), now.strftime("%Y-%m-%dT%H:%M")

# ai_governance.py:83-85 —— period 每次调用现算，从不落库
now = datetime.now(timezone.utc)
day_period, minute_period = _utc_periods(now)
```

| # | 问题 | 后果 |
|---|---|---|
| 1 | 周期边界由**调用时钟**决定，不落库 | 事后无法回答「这条用量属于哪个周期」，§12.3 的冻结边界无处可查 |
| 2 | 跨零点的请求归到**请求到达时**的周期 | 23:59:59 发起的、00:00:03 完成的请求，两端算不同周期；预留与结算可能落在不同周期 |
| 3 | 无「重置」事件 | §12.3「配额**不重复重置**」不可验证——当前靠 `period` 字符串不同自然分桶，看起来对，但没有机制保证 |
| 4 | 周期粒度硬编码为 UTC 日与 UTC 分 | §12.3 要求「夏令时、时区变化和周期切换**有测试**」，而当前连时区参数都不存在 |

### 3.2 规则

| # | 规则 | 说明 |
|---|---|---|
| PB-1 | 周期边界**先落库**（`quota_periods.period_start/end`），准入时**读取已冻结的行**，不现算 | 这是 §12.3 的直接要求 |
| PB-2 | 时区来自**租户设置**，缺省 UTC；同一租户的周期边界在一段时间内**恒定** | 时区变更只能影响**下一个**周期，不能追溯重划已用周期 |
| PB-3 | 周期切换时，上一周期的 `used`/`reserved` **原样冻结**，新周期另起一行 | 「配额不重复重置」的物理保证 |
| PB-4 | 夏令时切换（同一本地时间出现两次/缺失一次）必须有测试 | §12.3 明写 |
| PB-5 | **禁止**用「最后一次按钮点击日期」或任何客户端时间划周期 | §12.3 明写；周期只能由服务端冻结边界决定 |
| **PB-6** | `subscriptions.state` 的**取值集合固定为** `trialing` / `active` / `grace` / `expired` / `cancelled` | **总设计 §12.1 明文列出**这五个值，但此前**没有任何编号规则**承载它，导致 W-02 §3.3.1 的 `subscriptions_state` CHECK 取不到规则出处（INC-76）。**规则编号不是形式，是可被机器追溯的最小单位** |
| **PB-7** | **五个取值中 `trialing` 与 `grace` 的「天数」待 D-05**，**但取值集合本身不待裁** | D-05 未确认的是**期限数值**，不是**状态词汇**。**集合已定、天数待定**——这两件事必须分开，否则实施者会以为连词汇都没定而自行发明别名（违反 RQ-2 同类要求） |

## 4. 预算与预留（QT）

### 4.1 「可用值 = 已过账 − 已用 − 未决预留」

§12.3：「硬预算的可用值**包括未决预留**；
**未拿到实际供应商计量时不能宣称已精确限制费用**。」

当前 `ai_quota` 只有 `used`（`db.py:262-267`），**没有 `reserved`**。
后果是：W-08 的「派发中但结果未知」状态在配额上**不可见**——
系统认为额度还在，但上游可能已经计费。

| # | 规则 | 说明 |
|---|---|---|
| QT-1 | 准入时 `reserved += amount`；确认未派发则 `reserved -= amount`；确认完成则 `reserved -= amount; used += actual` | 预留是**独立计数**，不是「先加进 used 再退回」 |
| QT-2 | 可用值判据：`limit − used − reserved > 0`，判定与占用**在同一事务内** | 沿用 `consume_ai_quota` 的条件更新模式（`db.py:1075-1089`） |
| QT-3 | 预留**不得因过期自动释放**，除非能确认未派发 | §9.4 `reservations` 行：「未知外部结果不能凭过期自动释放」 |
| QT-4 | `budget_policies` 必须声明度量是**次数 / token / 货币成本**三者之一，**不混用** | §9.3 明确约束 |
| QT-5 | 上游未提供可信 usage 时，**不得**按估计值宣称已精确限制费用 | §12.3 原文；与 W-08 的 `usage_quality` 联动 |
| QT-6 | 预算告警 ≠ 硬预算；软预算只产生告警，不阻断 | §12.3 原文 |

### 4.2 与现有 `ai_governance` 的关系

**不删除现有机制。** §12.3：「当前每用户配额继续作为**旧接口兼容和风控**，
**不把其历史计数迁成金钱扣款**。」

| # | 规则 |
|---|---|
| QT-7 | 现有 `begin_call`/`release_ai_quota` 保留为**旧兼容闸**，叠加在租户配额之上，**不是替代关系** |
| QT-8 | `ai_quota.used` 的历史计数**不迁移**为任何货币或权益消耗；两套计数在报表上必须分列 |
| QT-9 | 旧闸的 `refund_call` 死代码（`ai_governance.py:113`，唯一调用方是测试 `test_ai_governance.py:173`）在 W-06 实施时**删除或修复**，不得原样留存 |

## 5. 角色与权益不相授（AT-14）

AT-14：「买权益但无角色、角色有权但 AI 到期 → **角色和权益不互相授予**；合法数据读取和退出保留。」

| # | 规则 | 说明 |
|---|---|---|
| EP-1 | 权益**不产生**任何角色或权限；角色**不产生**任何权益 | 二者是**正交**的两套判定，任一方向都不得推导 |
| EP-2 | 权益到期后，**阅读本人/授权数据**必须继续可用 | §12.1 `restricted` 行；AT-14 后半直接判这条 |
| EP-3 | 权益到期后**禁止新增受限制的 AI、席位或资源消费**，但**不得**锁住既有合法数据 | §12.1 原文 |
| EP-4 | 到期状态**不得**被表达成「账号被停用」——那会连登录和导出一起关掉 | 与 W-10 §3 的 `TENANT_RESTRICTED`（403，保留合法退出）必须区分于 `TENANT_SUSPENDED_SECURITY` |
| EP-5 | 退出导出路径在 `restricted` 下**必须**可达 | §12.1「申请续期和约定范围退出导出」 |
| EP-6 | 权益授予、变更、撤销**全部进审计** | 与 W-10 §1.1「计费：额度调整、权益变更」对齐 |

> **EP-4 的具体形态**：把商业到期实现成 `users.status = 'disabled'`。
> 后果是用户**登录不了**，也就无法申请导出、无法续期——
> §12.1 明确禁止这种绕过（「不能为了『可导出』绕过安全封禁」的反面同样成立：
> 也不能为了限制消费而阻断合法退出）。

## 6. 验收

| AC | 关联 AT | 判据 | 证据 |
|---|---|---|---|
| AC-06-1 | **AT-14** | 构造「有权益无角色」与「有角色无权益」两类账号：前者不得获得任何授权能力，后者不得获得 AI 额度；两类账号的**既有数据读取均正常** | W-03（角色）+ 本包 §5；两类账号的授权矩阵实测 |
| AC-06-2 | **AT-15** | 跨周期边界、租户时区变更、夏令时切换、`plan_version` 变更四种情形下：当前周期判定稳定、历史冻结规则不漂移、配额**不重复重置** | 本包 §3；四类情形各一组周期边界断言 |
| AC-06-3 | **AT-09**（席位部分） | 并发接受邀请 + 批量导入，席位剩余 1：最终激活数**恰好等于**剩余数，**不超额**；错误**不得**部分形成越界授权 | W-05 + 本包 §2；并发压测 + 激活行数快照 |

**本包无法独立验证的部分**（必须显式声明，不得混入「通过」）：

- 席位与周期在**真实 PostgreSQL** 上的并发语义——本机无 PG 实例（连续多轮阻塞），
  SQLite 的 `BEGIN IMMEDIATE` 语义与 PG 不同，**不得**用 SQLite 结果代替 PG 结论。
- 真实多租户数据——`tenant_memberships` 已有最小运行时表，但席位与权益对象未实现；AT-14/AT-15 仍无完整验收链路。

| 权益对象表是否存在、主键与唯一约束是否满足 PV-2/SL-1 | ✅ 可查 | 纳入 W-02 §4.1 expand DDL，由 `ddl_static_check` 与 `rls_policy_check` 覆盖 |

| SL-1 原子性（并发不超额） | ❌ | **并发测试**，AT-09 |

| QT-3 预留不因过期自动释放 | ❌ | **运行时测试**，与 W-08 联动 |

> **本包不新增静态门禁。**
> 与 W-04/W-05/W-09/W-10 同一判断：权益的合并、原子性与周期冻结
> **都是运行时性质**，静态检查能证明的只有「表建了、列有了、策略开了」。
> 现在加一条只能检查表存在性的门禁，会得到一个
> **看起来像验证的绿灯**——这比没有门禁更危险。
