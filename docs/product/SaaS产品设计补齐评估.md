## 1. 结论摘要

PaperGuard 已不只是“论文格式检查工具”：模板与规范治理、结构化写作、提交快照、教师审核、过程材料、归档和基础报表已经构成了较完整的**校内论文业务闭环**。

但从 SaaS 产品设计看，当前最准确的定位仍是：

> **面向单学校或单学院、小规模部署的试点产品。**
>
> 它还不具备作为共享多机构 SaaS 安全、可运营、可计费扩张的基础能力。

接下来不应优先继续堆叠单点写作功能，而应先补齐以下五类“平台底座”设计：

1. **租户与资源隔离**：把“学校/学院组织范围”与“客户租户边界”分开建模。
2. **机构管理与身份生命周期**：让机构管理员可以自助完成成员、权限、邀请、统一登录和治理。
3. **数据、AI 与安全治理**：明确论文正文、文件、密钥和审计记录的访问、保存、删除与外发边界。
4. **稳定运行与客户交付**：建立独立任务执行、可观测性、备份恢复和发布保障。
5. **商业化与客户成功**：先建立权益、用量、预算和客户健康度，再讨论支付接入。

建议以“**单机构可交付 → 共享 SaaS 可隔离 → 可商业化扩张**”三阶段推进，避免在租户隔离、账务与运行保障尚未就绪前直接开放多校共享、默认 AI 或在线收费。

## 2. 当前能力与 SaaS 边界

| 能力域 | 当前已有基础 | 对 SaaS 的含义 |
|---|---|---|
| 论文业务闭环 | 批次、阶段、成员、任务、候选版本、提交、审核、批注、过程材料、归档及统计均已纳入设计和当前工作区实现。 | 具备切入高校论文管理场景的核心业务价值。 |
| 文档与规范治理 | 模板、学校/学院/教师要求、版本快照、检查、豁免与申诉已被独立建模。 | 这是产品差异化的领域能力，应作为平台可配置资产继续沉淀。 |
| 身份与基本角色 | 密码哈希、会话、学生/教师/学院管理员/管理员角色与部分组织作用域已存在。 | 有基础认证与授权起点，但尚非多租户身份与访问管理系统。 |
| 数据一致性 | 草稿 `revision`、工作流乐观锁、提交幂等、版本快照、归档清单摘要均已设计或实现。 | 可以支撑审阅过程的可追溯性，是后续企业化治理的良好基础。 |
| 交付基础 | Docker、CI、数据卷、后端非 root 容器、Nginx 代理部署已具备。 | 可用于单实例交付，不等同于高可用、可监控、可扩展的平台运行面。 |
| 商业能力 | README 明确当前没有余额、用量、订阅、支付或扣费能力。 | 尚不能形成套餐销售、成本控制、续费或财务对账闭环。 |

### 2.1 需要明确区分的两个概念

当前组织模型已经支持学校、学院、专业、课程和批次等内部结构，但这不是 SaaS 的“租户”。

```text
SaaS 租户（合同、数据、计费、品牌、配置和支持边界）
└── 学校 / 教育集团
    ├── 学院
    ├── 专业
    ├── 课程 / 批次
    └── 成员、指导关系和论文资产
```

- **组织**回答“机构内部谁能看、谁负责、要求适用于哪里”。
- **租户**回答“哪一个付费客户拥有数据、配置、预算、品牌和管理权”。

若首版坚持“每个学校独立部署”，学校可暂时同时承担租户角色；但数据模型与产品文案仍应显式保留 `tenant` 概念，避免未来共享部署时进行高风险的全量重构。

## 3. 先做的战略决策

以下决策会决定后续数据模型、部署形态、报价方式和团队投入，必须先于大规模开发确认。

### D1：交付模式——私有化优先，还是共享多租户 SaaS？

| 方案 | 定义 | 适用阶段 | 必要设计 |
|---|---|---|---|
| 单机构独立部署 | 每所学校独立数据库、文件存储和运行环境。 | 首批试点、对正文出校敏感的客户。 | 部署自动化、机构管理员控制台、备份恢复、版本升级与服务支持。 |
| 共享多租户 SaaS | 多学校共用控制面和运行环境，数据严格按租户隔离。 | 产品模型稳定、客户数增长后。 | `tenant_id` 全链路、强制作用域查询、文件隔离、租户配置、审计、计费和平台运维。 |
| 混合模式 | 默认共享 SaaS，敏感学校使用独立实例。 | 中长期。 | 租户配置与功能旗标必须不依赖单一部署方式；同一产品契约支持两种运行形态。 |

**建议：**先按“单机构独立部署 + 可演进租户模型”完成 1–2 个真实学校试点；不要把“同一实例里有多个学校组织”直接宣传或当作“多租户 SaaS”。

### D2：首个付费客户与计费主体

需要确认到底是谁购买、谁管理、谁承担 AI 成本：

- 学校/学院年度订阅；
- 教师或课题组订阅；
- 学生个人订阅；
- 学校基础订阅 + 学生/教师增值 AI 用量；
- BYOK（用户自带模型密钥）与平台模型并存。

**建议的首版商业假设：**以学院或学校为合同与计费主体，按“在用成员数 + 可选 AI 额度”报价。学生个人不承担业务闭环的基础费用；BYOK 只作为补充，不替代平台的 AI 治理责任。

### D3：论文正文和 AI 的数据处理边界

必须由学校书面确认以下问题：

1. 哪些数据允许发送给外部模型供应商；
2. 是否允许学生自行配置任意 AI 服务 URL；
3. 是否需要供应商白名单、区域限制、数据不留存条款；
4. AI 结果是否需要使用声明、版本记录和人工确认；
5. 论文正文、归档、审计和用户密钥分别保留多久。

在这些规则未确认前，平台默认 AI 应保持可关闭，并且不应对外承诺“合规 AI 写作”或“学术不端判定”。

## 4. P0：共享 SaaS 或正式试点上线前必须完成的设计

### 4.1 租户模型与全链路隔离

**当前缺口**

- 当前系统有组织层级和组织上下文，但没有 `tenant` 实体、租户生命周期或租户级配置边界。
- 数据主要存于单个 SQLite 数据库和 JSON 列；对象范围依赖各接口的应用层过滤。
- 模板当前是全局资源，缺少租户/组织归属与可见性策略。
- 文件路径、归档、AI 配置、审计和后台任务尚未以租户作为第一等边界。

**需要的设计**

1. 新增 `Tenant`：`id`、名称、状态、部署模式、时区、数据区域、合同状态、默认语言、创建/停用时间。
2. 所有业务资源都必须能沿关系链回溯到唯一租户：用户成员关系、组织、模板、规范、项目、提交、文件、归档、任务、审计、用量和账务。
3. 请求上下文只能从登录会话、受信任子域名或受控机构选择器解析租户；**禁止接受客户端上传的 tenant_id 作为授权依据**。
4. 仓储/查询层应强制接收 `tenant_context`，而非由每个接口自行 `list_all()` 后筛选。
5. 文件对象使用由服务端生成的租户前缀和不可猜测 ID，例如：`tenants/{tenant_id}/projects/{project_id}/...`；下载在“生成链接”和“实际读取”两次重新鉴权。
6. 平台运维和客户管理员是不同角色：平台运维默认不能浏览论文正文；临时支持访问需要理由、时效、双重授权和审计。

**验收标准**

- 任意两个租户将项目、图片、提交、归档、任务、模板、规范和导出 ID 互换，均不能读取或修改对方数据。
- 每个列表、搜索、统计、导出、后台任务和文件下载都带租户范围测试。
- 即使出现 API 漏过滤，数据库/对象存储边界仍可阻断跨租户访问或提供告警。

### 4.2 统一资源授权与身份生命周期

**当前需要优先核查和修正的设计点**

1. `backend/app/main.py:110-126` 的图片下载判断将所有活跃教师/学院管理员视为可管理者，可能绕过项目接口中更严格的指导关系和组织范围校验。
2. `backend/app/auth.py:180-189` 的会话解析当前主要判断会话有效性；账号被拒绝/禁用、角色降级或“首次必须改密”应在服务端认证边界统一生效，而不能只靠前端路由跳转。
3. 模板 API 当前读取侧没有统一身份与作用域设计，且模板模型不含租户/组织归属。
4. 规范批量升级、过程材料、归档、通知和导出都需要复用同一个资源级授权服务，不能在各自 API 中复制简化逻辑。

**需要的设计**

- 建立统一的 `Authorization Service`：输入 actor、tenant、resource、action、purpose，输出 allow/deny 与审计事件。
- 把角色拆成“平台角色”和“租户/组织成员角色”，避免全局 `admin/teacher` 角色天然跨机构有效。
- 明确账号状态机：`invited → active → suspended → deactivated`；角色/状态变更立即撤销会话与长期令牌。
- 改密、MFA、恢复账号等高风险流程在服务端拥有 allowlist；“首次必须改密”账号只能改密、查看必要指引和登出。
- 机构成员管理需提供人员搜索、批量导入预检、邀请、停用、角色/范围授予、指导关系转交和操作历史，不能让管理员输入内部 ID 完成日常维护。

**验收标准**

- 被禁用或降权用户的已有会话立即失效。
- 未完成强制改密的账号不能写作、下载或调用 AI。
- 教师 A 不能访问教师 B 学生的正文、图片、检查报告、提交、过程材料或归档。
- 平台角色和客户管理员的访问范围在审计中可解释且可撤销。

### 4.3 机构管理控制台与信息架构

**当前缺口**

系统设置、用户认证和默认 AI 配置目前集中在顶栏弹窗；组织、规范和业务闭环分布于不同页面。功能继续增加后，机构管理员难以形成明确的操作路径。

**建议的机构管理控制台**

```text
机构控制台
├── 概览
│   ├── 首次启用清单
│   ├── 任务、审核、归档风险
│   └── 服务健康与公告
├── 成员与权限
│   ├── 成员、邀请、批量导入
│   ├── 角色与组织范围
│   ├── 指导关系与转交
│   └── 统一认证 / SSO
├── 学术配置
│   ├── 模板库
│   ├── 规范与规则版本
│   ├── 批次与阶段
│   └── 例外审批
├── 数据与合规
│   ├── 归档与下载授权
│   ├── 审计检索与导出
│   ├── 数据导出
│   └── 保留与删除策略
├── AI 与用量
│   ├── 供应商和模型白名单
│   ├── 功能开关与预算
│   └── 使用记录与异常
└── 支持与服务
    ├── 帮助中心、工单和反馈
    ├── 服务状态
    └── 实施与迁移记录
```

前端路由守卫可以改善体验，但不是安全边界；后端资源级授权始终是最终准入条件。

### 4.4 数据治理、审计与隐私

**需要的设计**

| 主题 | 必须明确的规则 |
|---|---|
| 数据分类 | 身份信息、论文正文、附件、检查报告、过程材料、归档、日志、AI 输入输出、API Key 分别分类。 |
| 保留策略 | 草稿、回收站、提交、归档、审计、备份、AI 记录分别配置保留期、责任人和法律保留例外。 |
| 删除流程 | 删除申请 → 影响评估 → 法律/归档例外 → 延迟物理清理 → 完成证明；不得把软删除误称为物理删除。 |
| 数据可携带性 | 机构可导出成员、模板、规范、论文、提交、归档、审计和配置；导出本身应是异步任务并需要二次授权。 |
| 审计 | 独立 append-only 审计链，至少记录登录、权限变化、正文/文件访问、下载、模板/规范发布、例外审批、AI 调用、导出、恢复和运维支持访问。 |
| 备份恢复 | 数据库、文件、归档制品和引用关系必须一致性备份；按 RPO/RTO 演练并留下恢复证据。 |

**当前设计风险**

- 工作流审计与普通 JSON 业务记录共用存储，且存在通用覆盖/删除能力，不能作为不可篡改审计的最终实现。
- 草稿回收站已存在，但过程材料、模板源文件、规范附件、归档制品的生命周期没有被统一为可配置、可执行、可审计的策略。
- README 已说明用户 AI Key 明文存入 SQLite；这不适合处理敏感论文数据的正式 SaaS 环境。

### 4.5 AI 治理与密钥管理

**需要的设计**

1. 平台模型和 BYOK 两条路径分别设计；每次调用都记录调用主体、租户、模型、用量、成本、状态、输入分类和数据处理同意版本。
2. BYOK 密钥不可明文存于普通业务数据库或常规备份；使用 KMS/Vault 加密、脱敏展示、最小权限读取和轮换/删除机制。
3. 平台默认模型需要租户级开关、模型白名单、预算上限、速率限制、超限策略和异常告警。
4. 外部端点必须校验协议、域名与出网策略，避免任意 URL 配置导致正文发送至未知服务。
5. AI 修改必须由用户确认后写入正文；生成结果不能自动形成审核结论、豁免或学术不端判断。

**上线门槛**

在无用量、预算、供应商边界和调用审计之前，不开放全体用户共享的默认付费模型；在无安全存储之前，不推荐在生产环境保存用户 API Key。

### 4.6 运行面、异步任务与可观测性

当前归档恢复和部分后台处理仍依赖 API 进程生命周期，站内 outbox 也尚未接入真实消费者。正式交付前需要设计独立运行面：

```text
Web API
  ├── 同步鉴权、校验和短事务
  ├── 写入业务状态、审计和 outbox
  └── 返回 job_id / request_id

Worker / Scheduler
  ├── 检查、归档、导出、通知、清理
  ├── 租约、幂等、指数退避、失败分类
  ├── 死信队列 / 人工处理队列
  └── 任务指标和结构化错误

Observability
  ├── request_id / job_id / tenant_id 关联
  ├── 结构化脱敏日志
  ├── 指标、链路、错误告警
  └── readiness / liveness / 依赖健康检查
```

**必须定义的运行指标**

- API 可用率、P50/P95/P99 延迟、错误率；
- 保存冲突、提交失败、授权拒绝和 AI 超限；
- 队列长度、最老等待时间、重试次数、死信数量；
- 归档/导出成功率、文件摘要不一致、恢复耗时；
- 每个租户的存储、活跃用户、AI 成本和风险任务数量。

## 5. P1：从可交付试点到可运营 SaaS 的设计

### 5.1 客户启用与客户成功

目前注册、模板建项目和任务发布形成了功能入口，但缺少“客户完成价值”的可操作定义。

**建议定义机构激活漏斗：**

```text
创建租户/部署完成
→ 指定机构管理员
→ 配置学校与组织范围
→ 发布至少一套模板 + 规范
→ 导入或 SSO 同步首批成员
→ 建立指导关系
→ 发布第一个阶段任务
→ 学生完成第一次提交
→ 教师完成第一次审核
→ 生成第一份有效归档
```

每一步需要：完成条件、责任角色、阻塞原因、帮助入口和数据指标。平台应对以下风险触发提醒：

- 管理员 7 天未发布首个任务；
- 模板/规范/教师分配缺失导致发布阻断；
- 教师待审核超过约定 SLA；
- 学生到期未提交或退回后无后续动作；
- AI 预算消耗异常、归档反复失败、存储即将超限；
- 关键管理员长期未登录或成员激活率过低。

### 5.2 帮助、反馈与支持闭环

工作流通知与客户支持是两类不同能力。建议新增：

- 角色化帮助中心：学生写作/提交，教师审核，管理员配置与导出；
- 应用内反馈：问题类型、截图/请求编号、脱敏提示、工单状态；
- 发布公告和产品更新说明；
- 可公开或可登录查看的状态页；
- 客服临时访问申请及其审批、到期和审计记录。

### 5.3 机构级报表与 SaaS 健康度

现有统计主要衡量论文业务结果，应在不误把“登录次数”当成教学质量的前提下，增加两层指标：

| 层次 | 建议指标 |
|---|---|
| 教学业务成效 | 按时提交率、审核周转、修订轮次、检查改善率、归档完成率。 |
| 产品采用与客户健康 | 管理员激活、已发布批次比例、教师审核覆盖率、活跃学生比例、功能采用、支持工单、异常任务、存储与 AI 预算消耗。 |
| 商业经营 | 试用转付费、合同活跃状态、授权使用率、续费风险、单位活跃用户成本、AI 毛利。 |

统计必须支持按租户、学院、批次和时间范围下钻，并始终执行隐私最小化原则：跨机构只能查看授权后的汇总数据。

### 5.4 移动端、可访问性与国际化

当前设计已把移动端定位为任务、消息和反馈优先。下一步需要把此边界变成可验证的体验设计：

- 移动首页只突出“当前待办、截止、反馈和消息”，不试图在手机复刻长文编辑器；
- 独立消息收件箱，支持未读、类型、任务、失败状态和跳转后的重新授权；
- 所有业务页面统一接入 i18n，避免规范、流程、组织页面长期混用硬编码中文；
- 关键状态不能只用颜色表达；审核、提交、归档和下载流程满足键盘可达、焦点管理和屏幕阅读器标签；
- 导出 DOCX、归档 ZIP、表格和长文本在窄屏和辅助技术下提供替代操作路径。

## 6. P2：商业化、生态与规模化设计

### 6.1 套餐、权益、用量与账务

业务角色（学生、教师、管理员）不应直接等于商业权益。建议独立建模：

```text
Product Plan（套餐）
  └── Entitlement（权益：成员、存储、归档、AI、SSO、审计保留期等）
      └── Subscription（租户订阅与有效期）
          └── Usage Meter（可计量用量）
              └── Immutable Ledger（不可变账务流水）
```

先完成以下能力，再接支付：

1. 用量事件不可变记录；
2. AI 请求的预留、成功结算、失败释放和超时对账；
3. 租户预算、额度、速率限制与超限降级；
4. 赠送额度、人工调整、冲正和审批记录；
5. 账单、合同周期、发票主体和争议处理；
6. 支付回调幂等、签名校验和对账。

### 6.2 高校身份与业务集成

潜在高校客户通常会提出以下能力，建议按客户证据决定投入：

- OIDC / SAML 单点登录；
- SCIM 或受控 CSV 同步成员与院系；
- 教务系统、课程系统、统一消息平台、邮箱、企业微信/钉钉的受控集成；
- 学校对象存储、私有模型网关、查重服务和长期归档系统；
- Webhook / API 事件订阅，支持“任务发布、提交、审核、归档失败”等受控事件；
- 集成权限、字段映射、失败重试、数据最小化与审计。

不要把第三方查重、AI 检测或教务数据直接接入核心流程；每个集成都需要单独确认采购授权、数据流向、责任边界、失败降级和验收样本。

### 6.3 扩展性与架构演进

共享 SaaS 前建议从“SQLite + JSON 全局记录”演进为：

- 具备版本化迁移、外键、索引和租户字段的关系数据库；
- 按领域拆分 Cohort/Stage、Submission、Archive、ProcessRecord、Notification、Billing 等服务层；
- 统一的资源授权、审计、存储引用和错误契约；
- 对象存储、任务队列、缓存和数据库连接池按真实负载逐步引入；
- 通过容量模型而非单用户本地测试确定 PostgreSQL、worker 数量和存储策略。

这不是立即“微服务化”的建议。首要目标是让领域规则、权限、事务和租户边界可复用、可验证；在没有明确瓶颈前，可保留模块化单体部署。

## 7. 推荐路线图与放行条件

### 阶段 S0：完成可交付的单机构试点

**目标：**让一个学院完成真实闭环，并具备最基本的数据安全和恢复能力。

- 修复统一资源授权、账号禁用/强制改密、模板范围与批量规范升级的跨范围风险；
- 将当前未跟踪的工作流、过程材料、服务和测试文件作为一个原子交付单元，避免仅提交已跟踪文件造成启动失败；
- 独立机构管理控制台的最小版本：成员、组织范围、指导关系、批次、模板、规范、归档和审计入口；
- 数据分类、保留期、备份与恢复演练；
- 独立消息收件箱与基础支持反馈；
- 定义试点容量、RPO/RTO、审核 SLA 和验收样本。

**放行条件：**

1. 同学院中不同教师/学生的全部资源交换 ID 后均被拒绝；
2. 提交、审核、归档、通知和恢复在重试/断线/重启后可解释且不重复；
3. 任意归档可验证对应正文、材料、规则、审核和文件摘要；
4. 完成数据库与文件一致性恢复演练；
5. 管理员无需查询内部 ID 即可完成成员导入、分配、发布和归档；
6. 真实试点用户完成一轮端到端验收。

### 阶段 S1：建立共享 SaaS 所需的租户底座

**目标：**在一个运行环境中安全服务多个独立客户。

- `tenant`、成员关系、租户级配置和生命周期；
- 关系数据库迁移、全链路租户查询边界、文件按租户隔离；
- 平台管理员与租户管理员分权；
- 租户级审计、导出、保留策略和支持访问控制；
- 独立 worker、真实 outbox 消费者、指标、告警和部署规范；
- 多租户负向授权测试、故障恢复和容量压测。

**放行条件：**

- 两个租户在同一环境中完成全流程并通过全部交叉访问、导出、搜索、后台任务和文件下载隔离测试；
- 数据库、对象存储、缓存、日志和指标都可按租户追踪与限制；
- 平台运维默认无正文访问权；
- 关键安全事件、任务失败和容量异常有可操作告警；
- 客户能够自助执行约定范围的数据导出与成员治理。

### 阶段 S2：商业化和规模运营

**目标：**实现可控制成本、可对账、可续费的商业闭环。

- 套餐、订阅、权益、用量、预算和账务流水；
- AI 供应商治理、模型白名单、密钥管理和数据处理声明；
- SSO/SCIM 与重点高校系统集成；
- 客户健康度、续费风险、工单和服务运营；
- 支付、发票和自动对账（在商业规则确定后）。

**放行条件：**

- 每次平台 AI 调用可追溯到租户、权益、成本与账务结果；
- 超限、失败、重复回调和退款/冲正都有确定流程；
- 合同到期、试用结束、降配和数据导出场景均有已验证体验；
- 客户支持、服务状态、使用指标和续费风险形成运营看板。

## 8. 设计待决清单

下列事项如果不经业务方确认，不应由技术实现自行假设：

1. 首批目标客户是学院、学校，还是面向教师/学生的个人产品？
2. 首期是否坚持每校独立部署，何时允许共享多租户？
3. 学校是否允许论文正文发送给外部 AI；允许哪些供应商与地区？
4. 平台 AI 与 BYOK 分别由谁承担成本与风险？
5. 学校账号体系如何接入：邀请、账号密码、OIDC/SAML、SCIM，还是混合模式？
6. 学生、草稿、提交、归档、审计、备份、AI 调用记录各自的保留期限是什么？
7. 归档是否需满足学校长期保存、PDF/A、电子签章或外部档案系统要求？
8. 机构管理员、平台运维、客户成功人员在何种条件下可临时查看正文？
9. 需要哪些接口对接教务、查重、统一消息和文件存储；各自的故障降级是什么？
10. 套餐按成员、活跃学生、批次、存储、AI token，还是组合计量？
11. 学校对可用性、并发、RPO/RTO、数据区域和安全评估有什么合同要求？
12. 是否需要服务国际学院；英文、时区、数据跨境和无障碍的目标范围是什么？

## 9. 结论

PaperGuard 的下一阶段重点应从“继续完善一篇论文如何写”逐步转向“一个机构如何安全、持续、可治理地使用这套系统”。

推荐优先级为：

> **资源授权与账户生命周期 → 单机构管理控制台与数据治理 → 租户底座与运行面 → AI 用量与账务 → SSO/生态集成与规模运营。**

只要前两层未补齐，项目适合以受控单机构试点交付；只有租户隔离、独立任务运行、审计/留存和客户自助治理得到验证后，才适合按多机构 SaaS 宣传或扩张。
