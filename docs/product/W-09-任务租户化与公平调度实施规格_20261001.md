## 0. 本规格要解决什么

W-03 §4.2 定义了异步任务的上下文契约（AS-1～AS-4），但**没有承接方**。
本包承接：任务按租户隔离、租约与栅栏、尝试历史、公平调度、死信处理。

总设计 §25.1 点名的风险是「**任务租约短于处理**」。
本轮代码取证发现，该风险在当前实现里**已经是可触发的缺陷**，不只是理论风险。

## 1. 现状取证（2026-10-01，代码只读）

`backend/app/db.py:2106-2160` 的 `claim_jobs` / `complete_job`：

| # | 事实 | 位置 | 风险 |
|---|---|---|---|
| 1 | `jobs` 表**有 `lease_token` / `lease_until` / `leased_by`，但无 `lease_epoch`** | `db.py:389-407` | 总设计 §19.1 契约 6 字段全缺（F-07）；**无栅栏** |
| 2 | `complete_job` 的 WHERE 是 `lease_token IS NULL OR lease_token = '' OR lease_token = ?` | `db.py:2145` | **空租约也能提交**——见 §1.1 |
| 3 | `claim_jobs` 的 UPDATE 是 `WHERE id = ?`，**无 epoch / 无 CAS** | `claim_jobs` 定义于 `db.py:2106`，UPDATE 语句见 `db.py:1725-1726` | 领取不是比较并交换，见 §1.2 |
| 4 | `claim_jobs` 可领 `state='running' AND lease_until <= now` 的任务 | `db.py:2124` | 租约过期的任务被重领，**旧 worker 仍可能持有它** |
| 5 | 无 `tenant_id` 列 | W-02 §4 #24 判为 `tenant` 但 expand 阶段才加 | 任务**不按租户隔离** |
| 6 | `ORDER BY created_at ASC LIMIT ?` | `db.py:2126-2127` | **无公平性**：一个租户的大任务可占满全部名额（AT-27） |
| 7 | 无死信状态；`max_attempts` 用尽后停在 `failed` | `db.py:413`、领取条件 `db.py:1976` | 无人处理的终态，无告警无留痕 |

### 1.1 缺陷 A：空租约可提交（AT-25 直接命中）

```python
# db.py:1681-1684
"UPDATE jobs SET state = 'succeeded', ... WHERE id = ? AND state = 'running' "
"AND (lease_token IS NULL OR lease_token = '' OR lease_token = ?)"
```

`lease_token IS NULL OR lease_token = ''` 这两个分支使**任何持有 `job_id` 的调用方
都能把任意 `running` 任务标记为成功**，无论它是否持有有效租约。

- `lease_token` 的默认参数是 `""`（`def complete_job(self, job_id, *, lease_token: str = "")`），
  **不传 token 就能提交**；
- 旧 worker 租约过期后任务被新 worker 重领，旧 worker 调 `complete_job`
  传自己的旧 token——此时 token 已不匹配，但**只要它在同一时刻先提交就能成功**。

**这正是 AT-25「旧 worker 无法发布或更新」当前无法通过的原因。**

> **修法不是「把 NULL 分支删掉」这么简单**：还要处理
> 「任务刚入队、尚未被领取」的状态转换。正确判据是
> **`lease_epoch` 比较**（见 §2.2），而不是 token 字符串比对——
> token 会被轮换，epoch 不会。

### 1.2 缺陷 B：领取不是 CAS（与总设计 §25.1 同源）

```python
# db.py:1664-1666
"UPDATE jobs SET state = 'running', attempt_count = ?, lease_until = ?, "
"lease_token = ?, leased_by = ?, last_error = NULL, updated_at = ? WHERE id = ?"
# ← 只有 id
```

领取时只按主键更新。两个并发 worker 读到同一行后**都会更新成功**，
`rowcount` 都是 1，于是**两个 worker 都以为自己领到了任务**。

当前靠 `BEGIN IMMEDIATE` 串行化缓解，但：
- 它只保证 SQLite 写锁，**PG 迁移后语义不同**；
- 即便串行，第二个 worker 读到的仍是**自己事务开始时的快照**，
  `SELECT` 与 `UPDATE` 之间的判定不是原子的。

## 2. 租约与栅栏

### 2.1 六字段契约（总设计 §19.1，W-02 §4.1 已加列）

`jobs` 表在 expand 阶段加：`tenant_id` / `resource_version` / `payload_schema_version` /
`attempt_generation` / `lease_epoch` / `deadline`。

| 字段 | 作用 | 谁写 |
|---|---|---|
| `tenant_id` | 任务归属租户 | 派发时（W-03 AS-2） |
| `lease_epoch` | **栅栏**：每次领取单调递增 | 领取事务内 |
| `attempt_generation` | 第几次尝试 | 领取时递增 |
| `deadline` | 绝对超时（`lease_until` 是相对的） | 派发时按任务类型设定 |
| `resource_version` | 乐观锁基准 | 派发时快照 |
| `payload_schema_version` | 载荷结构版本 | 派发时 |

### 2.2 领取：CAS 而非裸更新

```
BEGIN;
  SELECT ... FROM jobs
   WHERE <可领取条件>
     AND lease_epoch = :expected_epoch      -- ← 栅栏条件
   FOR UPDATE SKIP LOCKED;                   -- ← PG 语义
  UPDATE jobs SET lease_epoch = lease_epoch + 1, ...
   WHERE id = :id AND lease_epoch = :expected_epoch;
  -- rowcount = 0 → 被别人抢走，放弃
COMMIT;
```

| # | 规则 | 说明 |
|---|---|---|
| LE-1 | 领取**必须**带 `lease_epoch` 条件 | 缺它则并发领取必然双成功（§1.2） |
| LE-2 | 每次领取 `lease_epoch + 1`，**单调递增不回绕** | 旧 worker 的 epoch 永远小于新值 |
| LE-3 | 使用 `FOR UPDATE SKIP LOCKED` | PG 下避免 N 个 worker 抢同一行后串行等待 |
| LE-4 | `deadline` 与 `lease_until` **都检查** | 长任务靠心跳续租，但 `deadline` 是硬上限 |

### 2.3 提交：必须带 epoch，且**不得**有 NULL 通配

```
UPDATE jobs SET state = 'succeeded', ...
 WHERE id = :id
   AND lease_epoch = :my_epoch        -- ← 精确匹配，无 OR NULL
   AND state = 'running'
```

| # | 规则 | 对应缺陷 |
|---|---|---|
| LE-5 | 提交/失败**必须**精确匹配 `lease_epoch` | 修 §1.1：删掉 `IS NULL OR = ''` 两个分支 |
| LE-6 | **禁止**任何 `lease_token IS NULL OR ...` 形式的通配 | 通配 = 放弃栅栏 |
| LE-7 | `rowcount = 0` 必须**明确失败**并告警 | 静默返回 None 会让旧 worker 以为失败可重试 |

> **LE-6 的取舍要写清楚**：删掉 NULL 分支后，
> 「尚未被领取的任务无法被标记成功」——但那本来就是**正确行为**。
> 旧代码的 NULL 分支不是为「未领取」设计的，是**为了省事**，
> 代价是任何人都能提交别人的任务。**便利性不应由安全性买单。**

### 2.4 心跳与长任务

| # | 规则 | 说明 |
|---|---|---|
| HB-1 | 长任务**必须**续租（心跳），心跳间隔 < `lease_until` 的一半 | 避免正常长任务被误判过期 |
| HB-2 | 心跳**必须**带 epoch；epoch 不匹配时**停止工作** | 已被重领的 worker 必须自杀 |
| HB-3 | 超过 `deadline` **无条件停止**，不再续租 | 硬上限，防止无限重试（AT-27「无无限热重试」） |

## 3. 租户隔离与公平调度（AT-27）

### 3.1 一个租户不能占满全部名额

```sql
-- 错误：ORDER BY created_at LIMIT n —— 一个租户的大任务可占满全部名额
-- 正确：每个租户设 per-tenant 配额，且按「最久未服务」排序
SELECT ... FROM jobs
 WHERE <可领取>
   AND (SELECT COUNT(*) FROM jobs j2
         WHERE j2.tenant_id = jobs.tenant_id
           AND j2.state = 'running') < :per_tenant_limit
 ORDER BY COALESCE(last_served_at, created_at) ASC
 LIMIT :n;
```

| # | 规则 | 判据 |
|---|---|---|
| FS-1 | 每租户**并发上限**独立于全局上限 | AT-27「租户资源限额有效」 |
| FS-2 | 排序按「该租户最久未被服务的时间」而非全局 `created_at` | 否则大租户持续压榨小租户 |
| FS-3 | 重试退避**必须有上限** | AT-27「无无限热重试」 |
| FS-4 | 死信（dead letter）独立状态 + 告警 | 当前 `failed` 后停摆，无人处理（取证 7） |

> **FS-2 的具体形态**：全局 FIFO 在多租户下是**不公平**的——
> 租户 A 一次投 1000 个任务，会让租户 B 的 1 个任务等 999 个。
> 修法有两种：per-tenant 配额，或 weighted fair queuing。
> **本包选 per-tenant 配额**：C0 规模下它足够，且**更容易证明正确**——
> 「A 占了 5 个并发，B 还能拿到自己的 5 个」是可测的断言，
> 而 WFQ 的公平性判据需要长期统计才说得清。

## 4. 重复消费与终态一致（AT-26）

| # | 规则 | 说明 |
|---|---|---|
| ID-1 | **已发布效果不可重复生成** | 幂等键 = `(tenant_id, job_type, resource_id, resource_version)` |
| ID-2 | `attempt_generation` 递增但**效果不重复** | 多次尝试 ≠ 多次效果 |
| ID-3 | 附件孤儿**安全隔离**，不挂到任何已发布产物 | 孤儿清单登记（W-02 T-02.8 已建 `storage_objects`） |
| ID-4 | 取消与完成竞争时，**终态单一且可解释** | 用 epoch 做仲裁，不靠时间戳先后 |

> **ID-1 与 ID-2 的区别容易混**：重试**允许**（网络失败），
> 但**效果**不允许重复（渲染产物不能出两份）。
> 把两者混为一谈会导致「为了幂等而放弃重试」——
> 任务一失败就永久卡死，比重复更糟。

## 5. 归档恢复（AT-28 的任务侧）

| # | 规则 |
|---|---|
| AR-1 | 恢复前**必须先核对 manifest**，不得直接信任现有产物 |
| AR-2 | 正式修复写 `audit_events`（含 `request_id` 与操作者） |
| AR-3 | 恢复后的产物必须能被**真实下载并校验一致** |

> AR-1 直接对应总设计「备份恢复需应用 tombstone 以免已删内容复活」
> （W-02 §3.3 `storage_objects.state` 三态）。**恢复不是「信任备份」，
> 是「用备份 + 墓碑 + 校验」三方核对。**

## 6. 验收

| ID | 关联 | 判据 | 证据要求 |
|---|---|---|---|
| AC-09-1 | **AT-25** | worker 重启、租约过期、长任务心跳三种情形下：**旧 worker 无法发布或更新**；新进程可收敛 | 旧 epoch 提交的负例 + 新 worker 收敛记录 |
| AC-09-2 | **AT-26** | 同任务/事件重复消费**不重复生成已发布效果**；孤儿安全隔离；取消与完成竞争后终态一致 | 重复消费负例 + 孤儿清单 + 竞争用例 |
| AC-09-3 | **AT-27** | 一个租户积压 + 大任务与普通任务竞争时，**租户限额与公平策略有效**；无无限热重试 | 双租户并发压测 + 死信告警记录 |
| AC-09-4 | **AT-28** | 人工归档恢复：先核对 manifest；正式修复有审计；真实下载一致 | manifest 核对记录 + 下载校验 |
| AC-09-5 | §1.1 | `complete_job` **不含任何 NULL 通配**；不传 token 无法提交 | SQL 取证 + 负例 |
| AC-09-6 | §1.2 | 并发领取同一任务**恰好一个成功** | 并发压测（无 `BEGIN IMMEDIATE` 依赖） |
| AC-09-7 | §2 | 六字段契约齐备且**非空有值** | schema 取证 + 样本行 |
| AC-09-8 | — | **无任何生产写操作**；`git status` 无非预期改动 | 操作日志 + 差异摘要 |

> **AC-09-1 与 AC-09-5 测同一件事但不可互相替代**：
> AC-09-1 是端到端场景（worker 重启后的实际行为），
> AC-09-5 是代码形态（SQL 里还有没有 `OR NULL`）。
> 只验 AC-09-5 会在等价改写里漏掉语义；
> 只验 AC-09-1 则需要真实多进程环境——**当前没有**。

## 7. 门禁

| 检查 | 工具 | 守住什么 |
|---|---|---|
| 全局 `role` 引用计数 | `context_resolution_check.py` CR-4 | 任务侧的角色读取是否随租户化 |
| 规格↔AT 归属与漏引 | `at_traceability_check.py` AT-10/AT-11 | 本表覆盖 §24.2 归 W-09 的全部 AT |
| 规格代码引用行号 | `spec_citation_check.py` | 本文件 §1 取证行号不漂移（本文件写入时由该门禁核对通过） |

**本包暂不新增静态门禁**：AT-25～AT-28 全部是**并发与终态**判据，
静态检查证明不了「旧 worker 确实发不出去」「并发领取确实只有一个成功」。
**唯一能静态查且值得查的是 AC-09-5**（SQL 里是否还有 `OR NULL` 通配），
但它需要先读 `backend/app/db.py` 的实现文本——
`account_path_check` 已有 AST 基础设施可扩展，**待本包实施时一并加**，
现在加只会得到一个必然报红的常红项，不产生新信息。
