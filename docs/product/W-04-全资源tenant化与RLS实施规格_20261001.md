### 0.1 规格侧的一个既存缺口（本包要闭合）

总设计 §26.3 记录「无真实 PostgreSQL 实例 → **AT-04/06/45** 的 DDL 与 RLS 未验证」。
该缺口的**规格侧根因**是：

- **W-04 规格此前不存在**（本文件是首次产出）
- `AT-04`（A 项目关联 B 模板/组织/成员/附件 → 数据库拒绝）在 §24.2 归属 **W-04**，
  却**没有任何规格承载它的判据**——AT-04 的核心正是 W-02 §3.2 的复合外键设计

即：**数据库层的设计已经产出，但没有任何规格说明「怎么证明它真的拒绝了」。**
本包 §4 给出该证明方法，§5 给出 AT-03/04/05/06 的判据。

## 2. 改造原则：三层防护，不可互相替代

总设计 §8.2 要求「建议同时使用两层保护」。本包明确**三层各自的职责**：

| 层 | 机制 | 失效时的表现 | 谁负责 |
|---|---|---|---|
| **L1 应用层** | Repository 按 `ctx.tenant_id` 过滤 | **返回全量数据**（静默泄露） | W-03 + 本包 §3 |
| **L2 数据库行级** | RLS `USING`/`WITH CHECK`（W-02 §3.6） | **返回 0 行**（静默失败） | W-02 已产出策略 |
| **L3 数据库关系** | 复合外键 `(tenant_id, parent_id)` | **写入报错**（响亮失败） | W-02 §3.2 已产出 DDL |

> **三层缺一不可，但失败模式完全不同，必须分别测。**
> L1 漏了会泄露数据，L2 漏了会让人以为有隔离其实没有，
> L3 漏了会让人在应用层漏掉校验时写进脏数据。
>
> **只有 L3 会响亮地失败**——因此 AT-04 用它作为判据，
> 而 AT-03（列表/导出/搜索不泄漏）**必须用 L1/L2 验证**，
> 因为那两类越权在 L3 下**不产生任何错误**。

## 3. L1 应用层改造清单（W-03 已定原则，此处给顺序）

改造顺序按**风险 × 集中度**排列，来自 `resource-registry.yaml` 的引用统计：

| 优先级 | 目标 | 依据 |
|---|---|---|
| P0 | `workflow.py` 相关 34 处 `role` 读取 | 全局单值，跨租户角色必然串（W-03 CR-4） |
| P0 | 无 `WHERE tenant_id` 的全表读 | `cross_tenant_full_table_read` 风险标志 |
| P1 | 列表端点 | `unscoped_list_query`；**AT-03 主体** |
| P1 | 批量操作 | 批量是最容易漏过滤的路径 |
| P2 | 导出/报表 | `app_layer_only_file_authz`；需与 W-10 的租户级导出对齐 |
| P2 | 搜索 | 索引表达式跨租户（`json_extract(data,...)`）需确认过滤可下推 |

> **顺序不可跳。** P0 未完成时启用 RLS 会让 P0 路径**静默返回 0 行**——
> 表现为「功能坏了」而非「泄露了」，排障方向会被误导。

## 4. L3 数据库层验证方法（AT-04 的判据）

AT-04 判据原文：「API 与数据库关系约束拒绝，**第一笔写入前停止**」。

「第一笔写入前停止」意味着：**不能靠应用层校验兜底**。必须证明**即使应用层完全不校验**，
数据库也会拒绝。验证分三层，每层一个负例：

```sql
-- 负例 1：跨租户父子挂接（A 租户的组织挂到 B 租户的父节点下）
INSERT INTO tenant_organizations (tenant_id, id, parent_id, type, name)
VALUES ('tenant-A', 'org-new', 'org-of-B', 'college', 'X');
-- 期望：FOREIGN KEY (tenant_id, parent_id) 违反 —— 且**不是**因为找不到 org-of-B，
--       而是因为 (tenant-A, org-of-B) 这个组合不存在。

-- 负例 2：跨租户成员绑定（师生关系）
INSERT INTO teacher_student_bindings (id, tenant_id, teacher_membership_id, student_membership_id)
VALUES ('tsb-x', 'tenant-A', 'mem-of-B', 'mem-of-A');
-- 期望：复合外键拒绝

-- 负例 3：RLS 写策略（假设已 SET LOCAL app.tenant_id='tenant-A'）
UPDATE tenant_memberships SET tenant_id = 'tenant-B' WHERE id = 'mem-of-A';
-- 期望：WITH CHECK 违反（不是 WHERE 过滤 —— UPDATE 的旧行命中、新行不命中时报错）
```

> **负例 1 的关键细节**：如果只写单列 `FOREIGN KEY (parent_id) REFERENCES ... (id)`，
> 这条 INSERT 会**成功**（因为 `org-of-B` 确实存在），
> 只是产生一条跨租户的脏父子关系。**这正是 W-02 §3.2 用复合外键的原因。**
> 验证时必须确认报错来自复合外键，而非「恰好 id 不存在」。

## 5. 验收

| ID | 关联 | 判据 | 证据要求 |
|---|---|---|---|
| AC-04-1 | **AT-03** | 列表、详情、批量、报表、导出、搜索**全部**跨租户隔离；无正文、名称、邮箱、计数或存在性泄漏 | 6 类端点 × 2 租户的对称负例 |
| AC-04-2 | **AT-04** | A 租户项目关联 B 的模板/组织/成员/附件**被数据库拒绝**；报错发生在**第一笔写入前** | §4 三个负例 + 报错来源确认 |
| AC-04-3 | **AT-05** | 缺 `app.tenant_id` 的读/写被拒绝；连接池复用**不残留**上个租户设置 | 三段 SQL 序列 + 连接复用探针 |
| AC-04-4 | **AT-06** | 表所有者 / `BYPASSRLS` / 超级用户角色**不出现在** API 与 worker 的连接路径 | 角色清单 + 连接串核对 |
| AC-04-5 | **AT-02** | 伪造 tenant Header/URL/组织过滤**不能**授予权限；所有查询求授权范围**交集** | 三类伪造各自的负例 |
| AC-04-6 | **AT-13** | 下载/预览/归档/静态路径**鉴权前无文件内容**；无旧静态旁路；撤权策略可解释 | 未鉴权请求的响应体取证 + 旧 URL 探测 |
| AC-04-7 | §2 | 三层防护**分别**有负例；不得用 L3 通过替代 L1/L2 验证 | 各层独立证据 |
| AC-04-8 | §3 | P0 改造完成**之前**不得启用现有表 RLS | 改造清单 + 启用时序记录 |
| AC-04-9 | — | **无任何生产写操作**；`git status` 无非预期改动 | 操作日志 + 差异摘要 |

> **AC-04-6（AT-13）是本包最容易被漏掉的一条**（2026-10-01 由 AT-11 反向检查抓出）。
> §24.2 把 AT-13 归给 W-04，但本规格初版只写了数据类端点——
> **文件路径的鉴权恰恰是 RLS 覆盖不到的地方**。
>
> `resource-registry.yaml` 已就此挂了 `app_layer_only_file_authz` 风险标志：
> **RLS 只能筛行，筛不了文件内容**。静态文件一旦能被直接 URL 访问，
> RLS 隔离得再严也拦不住——**因为请求根本没到数据库**。
> 该项必须由 W-02 §3.3 的 `storage_objects` 目录 + 应用层授权承担，
> 不能计入「RLS 已覆盖」。

> **AC-04-1 与 AC-04-2 的验证对象不同，不可互相替代**：
> AT-04 是**写入**被拒（有响亮错误），AT-03 是**读取**不泄漏（**无错误**）。
> 只验 AT-04 就宣称 AT-03 通过，是本包最容易犯的错误——
> 数据库能挡住跨租户**写入**，但**读不到的行恰恰是 RLS 生效的证据**，
> 而不是「读不到就安全」的证明：读不到也可能是因为查询条件写错了。

## 6. 门禁

复用既有工具，不新增：

| 检查 | 工具 | 守住什么 |
|---|---|---|
| 策略矩阵完整性 | `rls_policy_check.py` | W-02 §3.6 的 13 张表策略齐全（INC-15） |
| contract 准入 | `contract_readiness_check.py` | 隔离清单未清零不得建 RLS（INC-16） |
| 逐表判定三方一致 | `schema_disposition_check.py` | §4 判定 ↔ 代码 schema ↔ 工具假设 |
| 全局 role 引用计数 | `context_resolution_check.py` CR-4 | P0 改造进度可量化 |
| 规格↔AT 归属与漏引 | `at_traceability_check.py` AT-10/AT-11 | 本包验收表覆盖 §24.2 归给 W-04 的全部 AT |

**本包暂不新增门禁**：L1/L2/L3 的负例都需要**真实 PostgreSQL** 才能执行，
静态检查证明不了「数据库真的拒绝了跨租户写入」。
在无 PG 实例前新增一个只能做正则匹配的「RLS 覆盖检查」，
会给出一个**看起来像验证、实际什么都没验证**的绿灯——**比没有门禁更危险**。

> 该缺口已如实登记在总设计 §26.3「无真实 PostgreSQL 实例」条目下。
> **解除条件是授权一个 PG 实例或安装 `pglast` + 起库**，不是加检查器。

## 7. 明确不做

- 不做合同/账务/支付（W-11/W-12）
- 不改 RLS 越权矩阵（W-02 §3.6 只保证「策略存在」，实际拦截属本包 §5）
- 不做 SSO/独立部署（W-13）
- 不做任务租户化（W-09）
- 不承诺「所有资源已 tenant 化」——**`conditional` 8 张里仍有 3 张待裁决**
  （`templates` 公共资产判定规则、`requirement_sets` 的 `scope` 语义、
  `workflow_records` 的 2 个 `*_candidate` kind），
  但**其余 5 张已可推进**，不再挂在裁决上（INC-72）
- 不在无真实 PG 的情况下声称 RLS 已验证
