## 0. 本规格要解决什么

W-12 是整条设计链的**最后一个商业化包**：把「钱」与「权益」之间的那条转换路径，
做成**渠道不可信也安全**的转换。

§24.2 归给它 **3 条 AT**（AT-40、AT-41、AT-42），全部围绕同一件事：
**渠道是不可信的外部系统，它会重复、乱序、伪造、迟到，而系统必须收敛到唯一结果。**

> **第 3、4、6 条合起来改变了 W-12 的设计基调**：
> 本包**不是**「从零设计一套支付管道」，
> 而是「把已经跑通的 outbox 形状**加上渠道边界**」。
> 这降低了工作量，但也带来第 7、8 条的风险——
> **照抄形状会连缺陷一起照抄。**

## 2. 支付流程（PY）

§16.2 的七步骨架照搬。本节补规格必须回答、实现者最容易做错的部分。

### 2.1 「支付完成」不是证据

§16.2 原文：**页面显示「支付完成」不是账务证据；客户端不能直接激活套餐。**

| # | 规则 | 说明 |
|---|---|---|
| PY-1 | 权益激活**只能**由**已验证的渠道事件**（经 inbox → 唯一过账）触发，**任何**前端回跳**不得**触发 | 伪造回跳是本包最直接的越权路径 |
| PY-2 | 回调必须校验：**签名、时间/重放、商户、订单、币种、金额**——五项**缺一不可** | §16.2 原文列举 |
| PY-3 | 原始签名与渠道凭据**不得写通用日志** | §16.2 原文；与 W-10 §1.3 敏感字段约束一致 |
| PY-4 | **先持久化已验证事件，再按渠道协议返回应答**；**未持久化时不得假装已成功消费** | §16.2 原文 |
| PY-5 | 订单金额、币种、租户、目标服务关系由**服务端冻结**；请求体携带的任何金额**一律忽略** | §18.2「服务端价格」；对应 W-11 PR-1 |
| PY-6 | 向渠道请求下单必须带**业务幂等键** | §16.2 第 3 步 |
| PY-7 | 客户端**不得**看到内部订单状态机；只看到「已提交 / 处理中 / 已到账 / 需处理」四态 | §16.2 末步「客户看见明确到账状态」 |

> **PY-4 的反直觉之处**：渠道要求快速应答，而「持久化 + 核对订单状态」会花时间。
> 正确取舍是**先落 inbox（快）再应答，慢的部分交给 worker**——
> 而不是「先应答再慢慢存」。后者的失败形态是
> **渠道认为已投递、本地没有记录**，事件**永久丢失**且无人知道。

### 2.2 订单状态机（§16.3）

```text
created → pending → succeeded / failed / closed
                  ↘ unknown / reconciling
```

| # | 规则 | 说明 |
|---|---|---|
| PY-8 | 结果不确定时进入 **`unknown`/`reconciling`**，**不得**随意改成 `failed` 后重开重复订单 | §16.3 原文 |
| PY-9 | 关单与付款竞争 ⇒ **查渠道最终状态**；**晚到成功事件仍要核对并按规则处理** | §16.3 第 2 条 |
| PY-10 | 支付、退款、服务关系、权益**分别记录状态**；**付款成功不代表后续权益变更已生效** | §16.3 第 3 条 |
| PY-11 | 续费**冻结下一周期与计划版本**；**取消自动续费 ≠ 立即取消已付款期限** | §16.3 第 4 条 |
| PY-12 | 合同人工开通、赠予、渠道支付是**三种不同来源**，每次有**批准证据和版本** | §16.3 第 5 条；与 W-06 **PV-5** 合并规则对齐 |

> **PY-8 是本包最容易写错的一条**：
> 「超时未收到回调 ⇒ 标记失败」是直觉做法，也是**重复收款**的直接来源——
> 用户实际上付了钱，系统认为失败并重开订单，用户再付一次。
> 正确形态：超时 ⇒ `reconciling` + **主动查渠道**（PRV-1 的「查询交易」），
> **只有渠道明确答复失败**才落 `failed`。

## 3. 回调幂等与乱序（CB）—— AT-40

### 3.1 inbox 的唯一性

| # | 规则 | 说明 |
|---|---|---|
| CBK-1 | `payment_event_inbox` 唯一键 = **`provider` + `merchant` + `event_id`** | §9.4 原文 |
| CBK-2 | inbox 行**必须**在应答渠道**之前**提交（PY-4） | — |
| CBK-3 | 重复事件 ⇒ **返回已有处理结果**，**不重复过账** | §15.4「支付确认：provider + merchant + external_transaction 只过账一次」 |
| CBK-4 | 事件**乱序**（先 `succeeded` 后 `created`）⇒ 处理**依赖本地状态与渠道可确认事实**，**不依赖收到顺序** | §16.2「而不是收到顺序」 |
| CBK-5 | `verified` 字段记录**验签是否通过**；**未验签的事件不得进入业务处理** | §9.4 |
| CBK-6 | 敏感原文仅**受控保管**（`payload_ref` 指向受控存储） | §9.4「敏感原文仅受控保管」 |

### 3.2 「已过账」的判定必须独立于「已收到」

| # | 规则 |
|---|---|
| CBK-7 | inbox 行需要**至少三态**：`received`（已持久化未处理）/ `processed`（已过账）/ `rejected`（校验不通过） |
| CBK-8 | `received` 是**可重放的**中间态；重放**只走已验证的业务路径**，**不重新验签后直接过账** |
| CBK-9 | `processed` 是**终态**；重复处理必须**返回首次结果** |

> **CBK-7 的必要性**：现有 `workflow_idempotency`（`db.py:383-390`）只有
> `request_hash` + `response`，**没有 pending/completed 区分**。
> 支付场景**不能照抄这个结构**——
> 它无法表达「已收到渠道事件但尚未过账」，
> 而这恰恰是重复与乱序最集中发生的窗口。
> **可复用的是锁内复判的并发模式（`backend/app/api/workflow.py:1503`），不是表结构。**

### 3.3 复用 outbox 形状，但**必须替换租约原语** ⚠️

`workflow_events` 的 outbox 形状非常完整，值得复用：
`dedupe_key UNIQUE`（去重）、`delivery_status`、`attempt_count`、
`lease_until`/`lease_token`/`leased_by`（租约）、
以及 `consume_in_app_outbox`（`workflow_jobs.py:230`）的 claim → ack 循环。

**但它的租约确认有缺陷，且是 INC-30 的第二处实例：**

| 位置 | 方法 | 租约校验写法 | 判定 |
|---|---|---|---|
| `db.py:2497` | `complete_job` | `(lease_token IS NULL OR lease_token = '' OR lease_token = ?)` | ❌ INC-30 已记 |
| `db.py:2612-2625` | `mark_workflow_event_delivered_with_lease` | **同一串通配** | ❌ **本轮新发现** |
| `db.py:2677-2708` | `fail_workflow_event` | `if row["lease_token"] and row["lease_token"] != lease_token` | ⚠️ 第三种写法，无 CAS |

| # | 规则 | 说明 |
|---|---|---|
| CBK-10 | 支付 outbox **必须**使用 W-09 的 **`lease_epoch` CAS**（LE-1～LE-6），**禁止**任何 `IS NULL OR ...` 通配 | **照抄形状必须同时替换原语**，否则等于把缺陷复制到资金路径 |
| CBK-11 | **同一语义只允许一处实现**：租约确认、租约释放、租约续期**各只有一个函数** | 现状是三处实现、三种严格度（INC-47） |
| CBK-12 | W-09 规格的 LE-5/LE-6 修复范围**只覆盖 `jobs` 表**，**须扩到 `workflow_events`** | 否则「旧缺陷已修」的结论对 outbox 不成立 |

> **这一节是本包最容易「看起来在复用、实际在复制缺陷」的地方。**
> 复用的判断标准不是「有没有现成代码」，
> 而是**「现成代码的缺陷会不会一起被继承」**。
> 支付路径上的租约缺陷比通知路径严重一个量级：
> 通知重复发是骚扰，**支付事件重复 ack 会掩盖重复过账**。

## 4. 未知与恢复（RC）—— AT-41

| # | 规则 | 说明 |
|---|---|---|
| RCV-1 | 渠道状态未知时**查渠道**（`query_transaction`），**不推断** | §16.3 |
| RCV-2 | 查询/重放**收敛到唯一终态**；**不重复收款** | AT-41 |
| RCV-3 | 渠道**长期不可查** ⇒ 保持 `reconciling` + 告警 + 人工案件，**不自动判失败** | §15.3 精神；不得因定时器到点改状态 |
| RCV-4 | 「支付成功但权益未生效」⇒ **客户可见中间态** + 自动重试激活 | AT-41「展示真实中间状态」 |
| RCV-5 | 权益激活失败**不得**回滚已过账的支付 | 两条链路解耦；PY-10 |

> **RCV-5 的取舍必须写清**：把激活放进同一个事务看起来更简单，
> 但一旦激活需要调用外部系统（W-11 结算、可能的邮件），
> 事务就会跨越不可控时长，**且失败会连带撤销一笔已经真实收到的钱**——
> 那是最难向客户解释的状态。
> 正确形态是**支付过账与权益激活分离，用 outbox 保证最终一致**，
> 代价是必须**如实展示中间态**（RCV-4）。

## 5. 退款与冲正（RF）—— AT-42

§16.4 五条 + AT-42。

| # | 规则 | 说明 |
|---|---|---|
| RF-1 | 退款申请**关联原支付**，**锁定可退余额** | §16.4 第 1 条 |
| RF-2 | 审批权限与**教学管理权限分开** | §16.4 第 1 条 |
| RF-3 | 渠道退款未知时**不可反复生成新退款**；先**查询原申请**并核对 | §16.4 第 2 条；对应 `query_refund` |
| RF-4 | **累计确认退款 + 有效预留退款 ≤ 原确认支付额** | §16.4 第 3 条 |
| RF-5 | 确认退款后**产生新账务凭证**（经 W-11 入口），**不删改原凭证** | §16.4 第 4 条 + JV-6 |
| RF-6 | 权益回退按**已裁决条款**操作；**不得删除学生论文或归档** | §16.4 第 4 条 |
| RF-7 | 发票/收据、税务、合同与监管适用性由**负责主体和专业人员**确认；本设计**不代为作合规结论** | §16.4 第 5 条 |

> **RF-4 的两个加数容易被漏掉第二个**：
> 「累计确认退款」只统计已确认的，**「有效预留退款」**（退款已发起但渠道未终结）
> 不计入就会让可退额被重复使用——
> 两笔并发退款各自看到「可退 = 原额」而都通过检查。
> 正确形态是**锁住可退额**（RF-1 的「锁定」），
> 而不是「查询时算一遍」。

## 6. 验收

| AC | 关联 AT | 判据 | 证据 |
|---|---|---|---|
| AC-12-1 | **AT-40** | 重复、乱序、伪造、金额或商户不符四类回调：验签后 inbox **幂等**（不重复过账），**不能错误过账或激活权益** | 本包 §2/§3；四类回调各一组，含**乱序**与**并发重复** |
| AC-12-2 | **AT-41** | 关单竞争、渠道未知、支付成功但权益失败三种情形：**查询/重放收敛**、不重复收款、展示**真实中间状态** | 本包 §4；含渠道 mock 的不确定应答 |
| AC-12-3 | **AT-42** | 并发部分退款、重复退款、渠道退款未知：**不超过可退额**、不重发新退款、确认后**补偿凭证** | 本包 §5；并发退款压测 + 守恒断言 |

**本包无法独立验证的部分**（不得混入「通过」）：

- **全部三条 AT 依赖渠道 mock**。§16.1 明确渠道未选定，
  因此**验收必须自带渠道替身**，且替身要能制造**重复、乱序、超时、金额不符**——
  一个只会返回成功的 mock 会让 AC-12-1～3 **全部假绿**。
- 真实渠道联调、签名协议、商户资质**均不可验证**（D-11 未决）。
- 权益激活的端到端效果依赖 W-06/W-11；`billing_accounts` 尚不存在。
- 并发语义需**真实 PostgreSQL**；本机无 PG 实例。

## 7. 门禁

| 判据 | 静态可查？ | 处置 |
|---|---|---|
| 新表 `payment_orders`/`payment_event_inbox`/`refund_requests` 是否登记 RLS | ✅ | `rls_policy_check` RL-1 双向核对 |
| **租约通配模式是否在资金路径复现** | ✅ **可静态查** | 见下 |
| inbox 唯一键（CBK-1）约束是否存在 | ✅ 仅约束存在性 | 行为正确性不可静态查 |
| 回调验签是否五项齐全（PY-2） | ❌ | 运行时 + 渠道替身 |
| 权益激活是否可由前端触发（PY-1） | ❌ | **端点级越权用例** |
| 退款不超可退额（RF-4） | ❌ | 并发压测 |

> **本包是所有工作包中唯一「值得新增静态门禁」的一个**，判据是 **CBK-10/CBK-11**。
> 理由与其他包相反：其余包的静态判据只能证明「表建了、列有了」，
> **证明不了运行时行为**，加了就是虚假安全感；
> 而租约通配是一个**可以用模式匹配精确检出、且历史上已实际发生过两次**的形态
> （`db.py:2497`、`db.py:2363`）。
> 门禁应检出 `lease_token IS NULL OR ...` 这类**空租约通配**出现在任何带租约的 UPDATE 上。
> **但必须同时声明它的边界**：它只保证「不出现通配」，
> **不保证**该处用了正确的 CAS 条件——后者仍是运行时判据。
