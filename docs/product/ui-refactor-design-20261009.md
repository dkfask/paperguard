## 1. 设计摘要

本方案保留真实前端的业务实现与角色工作台，以原型为视觉和导航参照，分阶段统一界面。不按原型页数重写前端，不把 API 全量迁移、编辑器重构或租户改造混入视觉任务。

本次仅授权编写并保存设计文档。所有阶段、接口、模型和工期均为建议；编写文档不代表恢复附件中标为 PAUSED 的 W01–W13 计划。

### 1.1 建议决策

| 编号 | 建议决策 | 理由 |
|---|---|---|
| D-01 | 保留 `AppShell` 与 `/workspace` 角色入口 | 复用现有业务，避免按原型复制多套页面 |
| D-02 | 将 Phase 0 改为事实核验与回归基线 | 先确认未明入口和角色可达性，不能把静态代码等同于业务验收 |
| D-03 | API 按模块渐进迁移，不作为视觉统一前置 | 类型化包装层仍依赖旧实现，全量迁移需要独立回归 |
| D-04 | 先验证代表性页面，再推广设计变量与基础组件 | 避免基础样式大改后才暴露复杂业务不兼容 |
| D-05 | 写作区先改外壳，不同时改保存、数据结构和编辑器生命周期 | 控制正文丢失、选区丢失和编辑状态回归风险 |
| D-06 | 教师私有过程材料模板单独立项 | 属于授权、文件与版本管理能力，不是新增一个页签 |
| D-07 | 第二校准入安全边界优先于全量视觉整理 | 纯视觉可独立推进，资源授权不能为 UI 进度让步 |

上述决策均待确认。本文不新增已批准的长期决策，不替代项目现有治理文件。

## 2. 目标、范围与非目标

### 2.1 目标

1. 统一导航、字体层级、间距、颜色、状态反馈和基础交互。
2. 让用户从角色工作台清楚找到下一步操作，并可直接定位业务页面。
3. 保留现有业务规则、权限约束、历史链接与正文编辑行为。
4. 将视觉调整、真实业务缺口和新增功能分开交付。
5. 建立绑定代码版本的页面状态矩阵与角色回归证据。

### 2.2 工作分类

| 类别 | 范围 | 处理方式 |
|---|---|---|
| V：视觉与导航 | 外壳、样式变量、基础组件、已有入口的组织与文案 | 本方案的主要实施范围 |
| R：已存在能力的缺口 | 后端有能力，但缺少页面入口、反馈或角色可达性 | 先确认产品预期，再单独建立修复任务；不伪装为纯视觉 |
| N：新增能力 | 教师私有模板、新的发布规则、新的资源授权 | 单独立项，见第 9 节 |
| S：安全与租户 | 资源归属、成员授权、文件隔离、存量迁移 | 沿用独立安全工作包，不由 UI 任务授权 |

### 2.3 非目标

- 不引入新的 UI 组件库，不全面重写现有视图。
- 不整体迁移 JavaScript 到 TypeScript，不因 Pinia store 数量少而搬迁全部状态。
- 不修改检查、修复和导出引擎的公共接口。
- 不修改认证机制、租户授权或数据库迁移账本。
- 不将学校、学院、专业组织层级描述为租户。
- 不交付完整共享多租户 SaaS、AI 收费或学术不端判定能力。
- 不改动小程序；Web 验收不代替微信真机 UAT。
- 不提交、推送、合并、部署或启动额外代理。

## 4. 信息架构设计

### 4.1 角色壳与业务目的地分离

保留 `/workspace` 作为角色概览，集中显示下一步行动、待办和异常。业务详情进入可定位的页面或面板，不把所有配置表单放回工作台。

目标结构如下。此结构表达导航意图，不要求每一项对应一个新路由或新 Vue 文件。

```text
统一应用外壳
├── 学生工作台
│   ├── 我的任务与论文
│   ├── 写作工作区（含上下文 AI）
│   ├── 提交与反馈
│   ├── 过程材料
│   └── 消息
├── 教师工作台
│   ├── 待办审核与批注
│   ├── 指导学生与进度
│   ├── 过程材料审核
│   └── 我的模板（后续功能，批准并实现后出现）
└── 管理工作区（按现有权限分别呈现）
    ├── 批次与阶段
    ├── 模板与规范
    ├── 组织与成员
    ├── 归档与审计
    └── 运维与设置（不扩大平台级权限）
```

学生归档下载是否加入“提交与反馈”，需先确认产品授权与后端支持，不由导航设计自动开放。

### 4.2 路由与导航规则

1. 保留已有 URL；若确需调整，提供兼容跳转并保留业务定位参数。
2. 可直接进入、刷新和返回重要业务目的地，不能依赖先访问工作台才能加载上下文。
3. 现有 `panel` 查询参数继续承担面板定位时，页面标题、菜单高亮和实际内容必须一致。
4. 列表筛选和分页按需进入路由；论文正文、凭据和其他敏感内容不进入 URL。
5. 教师、学生复用业务数据与状态机，不复制出独立但不一致的审核流程。
6. 菜单可见性仅改善体验；直达页面和 API 都必须维持原有权限检查。
7. 学院管理员与学校管理员不能因为共用外壳而获得相同权限。
8. 共享租户上下文不满足时显示明确受限状态，不回退到宽松 legacy 路径。

### 4.3 原型与现有架构的取舍

| 场景 | 建议 |
|---|---|
| AI 辅助独立页 | 以写作内的上下文操作为主；如有独立入口，先用于说明或定位，不复制编辑器 |
| 模板与规范合页 | 可以合并一级导航，继续保留不同业务模型和二级页面 |
| 组织与成员合页 | 可以统一管理区域，但保留组织范围、成员角色和操作权限差异 |
| 平台设置合页 | 不将平台设置与学校设置合成同一个授权范围 |
| 教师“我的模板” | 放在教师工作区域；不进入学院模板库的默认列表 |

## 5. 视觉与基础交互设计

### 5.1 设计变量

先建立原型变量与现有 CSS 变量的映射，至少覆盖颜色、文字层级、间距、圆角、边框、阴影和焦点状态。

- 以现有 `--primary`、`--surface-*`、`--on-surface-*` 等变量为起点。
- 原型的具体色值、字体和尺寸在原型版本确认后确定；本文不虚构视觉验收数值。
- 区分产品界面样式与论文正文样式。UI 变量不得覆盖模板控制的字号、行距和导出排版。
- 先核验 Tailwind 的实际构建入口与产物，再决定如何使用工具类。
- 不在视觉整理中顺手升级 Tailwind、改变全局 reset 或引入另一套同义 token。
- 限定富文本、Word 预览和第三方组件的样式作用范围；慎用深层选择器。

### 5.2 组件复用顺序

优先复用已有 `BaseButton`、`BaseInput`、`BaseModal`、`AsyncState`、状态徽标和确认对话框。

顺序为：变量映射 → 基础组件 → 列表与表单模式 → 角色壳 → 复杂业务页面。

只有出现重复业务结构且现有组件无法承载时才提取新组件。不为视觉统一先创建一套新的表格或表单框架。

### 5.3 统一状态规范

| 状态 | 必须呈现的内容 |
|---|---|
| 首次加载 | 明确加载反馈，避免把暂未返回显示成空数据 |
| 空列表 | 说明为什么为空，并仅展示当前角色有权执行的下一步 |
| 请求失败 | 可理解的错误、必要的请求 ID、明确重试入口 |
| 无权限或功能未启用 | 显示受限原因；不伪装成“暂无数据” |
| 保存中 | 禁止重复提交，保持输入内容与当前焦点 |
| 保存失败 | 保留用户输入，不显示已保存状态 |
| 异步任务 | 区分排队、处理中、成功、失败；只提供服务端允许的重试 |
| 危险操作 | 描述对象、影响与不可逆性，沿用现有确认机制 |

所有弹窗验证键盘操作、焦点进入与返回。状态不能只用颜色表达；窄屏、长文本和中英文均纳入验收。

## 6. 前端技术方案

### 6.1 API 边界

当前调用方向存在以下两种形态，不能仅通过目录名判断是否已经完成迁移：

```text
页面 → feature API → legacy 业务 API → HTTP
页面 → feature API → shared client → legacy client → HTTP
```

建议逐步收敛为“页面调用 feature API、feature API 依赖稳定请求边界”。迁移期间允许保留受控适配层。

- 新增业务调用不继续堆入大而全的 legacy 文件。
- 旧 API 不新增无关能力，但允许必要的缺陷修复。
- 页面视觉调整不必同时迁移其全部 API。
- 每次迁移验证请求方法、参数、响应类型、错误类型和副作用等价。
- 保留认证头、401 跳转、403 展示、请求 ID、FormData、Blob 下载和 204 空响应语义。
- 不把 legacy 响应直接当作 SaaS `data/meta` 响应；适配必须有显式边界与测试。
- 全量 API 迁移另行估时，不计入第 10 节纯 UI 排期。

### 6.2 状态职责

| 状态 | 推荐承载方式 |
|---|---|
| 服务端查询结果、加载与刷新状态 | 沿用 TanStack Query 或当前已有查询封装，渐进调整 |
| 表单草稿、弹窗、页内选中项 | 页面或业务组件本地状态 |
| 真正跨页面共享的客户端状态 | 在有明确消费者时使用 Pinia |
| 正文、编辑器选区与撤销历史 | 沿用写作模块的现有权威状态，不复制第二份正文 |

若后续引入多租户切换，查询缓存需包含影响数据范围的身份维度。退出、撤权或切换身份时应清理旧缓存，不能将前一个身份的数据留在新界面。

缓存分区不是后端授权。该要求属于后续接入约束，不表示本轮已经启用租户切换。

### 6.3 未使用代码处理

删除前检查生产引用、测试、动态注册、样式依赖和配置引用。

`WriterHeader` 已知存在测试引用，必须先判断该测试验证的契约是否仍有价值。若确认淘汰旧实现，应保留必要的行为测试覆盖，不能仅删除测试以消除失败。

清理提交与视觉提交分开，方便审查、定位和回滚。

## 7. 页面与场景对齐清单

| 业务场景 | 当前承载 | 计划处理 | 放行条件 |
|---|---|---|---|
| 学生任务中心 | `StudentWorkspace` 与任务卡片 | 工作台突出下一步动作，保留业务详情入口 | 加载、空态、截止状态与任务定位正确 |
| 论文写作 | `Writer` 与现有编辑组件 | 外壳优先，正文交互最小变化 | 第 8 节不变量全部回归 |
| AI 辅助 | 写作区内能力 | 统一入口与结果反馈，不创建第二编辑器 | 关闭 AI、请求失败与采纳流程可解释 |
| 预检与提交 | `Workflow` 与相关入口 | 梳理统一导航，不复制提交状态机 | 预检失败、正文变化、正式提交和重复操作不退化 |
| 学生批注反馈 | API 存在，页面调用待核验 | 先走查；缺口确证后转 R 类任务 | 学生能看到授权反馈并完成要求的处理 |
| 学生归档下载 | 待确认 | 确认业务资格与文件权限，再决定入口 | 不通过新增按钮隐式扩大下载权限 |
| 教师审核批注 | `TeacherWorkspace`、`Workflow` | 队列与审核详情保持定位一致 | 批注、退回、重提、通过及已结束只读状态可验证 |
| 过程材料审核 | `Workflow` | 聚焦材料对象、提交状态与审核操作 | 附件下载、退回与错误状态不退化 |
| 指导学生 | `TeacherStudents` | 统一列表与表单交互 | 不扩大可见学生和账号管理权限 |
| 批次与阶段 | `Cohorts` | 样式统一，保留版本与发布约束 | 截止时间、配置版本和成员操作仍按原规则 |
| 模板与规范 | `Templates`、`Policies` | 统一导航分组，保留各自生命周期 | 管理权限、发布和版本引用不混淆 |
| 组织与成员 | `Organizations`、`AdminUsers` | 统一管理体验，不合并授权边界 | 学院范围、学校范围和平台范围分别验证 |
| 归档与运维 | `Workflow`、`AdminWorkspace`、`Operations` | 归档业务与平台运维保持区分 | 状态、失败原因、下载和受控重试可追踪 |
| 教师私有模板 | 尚不满足本需求的授权闭环 | N 类后续任务，不纳入纯 UI 范围 | 完成第 9 节独立验收 |

每个场景至少记录：角色、前置数据、路由或面板、权限、正常状态、异常状态、关键操作、验收证据和对应提交。

## 8. 写作工作区专项约束

### 8.1 本轮允许的变化

- 工具栏、侧栏、抽屉、面板和状态提示的视觉整理。
- 在 props、事件和数据流保持等价的前提下，提取小型展示组件。
- 改善当前操作的可发现性、禁用原因与错误反馈。

### 8.2 不能随视觉变化一起修改的机制

- 正文数据结构、章节或段落 ID 的生成规则。
- 自动保存时机、版本号与冲突检测。
- 编辑器挂载、卸载和重新创建条件。
- 选区、撤销重做栈、导入覆盖与 AI 结果采纳逻辑。
- 模板约束、检查修复与 DOCX 导出契约。

确需修改上述机制时，另行提出设计与测试范围，不在视觉 PR 中混做。

### 8.3 写作验收不变量

1. 中文输入法组合输入不中断，不丢字。
2. 打开或关闭侧栏、切换布局后，正文和选区不被意外重置。
3. 保存失败保留草稿，重试不会静默覆盖更新版本。
4. 未保存离开页面有明确提示，成功保存状态与服务端一致。
5. AI diff 可查看、采纳或拒绝，行为与既有契约一致。
6. 导入、导出、检查与修复不修改用户原文件。
7. UI 样式调整不改变论文模板排版或导出内容。
8. 同一操作不因组件重挂载重复发起保存、生成或导出请求。

## 9. 后续功能：教师私有过程材料模板

本节是待立项设计，不属于 Phase 0–2 的实施授权。

### 9.1 最小可用范围

建议首版仅支持：教师上传 DOCX 过程材料模板，按明确业务范围发布，自己当前指导的学生下载使用。

首版不包含在线模板设计器、自动解析为写作结构、学院库共享、跨教师共享和自动替换学院要求。若需要模板驱动在线填写，须另行评估通用文档能力的适用性与运行时开关。

### 9.2 领域对象

优先复用现有 `DocumentTemplate`、`TemplateVersion` 和受控文件能力。下表是拟议的逻辑契约，物理表结构与迁移编号须在单独实施设计中确定。

| 对象 | 拟议字段或规则 |
|---|---|
| 教师材料模板 | `id`、`tenant_id`、`owner_membership_id`、名称、`material_type`、`visibility=teacher_private`、状态、当前发布版本 ID、创建与更新时间 |
| 适用范围 | 明确批次；按业务需要进一步限定阶段。是否允许一次发布到全部指导批次，待负责人确认 |
| 模板版本 | `id`、`template_id`、版本号、受控资产 ID、内容摘要、发布者、发布时间；发布后不可原地覆盖 |
| 学生使用记录 | 在现有过程材料或文档记录中引用 `template_version_id`，保存必要来源快照 |
| 指导关系 | 复用服务端已批准的有效关系，同时验证租户和业务范围；不维护第二套学生名单 |

模板生命周期建议为草稿、已发布、已归档；具体枚举与现有模型的映射在实施前确认。

新增版本不改变已提交学生材料的历史内容。发布必须原子切换当前版本，重放与并发冲突不能产生多个相互矛盾的当前版本。

### 9.3 授权判定

教师管理模板需同时满足：账号有效、租户有效、成员有效、具备管理能力、模板属于当前成员、资源租户与上下文一致。

学生发现或下载可用模板需同时满足：

```text
学生身份及成员有效
AND 资源属于当前租户
AND 模板已发布且未停止新的使用
AND 所属教师成员有效
AND 当前学生与该教师存在有效指导关系
AND 当前任务或批次落在模板适用范围内
```

`tenant_id`、所有者成员和可见性由服务端决定。客户端传来的任务、批次或模板 ID 只是定位条件，不是授权证明。

当前代码同时存在账号教师绑定与批次指导关系。新功能必须先确定它们在租户和批次内的解释规则；无法证明归属或关系时拒绝访问，不猜测回填。

### 9.4 可见性规则

| 调用方 | 默认权限 |
|---|---|
| 模板所属教师 | 管理本人的模板及版本 |
| 同租户其他教师 | 不可列表、查看详情、下载或修改 |
| 有效指导关系内的学生 | 仅发现和下载当前范围内已发布的可用版本 |
| 其他学生或跨租户用户 | 不可访问 |
| 学院管理员、学校管理员、平台支持人员 | 不因角色名称自动获得私有源模板权限；任何例外单独批准并审计 |

学院模板库须在后端查询层排除私有模板。列表、搜索、直取 ID、下载、批量和导出入口都执行相同授权策略。

解除指导后停止新的选择和源模板下载。既有学生材料按其自身授权保留历史引用，不因此向新导师开放旧导师模板库。

### 9.5 拟议 API

以下接口尚未实现，最终名称与请求模型需在后端契约评审中确认。

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/saas/v1/teacher/material-templates` | 创建模板草稿并上传首个 DOCX 版本 |
| `GET` | `/api/saas/v1/teacher/material-templates` | 列出当前教师自己的模板 |
| `GET` | `/api/saas/v1/teacher/material-templates/{id}` | 获取当前教师有权管理的模板详情 |
| `POST` | `/api/saas/v1/teacher/material-templates/{id}/versions` | 上传新版本，不覆盖旧版本 |
| `POST` | `/api/saas/v1/teacher/material-templates/{id}/versions/{version_id}/publish` | 发布已通过校验的版本 |
| `POST` | `/api/saas/v1/teacher/material-templates/{id}/archive` | 停止新的使用，保留历史引用 |
| `GET` | `/api/saas/v1/me/material-templates` | 列出当前学生在指定且已鉴权业务上下文中可用的模板 |
| `GET` | `/api/saas/v1/material-template-versions/{id}/download` | 鉴权后下载具体版本 |

契约要求：

- 复用可信请求上下文，不从请求体接受身份、租户或权限授予字段。
- JSON 响应沿用现有 SaaS `data/meta` 与 `error` 结构；下载成功返回文件，失败返回安全错误。
- 变更响应的命令元数据沿用 [SaaS 契约](../../backend/app/core/saas_contract.py)。幂等键格式与作用域须另行明确，不能只在 UI 禁用按钮。
- 拟采用 401 表示无有效会话，403 表示明确的能力或成员限制，404 表示不可访问或不存在的资源，409 表示版本或幂等冲突。
- 上传体积、媒体类型和字段校验失败分别使用约定的 413、415、422；这些是新增接口建议，不表示现有 API 已统一。
- 学生列表中的 `source`、来源名称和版本由服务端返回。学院来源与导师来源明确区分，不能由前端依据文件名猜测。
- 学院统一要求默认保持有效；导师模板作为补充，不自动替代必交材料规则。

### 9.6 文件、历史与审计

- 仅接收批准类型，校验扩展名、文件结构、体积与解压资源上限；不信任客户端 MIME 声明。
- 文件使用不可猜测标识，并存入非公开受控位置。租户存储前缀是新功能目标，不描述为当前全站已完成。
- 链接生成与实际读取均重新鉴权；旧链接不能绕过撤权。
- 复用已有安全校验能力，是否增加恶意文件扫描在实施前明确。不得未经授权把论文或模板上传到外部扫描服务。
- 模板源文件属于用户明确发布的持久化资产，与“上传检查后清理”的临时文件不同；需明确保留期限与删除政策。
- 首版以归档代替硬删除。清理仍被历史材料引用的资产需要独立授权与引用核验。
- 审计记录主体、动作、资源、版本、结果、请求 ID 和必要原因，不记录正文、凭据或文件二进制。

### 9.7 独立放行条件

必须覆盖教师 A/B、各自学生、未绑定学生、跨租户用户、停用成员、撤销指导关系等组合。

对列表、详情、版本发布、下载、归档、历史引用和重复提交分别执行允许与拒绝测试。只有页面隐藏或 mock 测试，不足以证明资源隔离完成。
