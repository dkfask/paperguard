# PaperGuard 单学校架构与 UI 调整方案

> 评估日期：2026-09-11  
> 适用范围：单学校 / 单学院试点，兼顾后续多租户演进  
> 当前基线：FastAPI + Vue 3，SQLite + JSON，Docker 单实例部署，论文业务闭环已基本落地  
> 目标：将“能完成业务流程的原型型单体”调整为“学校可以长期运营、维护和扩展的模块化产品”

---

## 1. 总体判断

当前项目的核心问题不是缺少更多业务实体，而是**边界和承载方式不够清晰**：

- 后端的工作流、过程材料、归档、通知、权限和存储逻辑大量集中在 API 文件中；
- `Workflow.vue` 同时承载学校管理员、教师、学生三种完全不同的工作台；
- 顶部导航同时混合学生写作、教师审核、学校配置和系统设置；
- 当前“组织作用域”已经存在，但认证、文件访问、模板、规范和项目授权还没有统一经过一个边界层；
- SQLite + JSON 适合当前单实例试点，但不适合继续无结构地增加查询、报表、租户和计费逻辑；
- UI 已有较好的视觉基础，但信息密度、操作层级、状态表达和移动端工作流仍需重新组织。

因此建议采用以下总策略：

> **不立即微服务化；先做模块化单体、统一授权、明确领域边界，再把 UI 改造成角色化工作台。**

目标架构如下：

```text
┌──────────────────────────────────────────────────────┐
│                    Vue 3 Web App                    │
│  Application Shell                                   │
│  ├── Student Workspace                               │
│  ├── Teacher Workspace                               │
│  ├── College Admin Console                           │
│  └── School Admin Console                            │
└───────────────────────┬──────────────────────────────┘
                        │ API / typed error / request_id
┌───────────────────────▼──────────────────────────────┐
│                 FastAPI Modular Monolith              │
│  Auth & Scope → Domain Services → Repositories        │
│  ├── Identity / Organization                          │
│  ├── Policy / Template                                │
│  ├── Cohort / Stage / Participant                      │
│  ├── Project / Version / Check                         │
│  ├── Submission / Review / Comment                     │
│  ├── Process Materials / Archive                       │
│  ├── Notification / Outbox                             │
│  ├── Audit / Data Governance                            │
│  └── Usage / AI Gateway                                │
└───────────────┬─────────────────────┬─────────────────┘
                │                     │
        ┌───────▼────────┐    ┌───────▼────────┐
        │ Relational DB  │    │ File Storage   │
        │ SQLite first   │    │ uploads/archive│
```

## 2. 后端整体架构调整

### 2.1 采用模块化单体，不立即拆微服务

单学校阶段不建议引入 Kubernetes、服务网格或多个独立微服务。当前最合适的是：

- 一个 FastAPI Web 进程；
- 一个可独立启动的 Worker 进程；
- 一个数据库；
- 一个受控文件存储目录；
- 必要时增加定时调度进程。

这样既能保留事务一致性，也能避免把提交、审核、归档拆到多个服务后产生分布式事务问题。

微服务拆分应满足真实条件后再考虑，例如：检查引擎、AI 网关或归档处理已经具有独立资源需求、独立发布节奏和明确容量瓶颈。不能仅因为某个 Python 文件变长就拆成网络服务。

### 2.2 后端目录建议

当前 `backend/app/api/workflow.py` 和 `process_records.py` 承载的职责过多，建议逐步调整为以下边界：

```text
backend/app/
├── api/                       # 只负责 HTTP、参数、依赖和响应
│   ├── auth.py
│   ├── organizations.py
│   ├── members.py
│   ├── templates.py
│   ├── policies.py
│   ├── projects.py
│   ├── cohorts.py
│   ├── stages.py
│   ├── participants.py
│   ├── submissions.py
│   ├── reviews.py
│   ├── process_records.py
│   ├── notifications.py
│   ├── archives.py
│   ├── reports.py
│   ├── audit.py
│   └── admin.py
├── domain/                    # 业务规则、状态机和领域错误
│   ├── identity/
│   ├── organization/
│   ├── policy/
│   ├── writing/
│   ├── workflow/
│   ├── archive/
│   └── governance/
├── services/                  # 用例服务，编排事务和领域对象
│   ├── access_service.py
│   ├── cohort_service.py
│   ├── submission_service.py
│   ├── review_service.py
│   ├── archive_service.py
│   ├── notification_service.py
│   ├── export_service.py
│   └── data_governance_service.py
├── repositories/              # 数据访问与范围查询
│   ├── user_repository.py
│   ├── project_repository.py
│   ├── workflow_repository.py
│   ├── file_repository.py
│   └── audit_repository.py
├── workers/                   # 可重复、可恢复的后台任务
│   ├── runner.py
│   ├── handlers.py
│   └── scheduler.py
├── contracts/                 # API 请求/响应 DTO 与错误码
│   ├── common.py
│   ├── workflow.py
│   └── admin.py
└── db.py                      # 连接、迁移、事务基础设施
```

迁移不要求一次性重写全部代码。建议按以下方式渐进：

1. 先把授权、状态变更和审计从 API 中抽成服务函数；
2. 再把工作流 JSON 读写集中到 repository；
3. 最后将 API 文件按领域拆小；
4. 每一步保持原接口兼容，并增加领域级测试。

### 2.3 统一请求上下文和授权边界

所有需要登录的请求应产生统一上下文：

```python
RequestContext(
    actor_id="...",
    role="teacher",
    organization_ids=["..."],
    school_id="...",
    request_id="...",
    locale="zh-CN",
    timezone="Asia/Shanghai",
)
```

授权服务统一接收：

```text
actor + action + resource + organization_scope + business_state
```

而不是让每个接口自行判断 `role == admin` 或 `can_manage(user)`。

建议使用明确的动作权限：

| 动作 | 示例 |
|---|---|
| `project.read_draft` | 学生本人、当前指导教师、获授权管理员 |
| `project.read_submission` | 提交相关学生和审核责任人 |
| `file.download` | 必须回到被引用的项目/提交进行授权 |
| `policy.publish` | 具有对应组织范围的管理员 |
| `cohort.publish` | 批次归属组织的管理员 |
| `archive.download` | 归档责任人或获授权角色 |
| `audit.read` | 学校/学院范围内的审计角色 |

**特别调整：**图片、材料附件、归档 ZIP、检查报告不能通过“用户是教师/管理员”直接放行，必须解析资源所属的项目、提交、批次和组织后再授权。

### 2.4 状态机从散落字符串调整为领域定义

当前前后端存在大量状态字符串。建议建立单一状态定义，至少包含：

- 阶段参与状态；
- 提交状态；
- 批注状态；
- 过程材料状态；
- 归档任务状态；
- 账号状态；
- 后台任务状态。

每个状态定义：

```text
状态名称
允许进入的事件
允许执行的动作
执行角色
需要写入的审计事件
需要发送的通知
```

例如：

```text
submitted
  ├── teacher.return → needs_revision
  ├── teacher.approve → approved
  ├── student.withdraw → withdrawn
  └── archive.start → rejected（非终稿不允许直接归档）
```

状态变化必须由领域服务完成，前端只能发起事件，不能自行推断成功状态。

### 2.5 数据存储演进

#### 单学校当前阶段

SQLite 可以继续使用，但需要补齐：

- 版本化迁移表 `schema_migrations`；
- 统一事务入口；
- 关键对象独立索引；
- `created_at / updated_at / revision`；
- 外键约束和软删除策略；
- 审计表与业务记录分离；
- 文件引用表与业务对象解耦；
- 工作流列表禁止通过 `list_all()` 后在 Python 中随意筛选。

#### 后续规模阶段

在出现以下任一条件时迁移 PostgreSQL：

- 多学院并发提交明显增加；
- 需要多个 Web 实例或多个 Worker；
- 报表查询开始影响写作和提交；
- 租户/组织数据需要数据库级隔离；
- 学校要求更强的备份、恢复和审计能力。

迁移时保留领域服务和 repository 接口，不让业务代码直接依赖 SQLite 专有行为。

### 2.6 后台任务独立化

归档、导出、检查、通知和清理不应长期依赖 FastAPI `BackgroundTasks`。建议统一为持久任务：

```text
POST /api/archives
  → 创建 job(state=queued)
  → 事务写 outbox/audit
  → 返回 202 + job_id

worker
  → claim（租约）
  → running
  → 生成临时制品
  → 校验摘要
  → 原子登记
  → succeeded / failed
```

任务至少需要：

- `job_id`、业务对象 ID、任务类型；
- 最大重试次数、退避时间；
- `lease_until` 和 `lease_token`；
- 可展示的用户错误与内部诊断错误；
- 死信或人工处理状态；
- 重启后可恢复；
- 同一幂等键不能重复生成有效制品。

单学校阶段可以使用 SQLite jobs 表 + 独立 Worker，不必立即引入 Redis/Celery。只有在任务量、并发或部署规模证明需要时再更换队列。

### 2.7 配置与可观测性

当前环境变量和系统设置较分散。建议建立配置分类：

```text
RuntimeConfig       服务地址、端口、数据库、文件目录
SecurityConfig      会话时长、上传限制、CORS、密码策略
WorkflowConfig      任务重试、租约、保留期、并发限制
AIConfig            模型、供应商白名单、超时、预算与开关
DeploymentConfig    学校标识、时区、语言、备份位置
```

增加：

- `/health/live`：进程是否存活；
- `/health/ready`：数据库、文件目录、必要依赖是否可用；
- `request_id`、`job_id`、`actor_id` 结构化日志；
- 错误日志脱敏，不记录论文全文、API Key 和完整 Token；
- API 延迟、任务队列、归档失败、文件缺失、授权拒绝等指标；
- 管理员可见的系统状态页。

## 3. 前端整体架构调整

### 3.1 从“单一 Workflow 页面”调整为角色化工作台

当前 `Workflow.vue` 同时处理管理员、教师和学生，已出现大量条件分支和内嵌表单。建议保留统一壳层，但拆分工作台：

```text
AppShell
├── StudentWorkspace
│   ├── StudentOverview
│   ├── MyTasks
│   ├── MySubmissions
│   ├── MyMaterials
│   └── Notifications
├── TeacherWorkspace
│   ├── TeacherOverview
│   ├── ReviewQueue
│   ├── StudentProgress
│   ├── ReviewDetail
│   └── Notifications
├── CollegeAdminWorkspace
│   ├── AdminOverview
│   ├── Cohorts
│   ├── CohortDetail
│   ├── Members
│   ├── PoliciesTemplates
│   ├── Archives
│   ├── Reports
│   └── Audit
└── SchoolAdminWorkspace
    ├── SchoolSettings
    ├── OrganizationTree
    ├── RoleScope
    ├── IdentityIntegration
    ├── AISettings
    └── DataGovernance
```

不要继续把新功能全部添加到 `Workflow.vue`。建议先从其中抽出：

- `TaskCard`；
- `StatusBadge`；
- `DeadlineLabel`；
- `NotificationInbox`；
- `ReviewQueue`；
- `ReviewEvidence`；
- `StageConfigForm`；
- `MemberImportWizard`；
- `ArchiveJobStatus`；
- `DataTable`；
- `EmptyState`、`ErrorState`、`LoadingState`。

### 3.2 新的导航结构

当前顶栏同时放置“我的论文、业务闭环、写作规范、模板管理、组织与作用域、教师管理、用户管理、AI 设置”，随着功能增长会继续拥挤。建议按角色采用侧边栏或二级导航。

#### 学生

```text
工作台
我的任务
我的论文
提交记录
过程材料
消息
帮助
```

#### 教师

```text
工作台
待审核
学生进度
过程材料
规范与要求
消息
帮助
```

#### 学院管理员

```text
概览
批次与阶段
成员与指导关系
模板与规范
提交与归档
统计报表
审计记录
消息
帮助
```

#### 学校管理员

```text
学校概览
组织与成员
模板与规范
学院与批次
权限与认证
数据治理
AI 与系统设置
审计与运行状态
```

顶部保留：

- 当前学校/学院范围；
- 当前批次或工作空间；
- 未读消息；
- 帮助/反馈；
- 账号菜单。

管理员功能不再主要依赖顶栏弹窗。弹窗只适合确认、快速编辑和轻量操作；成员导入、阶段配置、审计查询和数据导出应使用独立页面。

### 3.3 统一页面结构

每个管理页面采用固定结构：

```text
页面标题 + 说明
├── 面包屑 / 当前组织范围
├── 页面级主操作
├── 指标摘要（需要时）
├── 筛选和搜索
├── 主列表或工作区
└── 分页、批量操作和帮助说明
```

每个页面必须设计以下状态：

- 首次加载；
- 空数据；
- 无权限；
- 网络失败；
- 版本冲突；
- 后台任务进行中；
- 数据已被其他人更新；
- 操作成功后的下一步。

不能只显示一个通用的“操作失败”。错误信息应包含：发生了什么、是否已保存、用户下一步做什么、`request_id` 在哪里。

## 4. 关键 UI 重构方案

### 4.1 学生端：从“功能列表”调整为“下一步任务”

学生首页的核心不是显示所有功能，而是回答三个问题：

1. 我现在处于哪个阶段？
2. 我最应该处理什么？
3. 截止时间和阻塞原因是什么？

建议首页结构：

```text
欢迎信息 + 当前批次
┌────────────────────────────────┐
│ 当前主任务                     │
│ 初稿 / 终稿 · 距截止 5 天       │
│ 阻塞：摘要字数不足              │
│ [继续写作] [查看要求]           │
└────────────────────────────────┘

待处理事项
├── 退回批注 2 条
├── 必交材料 1 项
└── 待确认的新规范版本

阶段时间线
未开始 → 进行中 → 待审核 → 需修改 → 已通过 → 已归档

最近提交 / 消息 / 帮助
```

“上传检查”不应与学生正式任务并列为同等主入口。它可以作为写作页中的检查工具，或放在“工具”区域，避免学生误以为上传检查就是正式提交。

### 4.2 写作页：保持写作专注，减少管理干扰

现有 Writer 是核心体验，应继续以正文为中心：

```text
顶部：论文标题 · 当前阶段 · 保存状态 · 规范版本 · 提交
左侧：章节树
中间：正文编辑区
右侧：
  ├── 检查问题
  ├── 当前写作依据
  ├── 教师批注
  └── 提交门禁
底部：版本、恢复、快捷键和帮助
```

需要调整：

- 将“当前规范包”固定为可折叠面板，不与正文争夺空间；
- 检查问题按“阻断 / 警告 / 建议 / 未覆盖”分组；
- 每条问题显示来源、版本、实际值、期望值和位置；
- 自动修复必须先预览差异，生成新草稿版本；
- 保存冲突使用专门的冲突面板，不使用普通错误条幅；
- 提交入口显示清晰的候选版本、检查时间、门禁和警告确认；
- 手机端只提供查看要求、检查摘要、批注和轻量修改，不强行复刻完整编辑器。

### 4.3 教师端：从“任务列表 + 长详情”调整为审阅工作台

教师最重要的是处理待办，而不是浏览整个系统。

建议布局：

```text
顶部：待审核 8 · 超时 2 · 本周已完成 12

左侧筛选：
批次 / 阶段 / 状态 / 迟交 / 等待时长

中间列表：
学生 · 论文 · 提交编号 · 截止状态 · 检查摘要 · 等待时间

右侧或独立详情页：
固定提交快照
检查门禁
批注列表
人工核验清单
[退回修改] [通过提交]
```

关键原则：

- 审阅页明确标注“固定提交快照”，不能混入学生当前草稿；
- 批注锚点失效时显示原文片段和失效提示，不跳到相似文本；
- 退回操作必须要求原因和修订截止；
- 通过操作显示尚未完成的人工核验和阻断批注；
- 审核完成后自动进入下一条待办或回到筛选列表；
- 通过、退回和批注按钮固定在可见操作区，不让教师滚到正文末尾找按钮。

### 4.4 管理员端：从“业务页面堆叠”调整为配置向导 + 数据表

管理员页面应优先支持高频校务动作：

#### 批次创建向导

```text
1. 基本信息
2. 组织与学年
3. 导入学生
4. 分配教师
5. 配置阶段
6. 选择模板与规范
7. 发布预检
8. 确认发布
```

每一步显示阻断项、警告项、影响人数和返回修改入口。

#### 成员导入

采用：

```text
上传 / 粘贴 → 字段映射 → 预检 → 错误清单 → 确认有效行 → 结果报告
```

管理员不应填写 `student_id, teacher_id` 这样的内部 ID。应支持：

- 学号、工号、姓名、邮箱等业务字段；
- 自动匹配已有账号；
- 同名和重复账号人工确认；
- 指导教师下拉搜索；
- 失败行单独重试；
- 导入结果可下载。

#### 阶段配置

拆成四个标签页：

1. 基本信息与时间；
2. 模板、规范与版本；
3. 必交材料与门禁；
4. 发布预览与影响范围。

不要把所有字段放在一个长表单中。发布前必须明确显示：成员数、缺失教师数、缺失模板/规范数、截止时间、预计通知人数和配置版本。

### 4.5 归档、审计和数据治理 UI

这些能力不能长期埋在工作流底部。

#### 归档中心

- 待归档、生成中、成功、失败、被替代；
- 按批次、阶段、学生、时间筛选；
- 归档 manifest、文件摘要、依据版本和审核历史；
- 失败原因、重试、下载授权；
- 更正归档与前版关联。

#### 审计中心

- 操作者、时间、组织、对象类型、动作、结果、原因筛选；
- 查看单次事件详情和关联 request/job ID；
- 支持导出审计记录；
- 正文和密钥默认不出现在审计列表中；
- 临时支持访问必须有独立标识和过期时间。

#### 数据治理

- 保留策略按数据类型展示；
- 回收站、待清理、法律保留、清理失败；
- 机构级数据导出任务；
- 备份最近成功时间和最近恢复演练结果；
- 学校管理员可查看但不能绕过资源授权下载正文。

## 5. 视觉和交互系统调整

### 5.1 保留现有视觉优点

当前 `style.css` 已建立较完整的颜色、圆角、按钮、卡片、响应式基础，建议保留：

- 蓝色主色和清晰的状态色；
- 低阴影、轻边框、较克制的卡片；
- Material Symbols 图标体系；
- 中英文基础字体栈；
- 现有写作页的轻量、专业气质。

### 5.2 从“所有内容都是卡片”调整为层级化布局

建议减少大面积卡片嵌套，使用三种容器层级：

1. **页面层**：背景和主要内容区域；
2. **工作区层**：列表、编辑区、审阅区；
3. **操作层**：表单、确认、抽屉和弹窗。

管理页面优先使用表格、筛选条、分段导航和时间线；卡片只用于摘要和关键任务，不要把整个流程每一步都包成独立卡片。

### 5.3 统一状态表达

状态必须同时提供：

- 文字；
- 图标；
- 颜色；
- 必要时的下一步动作。

建议状态体系：

| 类型 | 颜色 | 示例 |
|---|---|---|
| 进行中 | 蓝色 | 检查中、待审核、同步中 |
| 需要处理 | 橙色 | 需修改、即将截止、待补材料 |
| 成功 | 绿色 | 已通过、已归档、已同步 |
| 阻断/失败 | 红色 | 检查失败、权限不足、归档失败 |
| 未开始/未覆盖 | 灰色 | 未开始、未检查、无数据 |

“警告”和“阻断”必须在颜色、文案和按钮行为上明确区分。

### 5.4 统一反馈方式

避免在同一页面混用 `alert`、`confirm`、顶部条幅和局部错误文本。建议建立：

- `Toast`：短暂成功提示；
- `InlineError`：字段级错误；
- `ErrorBanner`：页面级错误和 request ID；
- `ConfirmDialog`：删除、发布、重开、退回等不可逆或高影响动作；
- `JobStatus`：导出、归档、检查等异步任务；
- `ConflictPanel`：版本冲突和本地恢复。

`window.prompt` 不适合正式校务流程。关闭批次、重开任务、退出学生和更正归档应使用结构化对话框，提供理由字段、影响范围和确认摘要。

### 5.5 可访问性和响应式

- 所有图标按钮必须有可读 `aria-label`；
- 模态框打开后聚焦标题或首个输入，关闭后恢复原焦点；
- 键盘可以完成筛选、表格、批注和审核操作；
- 不能只用颜色区分状态；
- 表格在移动端提供卡片或横向滚动替代方案；
- 移动端底部可固定主要操作，但不能遮挡正文；
- 复杂表单支持保存草稿和离开提示；
- 统一接入 i18n，逐步消除工作流、组织、规范页面的中文硬编码。

## 6. 推荐路由和组件改造顺序

### 阶段 A：不改变后端契约的 UI 重构

1. 建立 `AppShell`、角色导航和权限感知菜单；
2. 将 `Workflow.vue` 拆为学生、教师、管理员三个容器；
3. 抽取状态、通知、任务卡、表格、异步任务和错误组件；
4. 把管理员弹窗迁移为独立页面；
5. 增加独立消息页、归档页和审计占位页；
6. 移除 `window.prompt`，统一结构化对话框。

### 阶段 B：后端模块化和统一授权

1. 抽取 `access_service`；
2. 修正媒体、附件、模板、规范批量升级的资源授权；
3. 抽取 workflow repository 和领域服务；
4. 建立统一错误码、request ID 和状态定义；
5. 将归档、导出、通知迁移到独立 Worker；
6. 增加权限负向测试和恢复测试。

### 阶段 C：单学校运营能力

1. 成员/指导关系向导；
2. 批次发布向导；
3. 学院运营看板；
4. 数据治理、备份和导出页面；
5. AI 设置、预算和调用记录；
6. 邮件/企业微信等通知适配器；
7. 学校统一认证适配器。

### 阶段 D：后续 SaaS 演进

1. 增加显式 tenant；
2. 将 repository 查询全部纳入租户上下文；
3. 数据库迁移 PostgreSQL；
4. 文件存储切换为对象存储；
5. 增加套餐、权益、用量和账务；
6. 只有在真实规模需要时再进行服务拆分。

## 7. 推荐验收标准

### 架构验收

- API 层不直接实现复杂状态转换和跨表业务规则；
- 所有正文、图片、附件、报告和归档下载复用统一授权服务；
- 所有异步任务可查询、可重试、可恢复；
- 审计记录与可变业务记录分离；
- 数据库迁移可重复执行并有失败恢复策略；
- Worker 与 Web 进程可以独立重启；
- 关键日志包含 request/job 关联信息且不泄露论文正文和密钥。

### UI 验收

- 学生、教师、学院管理员登录后看到不同且清晰的工作台；
- 管理员无需内部 ID 即可完成成员导入和指导关系分配；
- 教师从待办列表到审核决定不超过明确的连续操作路径；
- 学生首页能在一个视图中看到当前阶段、截止时间、阻塞原因和主操作；
- 发布、退回、重开、归档、导出都有影响范围和下一步提示；
- 加载、空数据、无权限、网络失败、冲突和任务进行中状态均有专门 UI；
- 桌面端和移动端主要任务无遮挡；
- 键盘、屏幕阅读器和中英文长文案不会破坏关键流程。

### 业务验收

至少使用以下样本进行端到端演练：

- 两个学院；
- 多名教师和学生；
- 两个阶段；
- 两套规范版本；
- 含图片、表格和过程材料的论文；
- 教师转交、延期、退回、更正归档、文件缺失和服务重启场景。

## 8. 最终建议

如果只做一轮架构和 UI 调整，建议按以下顺序执行：

> **先统一授权和任务边界，再拆角色工作台；先把大页面拆成可复用组件，再把后台任务独立化；最后补齐管理控制台、审计、数据治理和移动端体验。**

不建议当前阶段：

- 直接把系统拆成多个微服务；
- 为了“看起来像 SaaS”强行引入复杂租户计费；
- 继续向 `Workflow.vue` 添加更多条件分支；
- 用顶栏弹窗承载成员、批次、审计和数据治理；
- 在没有统一授权服务前继续增加文件下载和外部集成。

单学校阶段的理想目标不是“功能最多”，而是：

> **学校管理员能配置，教师能高效审核，学生知道下一步，论文和过程材料可追溯，系统在失败后可恢复。**

达到这一目标后，再引入租户、SSO、计费和多机构扩展，整体风险最低。
