## 0. 本规格要解决什么

W-07 管的是**「论文正文发到哪里去、用谁的密钥发、租户同不同意」**。
§24.2 归给它 **4 条 AT**（AT-16、AT-17、AT-18、AT-19 前半）。

2026-10-04 已补部分基础保护；**仍缺租户外发政策与成员级 BYOK 域**，存量无租户映射路径的隐式回退也仍需迁移契约约束。

### 0.1 现状取证（2026-10-04，基础实现后重绑）

| # | 事实 | 位置 | 与设计的关系 |

> **第 1 条是本包最严重的一条**，因为它不是「没做」，是「做成了另一个东西」：
> ADR-03 明确选择「**全局账号** + 租户成员/组织授权」——
> 也就是说，**一个用户天然可能在多个租户里有不同角色**（AT-01 的场景）。
> 而 BYOK 配置挂在**全局账号**上，只有一份。
> 结论：**当前架构下，一个在 A 校配了 BYOK 的教师，在 B 校也会用这份密钥。**
> 论文正文的流向因此不受租户边界约束。

## 1. 租户 AI 政策（TP）

### 1.1 解析顺序必须整体替换

§13.1 的目标顺序（**先判政策，再判配置来源**）：

```text
租户禁止外发                      → 不调用外部 AI
允许成员 BYOK 且存在有效本租户成员配置 → 使用该配置
否则存在有效租户默认                → 使用租户默认
否则允许平台回退且具备平台 AI 权益   → 使用平台供应商池
否则                              → 明确返回 AI_NOT_CONFIGURED / AI_POLICY_DENIED
```

当前实现（`ai.py:110-154`）是**另一套**：

```text
租户/成员身份校验 → 用户配置（全局账号级）→ 作用域数据库配置 → 平台全局/环境变量 → None
```

两者的差别不是顺序微调，是**缺了整整一层**：

| # | 规则 | 说明 |
|---|---|---|
| TP-1 | 解析入口必须是 `resolve_ai_config(ctx: RequestContext, ...)`，**必须接收已解析的 `RequestContext`** | 现有 `_resolve_cfg(store, user)` 的入参是 `user: dict`，已有服务端成员解析的租户字段，但尚未冻结为完整租户政策和成员凭据作用域 |
| TP-2 | 政策判定**先于**任何配置来源判定；政策为「禁止外发」时**立即拒绝**，不进入来源解析 | §13.1 首行 |
| TP-3 | 平台回退**必须显式允许**（租户政策 + 具备平台 AI 权益），不得自动发生 | §13.1 第 4 行与「共享 SaaS 中必须显式允许」 |
| TP-4 | 租户未配置 ⇒ **不得**借用平台配置；返回 `AI_NOT_CONFIGURED` | 直接推翻 `backend/tests/test_ai_tenant_isolation.py:118` 的 `test_unconfigured_tenant_falls_back_to_global` |
| TP-5 | 解析结果必须返回**来源枚举**（`tenant_default` / `member_byok` / `platform_pool`），供 `/status`、`/disclosure` 与 W-08 冻结使用 | 现有 `source` 只有 `"user"` / `"system"` 两种，**丢失了归属维度** |
| TP-6 | `/status`、`/disclosure`、`/assist` **必须共用同一个解析函数** | 现有三处各自调用 `_resolve_cfg`（`ai.py:644`、`ai.py:663`），一旦分叉就会出现「状态说可用、实际拒绝」 |

> **TP-1 是本节最容易被低估的一条。**
> 现有 `_resolve_cfg(store, user)` 的签名里**没有租户**。
> W-03 定义的 `RequestContext`（`backend/app/core/context.py:16-64`）
> 恰恰就是为了解决这个——**本包必须等 W-03 落地后才能改**，
> 否则会做出「再传一个 `tenant_id` 参数」的临时方案，
> 而那正是 §8.1 `context_resolution_check` 报出的 **114 处全局 `role` 引用**同一类问题。

### 1.2 政策可约束的维度

§13.1：「租户可限制**供应商、模型、接口协议、可发送内容类别及平台回退**。」

| # | 规则 | 说明 |
|---|---|---|
| TP-7 | 政策存于 `tenant_settings`（§9.3），**有 `schema_version` 与显式继承规则** | 不得散落在环境变量 |
| TP-8 | 「可发送内容类别」必须在**派发前**判定，且判定结果进入请求事实（W-08） | 否则事后无法证明当次外发是否合规 |
| TP-9 | 政策变更**立即生效**于后续请求；已冻结在历史请求上的 `policy_version` **不变** | §13.1「不在异步结算时读取『现在的学校默认』来解释历史请求」 |
| TP-10 | 配置测试（`ai.py:452-542`）**必须走同一套政策与出站限制** | §13.1「不得作为绕过额度的隐藏入口」；现有实现已满足（内部调用 `_metered_chat`），**保留** |

| # | 规则 | 说明 |

> 验收必须能证明：**删掉旧列后，全部 AI 用例仍然通过**。

## 3. 密钥格式与轮换（SK）

### 3.1 现状与目标的差距

| 现状 | 目标（§13.2） |
|---|---|
| `pgsec1$` 前缀仍同时承载新 AES-GCM 与旧认证流兼容读取（`secret_store.py:24`、`secret_store.py:81-126`） | 受维护的 **AEAD**，AAD 绑定租户/凭据 ID/用途 |
| 无 `key_id`、无 `algorithm`、无格式版本字段（仅靠 `pgsec1` 前缀） | 保存 `algorithm`、`format_version`、`key_id`、`nonce`、密文 |
| 缺主密钥已经拒绝读写（`secret_store.py:51-57`） | 新写入**失败关闭** |
| 解密失败抛出异常（`secret_store.py:125-126`）；部分 API 的结构化故障响应尚未覆盖 | 返回**明确不可用状态**，不得回退到另一供应商 |
| 无轮换机制 | 先双读 → 重加密 → 核对 → 才退役旧 key |

### 3.2 规则

| # | 规则 | 说明 |
|---|---|---|
| SK-1 | 新密文格式使用标准 AEAD，**AAD 绑定 `tenant_id` + `credential_id` + 用途** | §13.2 第 1 条。AAD 绑定用途意味着「学生配置的密钥」不能被当作「平台凭据」解密 |
| SK-2 | 密文保存 `algorithm` / `format_version` / `key_id` / `nonce` / 密文；**nonce 在同一 `key_id` 下不得重复** | §13.2 第 2 条 |
| SK-3 | 随机源必须正确（CSPRNG）；不得为性能或便利改用可预测源 | §13.2 第 2 条 |
| SK-4 | 主密钥**不得**出现在数据库、报告、Git、浏览器或对象清单中 | §13.2 第 3 条 |
| SK-5 | 新商业写入缺主密钥或密钥不可用 ⇒ **失败关闭**，返回 `AI_CREDENTIAL_UNAVAILABLE` | 基础加密写入已 fail-closed；所有 API 出口仍须满足本条 |
| SK-6 | 存量明文/`pgsec1` 数据：先**验证可解密**，再在受控迁移中重加密；**不自动在线批量覆盖生产密钥** | §13.2 第 6 条 |
| SK-7 | 迁移过程**不得**在日志打印旧值 | §13.2 第 6 条 |
| SK-8 | 轮换顺序固定：部署双版本读取 → 重加密 → 核对完成 → 才退役旧 `key_id` | §13.2 第 7 条。**顺序颠倒会产生一段「旧密钥已退役但数据未重加密」的不可读窗口** |
| SK-9 | 保留经批准的恢复密钥来源 | §13.2 第 7 条 |
| SK-10 | 错误密钥 / 密文篡改 / key 丢失 ⇒ **明确不可用**；**禁止**回退到另一供应商发送正文 | §13.2 第 8 条。**这是本包与 §2 组合后最关键的一条**，见下 |
| SK-11 | 密钥不可用**不得**冻结普通论文阅读 | §13.2 第 5 条：「不为了加密故障冻结全部教学业务」 |
| SK-12 | 自定义加密实现**不得**继续被当作「无需安全评审」的标准方案 | §13.2 首段；ADR-06 |

### 3.3 SK-10 的历史失效链与回归要求（必须单独验证）

下面是旧实现的复合失效链。2026-10-04 已不再静默置空，但其他配置读写出口与故障覆盖仍需核对；必须保留“不回退发送正文”的集成回归：

```text
主密钥配错 / 密文被篡改
  → secret_store.reveal_config() 捕获 SecretDecryptError
  → secret_store.py:166   out[field] = ""            （降级为「未配置」）
  → ai._resolve_cfg()      all(cfg.get(k) for k in (...,"api_key",...)) 判定不通过
  → 继续回退到 _system_cfg()
  → 用**平台/另一租户的供应商**发送论文正文
```

**设计要求是「明确不可用」（SK-10），实现结果是「换一个供应商继续发」。**
最后一行是**数据治理事故**：正文流向了一处从未被批准的处理器，
而且**没有任何记录表明发生过这次改道**——因为 `record_usage` 记的是
解析后的 `source`，它会是 `"system"`，看起来完全正常。

> **验收要求**：必须有一条测试构造「密钥不可读」，
> 断言结果是 `AI_CREDENTIAL_UNAVAILABLE`，
> 且断言**上游客户端一次都没有被构造**（不只是断言错误码）。
> 只断言错误码的测试会被「回退成功」的假象骗过。

## 4. 出站限制（OB）

### 4.1 保留现有能力

`outbound_guard.assert_safe_outbound_url`（`services/outbound_guard.py:137`）
已在派发前调用（`ai.py:471`），阻断私网、环回、链路本地（含 `169.254.169.254`，
见 `outbound_guard.py:67-76`）与 IP 简写。**这部分是本包唯一已经做对的资产。**

| # | 规则 | 说明 |
|---|---|---|
| OB-1 | 出站校验**必须**保持在**派发之前**，且先于配额占用 | 现有顺序（`ai.py:471-542` `begin_call`）正确，保留 |
| OB-2 | 保存配置时（`ai.py:309` 附近的 `_request_cfg`）与派发时**都**校验 | 现有保存时 `resolve_dns=False`、派发时 `resolve_dns=True`，双点校验保留 |
| OB-3 | 域名白名单/私网放行开关属**部署配置**，不得由租户或用户侧请求控制 | `outbound_guard.py:56` 的 `_allow_private_network` |
| OB-4 | **必须**配合外部网络出口控制 | §13.1 明写；应用层校验**不是**唯一防线 |

### 4.2 DNS 重绑定的能力边界（如实声明）

| # | 规则 | 说明 |
|---|---|---|
| OB-5 | 必须在解析后、连接前做校验，并在**校验通过的地址集合**上连接 | 见下两行取证 |

取证一（应用层校验确实在解析后执行）——`outbound_guard.py:137` 的
`assert_safe_outbound_url` 在 `resolve_dns=True` 时解析并逐个检查地址。

取证二（残余窗口的来源）——`ai.py:625-632` 的 `httpx.Client`
在建立连接时**自行再次解析**同一域名，与上面的校验不在同一次解析上。

> **OB-5 是能力边界，必须写清楚而不是假装已解决。**
> 完全关闭 TOCTOU 需要「自定义传输层按已校验 IP 拨号 + 校验 Host/SNI」，
> 属于**部署形态变更**，不是本包能在应用层单独完成的。
> **如实结论**：应用层能挡住「直接写私网 IP」「环回」「元数据端点」「IP 简写」，
> **挡不住**「先返回公网 IP、第二次解析返回内网 IP」的重绑定。
> 残余风险由 OB-4 的网络出口控制承担。

### 4.3 重定向：当前安全，但是隐式的

| # | 规则 | 说明 |
|---|---|---|
| OB-6 | `httpx.Client` **显式**设置 `follow_redirects=False`，并在代码注释中写明理由 | 当前依赖 httpx 默认值（`ai.py:625`）恰好是 `False`，**行为安全但意图不可见**。一次「顺手加个 `follow_redirects=True` 支持供应商跳转」的重构就会静默打开 SSRF 面 |

> **OB-6 属于「今天对、明天可能错」的防御。**
> 它没有对应的现存缺陷，因此不登记为 INC；
> 但它必须写进规格——**因为规格是实施者读的东西，而代码注释未必被保留。**

## 5. 熔断作用域（CB）

§13.1：「供应商**认证失败/额度不足按凭据作用域**熔断，供应商**公共故障按端点**熔断；
**不能因一位 BYOK 用户密钥错误熔断全部租户**。」

现状：熔断键 = 归一化 `base_url`（`ai.py:319-326`），
且 `ai.py:390-397` 对**任何** `HTTPException` 都 `record_failure`。

| # | 规则 | 说明 |
|---|---|---|
| CB-1 | 熔断键**二级**：`credential_scope`（`tenant_id` + `credential_id`）+ `endpoint` | 单键 `base_url` 满足不了 §13.1 |
| CB-2 | HTTP **401/403**（凭据问题）⇒ 只影响该凭据作用域，**不得**计入端点级熔断 | `ai.py:393-394` 当前把 401 记进 `record_failure`，与 5xx 不可区分 |
| CB-3 | HTTP **5xx / 连接失败 / 超时** ⇒ 计入端点级熔断 | 公共故障 |
| CB-4 | 429/额度不足 ⇒ 按**凭据作用域**处理，不熔断全端点 | §13.1「额度不足按凭据作用域」 |
| CB-5 | 分类必须在**协议适配层**完成，而不是在 `_chat_completion` 的统一 `except` 里 | 现有 `except HTTPException: record_failure`（`ai.py:393-398`）**丢掉了状态码分类信息** |

> **CB-5 的问题是结构性的**：
> `_chat_completion` 是「全部上游派发的唯一出口」（其 docstring 明确说明这一点），
> 这个设计**是对的**（单一出口便于计量与熔断）。
> 但它在最外层统一捕获异常，意味着**协议层已经知道是 401 还是 503 的信息被丢弃了**。
> 正确做法不是把熔断拆散到各协议函数（那会回到「7 个派发点各自熔断」的老问题），
> 而是让协议层**返回带分类的结果对象**，由唯一出口据此分流。

## 6. 验收

| AC | 关联 AT | 判据 | 证据 |
|---|---|---|---|
| AC-07-1 | **AT-16** | 租户禁外发 / 禁 BYOK / 禁平台回退三种政策各自生效：**无任何未批准供应商调用**，且**不悄悄改来源** | 本包 §1；三类政策各一次派发探针（断言上游客户端未构造） |
| AC-07-2 | **AT-17** | 私网、环回、重定向、DNS 重绑定四类出站：应用与网络控制拒绝，**无内部资源读取** | 本包 §4；**注意 OB-5 的能力边界**——重绑定项本机无法完整验证 |
| AC-07-3 | **AT-18** | 主密钥缺失 / 错误 / 密文篡改 / 轮换中：秘密使用**受控失败**，**正文阅读独立可用**，新写**不落明文** | 本包 §3.3 失效链；断言错误码 + 断言上游客户端未构造 |

**本包无法独立验证的部分**（不得混入「通过」）：

- AT-17 的 DNS 重绑定项**在本机无法完整验证**（需可控 DNS 与网络出口），
  当前只能验证应用层对私网/环回/元数据/IP 简写的拒绝。
- AT-18 的轮换**需要两个 `key_id` 的双读窗口**，属部署级演练，不是单进程测试。
- 多租户 BYOK 隔离（BK-3/BK-4）**需要 `tenant_memberships` 表**——
  该表已存在最小运行时形状，但成员凭据域未实现；基础身份测试不等于 BK-3/BK-4 通过。

| 判据 | 静态可查？ | 处置 |
|---|---|---|
| 新表 `provider_credentials` / `tenant_settings` 是否登记 RLS 策略 | ✅ | `rls_policy_check` RL-1 自动覆盖。**2026-10-02 核实（INC-82）**：`provider_credentials` 的 DDL 原先寄居在 `docs/tenancy/system-settings-scope-inventory.md` §5（标题写着「交 W-07」，即**盘点素材**），因而**既不在 W-02 §3.3.1、也不在 §3.6 矩阵**——RL-1 一度报不出它。已迁入 **W-02 §3.3.0b** 并补齐矩阵第 25 行 + `ENABLE`/`FORCE`/`CREATE POLICY` + L3 复合外键 `(tenant_id, membership_id) → tenant_memberships(tenant_id, id)`。**该表存 `key_ref`（密钥的版本化引用），能读到这一行就等于拿到取密钥的资格**，因此**缺 RLS 的风险等级在全部 C0 表里最高** |
| 新错误码是否登记 | ✅ | `error_codes_check` EC-06 |
| 规格代码引用行号是否准确 | ✅ | `spec_citation_check`（本包 §0.1 全部引用已机器核对） |
| BK-3/BK-4 密钥不串租户 | ❌ | 运行时测试 |
| SK-10 解密失败**不得回退** | ❌ | 运行时测试（须断言上游客户端未构造） |
| CB-1 熔断作用域隔离 | ❌ | 并发/故障注入测试 |

> **本包不新增静态门禁**，与 W-04/05/06/09/10 同一判断。

> 静态 grep 只能证明某个字符串出现过，**证明不了分支走向**。
