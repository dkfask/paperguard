## 2. 追溯规则

### 2.1 一条 AT-ID 必须能回答的五个问题

| # | 问题 | 字段 |
|---|---|---|
| 1 | 验什么 | `criterion`（**必须逐字取自设计文档**） |
| 2 | 在哪个阶段、哪个工作包 | `stage` / `work_package` |
| 3 | 凭什么认为它已部分达成 | `current_evidence` + 六态 |
| 4 | 它关联哪些已知缺陷 | `related_findings` |
| 5 | 什么挡着它 | `blockers` |

**答不上第 1 问就等于没追溯**——判据必须来自设计文档，不能自己重写。重写判据是最隐蔽的偷懒：判据一软，什么都能"通过"。

### 2.2 不可编辑字段

矩阵中以下 5 个字段**由设计文档单向决定**，校验器 AT-02 逐字比对：

```text
id · stage · work_package · scenario · criterion
```

我本轮实际踩到的漂移（已修）：

| 漂移 | 我的写法 | 设计文档实际 | 后果 |
|---|---|---|---|
| AT-43/44/45 的 stage | `cross` | `按范围` / `各阶段` | 自造了设计文档没有的分类 |
| AT-44/45 的 work_package | `各阶段` | **空**（该格只有阶段名） | 凭空给它们安了工作包 |

> 两条都是我"顺手补全"的。**矩阵的价值在于如实反映设计，写着好看反而有害。**

### 2.3 可编辑字段

`related_findings` / `current_evidence` / `blockers` / `gate_state` / `note` 随进展更新，但：

- `current_evidence` 的 `state` 必须是合法六态（AT-08 校验）
- `blockers` 必须在字典中登记（AT-05 校验），不允许写自由文本
- `gate_state` 必须是 4 个合法值之一（AT-06 校验）

## 3. 证据六态与 AT-ID 的关系

全项目统一的引用规范：

| 六态 | 含义 | 能否支撑 AT 放行 |
|---|---|---|
| `local_fixed` | 本地已改 | ❌ |
| `local_gate_passed` | 本地门禁通过 | ❌ |
| `committed_pushed` | 已提交推送 | ❌ |
| `merged` | 已合并 | ❌ |
| `runtime_verified` | 运行时已验证 | ⚠️ 部分（仍需严格 UAT） |
| `strict_uat_passed` | 严格 UAT 通过 | ✅ **唯一充分条件** |

外加一个设计专用态 `design_ready`（本项目的设计产出），**它不是运行证据**，不能用于放行。

### 3.1 强制规则

> **只有 `strict_uat_passed` 能让一条 AT-ID 判为通过。**

其余五态都是"必要不充分"。矩阵里 26 条证据条目中，绝大多数是 `local_gate_passed` 与 `design_ready`——这正确反映了"本地已验证"与"已验收"之间的巨大差距。

### 3.2 `strict_uat_passed` 的最低要求

一条 AT 要标 `strict_uat_passed`，必须同时具备：

```text
□ 判据逐条命中（不是"大致通过"）
□ 环境隔离：非生产，且使用合成数据（设计文档 §24.1）
□ 真实操作路径：不是只调 API 或只看页面渲染
□ 失败路径也验证过（AT-44 明确要求"不仅页面打开"）
□ 证据可复现：命令 + 实际输出，不是结论陈述
□ 关联审计记录可查（AT-29）
```

## 4. 放行判据

### 4.1 阶段放行

| 阶段 | AT 范围 | 放行条件 |
|---|---|---|
| **C0** | AT-01～AT-34 | 全部 34 条 `strict_uat_passed` |
| **C1** | AT-35～AT-39 | C0 已放行 + MR-FIX-1～4 完成（`ai-metering-runbook.md` §5.2）+ V-1 供应商口径确认 |
| **C2** | AT-40～AT-42 | C1 已放行 |
| 跨阶段 | AT-43～AT-45 | 按其出现阶段分别放行 |

### 4.2 早停规则

以下情况**不必等全部 AT 做完**就能判定不放行：

| 条件 | 判定 |
|---|---|
| 任一 AT 的 `strict_uat_passed` 依赖未修复的安全缺陷（F-1/F-5） | ❌ 直接不放行 |
| 存在跨租户数据泄漏（AT-01～AT-06 任一失败） | ❌ **一票否决**，不进入 C1 |
| 账务不可核对（AT-36 失败） | ❌ 不进入 C2 |
| 退出/导出能力缺失（AT-31/AT-32 失败） | ❌ **合同义务未履行**，不放行 |

> **一票否决项的存在是为了防止"用平均分掩盖单点致命缺陷"。**
> 34 条里通过 33 条，不能推出"隔离基本没问题"——只要有一条能泄漏跨租户正文，就是不能上线。

### 4.3 当前 C0 的阻塞全景

按门禁统计的 21 条 `blocked_on_scope`，归因只有 **4 类**：

| 类别 | 阻塞项 | 影响 AT 数 |
|---|---|---|
| **无租户字段** | `T-ENABLE-MULTI-TENANT` | ~14 条 |
| **业务裁决未答复** | Q-07/08/09、BQ-1/2/4/5、V-1 | ~5 条 |
| **无真实 PG 实例** | `PG-REAL-INSTANCE` | 3 条（AT-04/06/45） |
| **运维能力缺失** | `OPS-FIX-5a/5b/6a/6c/7b` | 5 条（AT-28/31/32/33/34） |

> **这说明 C0 的关键路径不是技术实现，而是"打开多租户开关"和"答复业务裁决"。**
> 继续加深设计文档的边际收益已经很低——21 条阻塞中有 19 条与"能否开始"而非"怎么设计"有关。

## 5. 用例编写规则（阻塞解除后）

### 5.1 AT-ID 到测试用例的映射

```text
AT-ID
  ↓ 一一对应（不合并、不拆分）
TC-<AT-ID>-<序号>        自动化用例（pytest / Playwright）
MAN-<AT-ID>              人工验收步骤（含环境、账号、预期）
EVD-<AT-ID>-<运行标识>    证据文件（命令 + 原始输出）
```

**不允许**用一个测试覆盖多条 AT（判据会互相掩盖），也**不允许**一条 AT 拆成互不相干的多条（会漏掉中间态）。

### 5.2 每条用例必须记录

| 字段 | 要求 |
|---|---|
| 环境 | 生产 / 隔离环境 / 本地；**默认隔离** |
| 数据 | 合成数据的构造方式（设计文档 §24.1 要求两个租户、多角色） |
| 前置 | 依赖的前置 AT-ID 是否已通过 |
| 步骤 | 可被他人独立复现 |
| 实际输出 | **原始输出**，不是"符合预期" |
| 判据核对 | 逐条对照 `criterion`，不是整体印象 |
| 六态 | 最终引用哪一态 |

### 5.3 反模式（明确禁止）

| 反模式 | 为什么禁止 |
|---|---|
| 把 `criterion` 改软以让它通过 | 判据是设计文档的承诺，不是可调参数 |
| 用 `local_gate_passed` 冒充验收 | 4 轮本地回归 ≠ 严格 UAT |
| 复用旧报告冒充新运行 | 仓库已有 `check-report-version.sh` 专门防这个 |
| 只验成功路径 | AT-44 明确要求"错误恢复" |
| 多人共用一个测试账号 | 会掩盖并发与越权问题（见本轮 `ai-metering` 用例踩过的坑） |
| 视觉快照用 `--update-snapshots` 消失败 | 会关闭真实的视觉回归守护 |

## 6. 门禁

`tools/at_traceability_check.py`，退出码 0/1。

| 检查 | 判据 | 守护什么 |
|---|---|---|
| AT-01 | AT-ID 集合与设计文档**完全相同** | 不增不减不换名 |
| AT-02 | 5 个不可编辑字段**逐字一致** | 判据不被改软 |
| AT-03 | 标准阶段条目的编号与区间一致 | 阶段错配 |
| AT-04 | 全部有非空判据 | 无判据的"验收" |
| AT-05 | blocker 引用在字典中登记 | 自由文本阻塞项无法追踪 |
| AT-06 | `gate_state` 取值合法 | 状态词表收敛 |
| AT-07 | **无任何 `strict_uat_passed`** | 🔴 防越界声明 |
| AT-08 | 证据六态合法 | 防止自造状态名 |
| AT-09 | 矩阵非空壳 | 防空洞追溯 |

### 6.1 AT-07 为什么最重要

它是**唯一一个专门防止"把没做的事说成做了"的检查**。

追溯矩阵最危险的失效模式不是"漏填"，而是"填高了"——把 `local_gate_passed` 写成 `strict_uat_passed`，让整条链路看起来完成了。AT-07 让这种越界**在提交前就失败**。

### 6.2 阳性对照

`--self-test` 用设计文档自身构造一份合规矩阵，验证比对逻辑**在正确时能变绿**。

> 一个只会报红的检查器没有价值。本门禁的阳性对照与 `api_contract_check.py` 同一思路。
>
> **自检已实际抓到我自己的 3 个 bug**：
> 1. AT-03 把设计文档的「按范围」「各阶段」当成非法阶段名（设计文档用自己的措辞，不是错）
> 2. AT-09 在自检模式下必然失败，导致阳性对照根本不可能通过
> 3. 中文引号写进 Python 字符串导致 SyntaxError
>
> 另外 AT-02 在真实矩阵上抓到 **5 处漂移**（我自造的 `cross` 阶段标签、给 AT-44/45
> 凭空补的工作包），以及 1 个未登记的 blocker。全部已修正。
> **这正是本门禁存在的意义：手工维护的追溯矩阵一定会漂。**

### 6.3 三个门禁的当前可运行状态（2026-10-01 实测）

| 门禁 | 真实基线 | 阳性对照 | 说明 |
|---|---|---|---|
| `api_contract_check.py` | exit **1**（如实报红：8/9 未达标） | exit **0** ✅ | 双向可信 |
| `at_traceability_check.py` | exit **0**（9/9 通过） | exit **0** ✅ | 双向可信 |
| `ddl_static_check.py` | exit **1** | 无该模式 | ⚠️ **跑不起来**：输出「需要 pglast」，`pglast` 未装进项目 `.venv` |

> **`ddl_static_check.py` 目前不是一个有效的门禁。**
> 它的退出码 1 是**依赖缺失**，不是「DDL 有问题」——两者在退出码上无法区分，
> 这本身就是个隐患：CI 里看到红灯会误判成 DDL 缺陷。
>
> 之前该工具的验证是在 `/tmp` 独立 venv 中做的（装有 pglast 8.4），
> **从未在项目自身环境中验证过**，这与「本地验证要用项目自身解释器 + 干净环境」
> 的纪律相悖。
>
> **处置（AT-T-6）**：把 `pglast` 声明为**开发依赖**（`backend/requirements-dev.txt`），
> 并让该脚本在依赖缺失时**以不同退出码**（如 2）退出，让「工具坏了」与「检查未过」可区分。
